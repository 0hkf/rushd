# متطلبات روافد العقارية — مسودة جديدة

تاريخ التحديث: 6 أكتوبر 2026.
الحالة: القرارات التالية أكدها صاحب المشروع؛ التفاصيل المفتوحة تحتاج إجابات قبل اعتماد الخطة النهائية.
هذا الملف يعيد بناء المتطلبات، ولا يدّعي استعادة خطة الثلاثة شهور الأصلية المفقودة.

## 1. الهدف والحدود

- موقع فعلي يعرض عقارات ويستقبل اهتمام العملاء، وليس مجرد عرض تجريبي.
- البداية في مكة. التوسع إلى مدن أخرى لاحقًا.
- عروض بيع وإيجار؛ الإيجار شهري أو سنوي بحسب العقار.
- الأدمن وحده يضيف المواصفات والأسعار وينشر ويعدل العقارات.
- لا دور بائع ينشر إعلاناته. تبقى الحسابات القديمة متوافقة دون صلاحيات نشر.
- هوية روافد العقارية الحالية: خلفية بيج وأحمر عنابي، عربية RTL ومتجاوبة.
- جميع الأنواع الحالية ضمن النطاق: أرض، شقة، فيلا، عمارة، تجاري، مزرعة، وأخرى (`LAND/APARTMENT/VILLA/BUILDING/COMMERCIAL/FARM/OTHER`).
- الميزة المميزة: مساعد يأخذ متطلبات المستخدم، ويرشح العقارات الأنسب من العروض المنشورة، ويبرر الترشيح أو تقييم عقار يختاره المستخدم.
- تقييم ملاءمة العقار للاحتياجات منفصل عن تقييم سعره مقارنة بالسوق؛ بيانات السوق يدخلها الأدمن مع مصادرها.
- الوقت مرن، وقد يمتد إلى سنة أو أكثر؛ لا موعد ملزم لثلاثة شهور. المتاح حاليًا ثلاثة أيام عمل أسبوعيًا، والساعات في اليوم لم تحدد.
- الميزانية المالية الحالية صفر. نبدأ بنموذج جاهز مستضاف ذاتيًا، لا تدريب من الصفر ولا اشتراك Gemini في المسار المعتمد.

## 2. التواصل

المطلوب للنسخة المستهدفة:

- زر اتصال هاتفي وزر واتساب للتواصل مع إدارة المنصة.
- إرفاق رابط أو رقم العقار في رسالة الواتساب المقترحة.
- إدارة بيانات الاتصال وإظهارها دون كشف بيانات مستخدمين أو حسابات الأدمن.
- الأرقام الفعلية ومن يديرها لم يحددا بعد.

مؤجل صراحة: نموذج طلب اهتمام داخل الموقع مع متابعة الطلبات بواسطة الأدمن. لا محادثة داخلية الآن.

## 3. الميزات المطلوبة

| الميزة | الحالة الحالية | المطلوب |
|---|---|---|
| الدخول والصلاحيات | منفذة ومختبرة | التحقق على بيئة النشر |
| إضافة وتعديل وعرض العقارات | منفذة ومختبرة | مراجعة المواصفات التفصيلية لكل نوع |
| البيع والإيجار | منفذان | إبقاء السعر مرتبطًا بفترته |
| الصور | غير منفذة | رفع آمن وترتيب وصورة رئيسية ومعرض |
| المفضلة | غير منفذة | حفظ وإزالة وعرض العقارات المفضلة |
| المقارنة | غير منفذة | مقارنة عقارين أو ثلاثة بنفس وحدات السعر والفترة |
| الموقع والخريطة | تخزين منظم فقط | اختيار موقع وعرض خريطة؛ خيار مجدٍ ضمن ميزانية صفر لم يعتمد |
| تحليل السعر | غير منفذ | حسابات قابلة لإعادة الإنتاج ومقارنة بمرجع موثق |
| جمع احتياجات المستخدم | منفذ ومتحقق محليًا | نموذج أسئلة للمسجلين فقط، يتحقق من المدخلات دون حفظ دائم؛ لا ترشيح بعد |
| ترشيح شخصي | غير منفذ | جمع الاحتياجات وتصفية وترتيب العقارات مع أسباب الملاءمة والتنازلات |
| تفسير AI | غير منفذ | شرح عربي للترشيح ولعقار يختاره المستخدم، اعتمادًا على أدلة متحققة |
| تقرير PDF | غير منفذ | مواصفات ونتائج ومصادر وتاريخ تحليل واضح |
| اتصال وواتساب | غير منفذين | تواصل مباشر مع إدارة المنصة |

اختيار جميع الميزات يعني إدراجها في النطاق المطلوب، ولا يعني أنها منفذة أو يلزم إطلاقها دفعة واحدة. الخطة مراحل بشروط إنجاز، وليست توزيعًا ثابتًا على 12 أسبوعًا.

## 4. رحلة الترشيح الشخصي — الميزة معتمدة والتفاصيل مقترحة

1. المستخدم يحدد بيعًا أو إيجارًا وفترته، ونوع العقار، والميزانية، والأحياء المفضلة، والمساحة، والغرض، ثم احتياجات تخص النوع.
2. يميز نموذج الإدخال بين شروط لا يمكن التنازل عنها وتفضيلات مرنة وأهميتها. قرار صاحب المشروع (`1A`): نموذج أسئلة واضح؛ لا محادثة في R1. أي إضافة لاحقة لاستخراج الاحتياجات من نص تؤكد قبل الترشيح.
3. الباكند يبحث في العروض المنشورة والمتاحة فقط، ويستبعد المخالف للشروط الإلزامية، ثم يرتب النتائج بقواعد واضحة قابلة للاختبار.
4. تظهر النتائج مع ما تحقق وما لم يتحقق وما هو مجهول. عدم وجود تطابق لا يسمح بتجاوز الميزانية أو الشروط بصمت؛ تعرض خيارات تخفيف يوافق عليها المستخدم.
5. عند اختيار عقار، يحصل المستخدم على تبرير مرتبط بمتطلباته، ونقاط قوة وتنازلات وبيانات ناقصة، وتصنيف ملاءمة مثل «مناسب جدًا / مناسب / مناسب جزئيًا / غير مناسب» بعد اعتماد قواعده.
6. النموذج اللغوي يشرح الأدلة، ولا يقرر أسعار السوق أو يغير ترتيب النتائج أو يخترع عقارات أو خدمات قريبة.

ضوابط التصميم المقترح:

- نمذجة المواصفات بحسب النوع: عرض الشارع والواجهة للأرض، وعدد الغرف والدور والمصعد للشقة، ومواصفات الوحدات للعمارة، وغيرها بعد الاعتماد. هذه الحقول ليست كلها موجودة الآن.
- عدم خلط مساحة الأرض بالمساحة الصافية للشقة أو إجمالي مساحة البناء. لا درجة عامة واحدة لجميع الأنواع دون قواعد خاصة بها.
- معلومة مجهولة لا تعتبر شرطًا متحققًا. تعرض تغطية البيانات، ولا تقدّم نسبة الملاءمة كاحتمال ربح أو نجاح استثمار.
- «قريب من متطلباتك» يعني توافق المواصفات؛ المسافة الفعلية إلى مدرسة أو الحرم مثلًا لا تذكر دون بيانات موثقة، وزمن القيادة يحتاج خدمة ومسارًا منفصلين.
- قواعد الأوزان وحدود التصنيف وعدد النتائج تتحدد بعينات اختبار واقعية قبل النشر؛ لا درجة من 100 معتمدة الآن.
- قرار الوصول (`2B`): جمع الاحتياجات والترشيح للمسجلين فقط؛ لا إتاحة للزوار في هذه النسخة. الاحتياجات مؤقتة دون حفظ دائم.
- نتائج المستخدم تولد حسب احتياجاته. الأدمن مسؤول عن جودة العقارات والمراجع، وليس مطلوبًا اعتماد كل ترشيح يدويًا. مراجعة جودة القواعد والقوالب قبل الإطلاق مطلوبة.

## 5. بيانات السوق والتحليل — تصميم مقترح ينتظر الاعتماد

- الأدمن يدخل مرجع السوق ومصدره وتاريخه ونطاقه، لا رقم متوسط مجهول المصدر فقط.
- المرجع يميز المدينة والحي ونوع العقار والبيع أو الإيجار وفترته ووحدة السعر.
- يميز سعر العرض عن سعر صفقة فعلية. لا تجمع مراجع غير قابلة للمقارنة أو بيانات قديمة بلا تنبيه.
- الباكند يحسب المؤشرات المناسبة للنوع وفارق السعر عن مرجع قابل للمقارنة بصورة حتمية. سعر المتر يستخدم فقط عندما تكون وحدة المساحة ومعنى المقارنة صالحين، لا قاعدة عامة لكل العقارات.
- للإيجار تقارن نفس الفترات أو تحولها إلى وحدة موحدة مع إظهار التحويل. لا تخلط السعر الشهري والسنوي أو سعر البيع.
- عدم وجود مرجع صالح ينتج «بيانات غير كافية لتقييم السعر»، لا قيمة سوقية مختلقة.
- انخفاض السعر وحده لا يثبت جودة العقار أو سلامته أو ملاءمته للاستثمار.
- مخرجات تحليل السعر منفصلة عن الملاءمة: موضع سعر العرض بالنسبة للمرجع، أسباب الحكم، نقص البيانات، المصدر والتاريخ وحدود التحليل.
- قد يكون العقار مناسبًا للاحتياجات لكن سعره أعلى من المرجع، أو رخيصًا لكنه غير مناسب. لا ضمان ربح أو ارتفاع مستقبلي ولا ادعاء تقييم مهني معتمد.

## 6. الذكاء الاصطناعي والاستضافة والأمان

قرار المستخدم لمسار AI في الأسئلة السابقة: نموذج جاهز مستضاف ذاتيًا. اختيار النموذج النهائي ومكان تشغيله العام لم يعتمدا بعد؛ التشغيل المحلي مرشح للبداية بميزانية صفر. هذا قرار منفصل عن `2B` الأخير الذي يحدد إتاحة الترشيح للمسجلين فقط.

التوصية الهندسية المقترحة وليست قرارًا معتمدًا:

- إبقاء React وSpring Boot وPostgreSQL؛ المصادقة والصلاحيات والبيانات والتصفية والترتيب والحسابات داخل الباكند الحالي.
- تجربة `Qwen3:4b` مضغوط عبر Ollama لتفسير الأدلة بالعربية. مواصفات الجهاز التي قرئت: `arm64` وذاكرة 16 GiB؛ هذه قرينة على جدوى التجربة، لا اختبار سرعة أو جودة. لم ينزل النموذج أو يشغل بعد.
- قياس صحة التفسير العربي، الالتزام بالمصدر، زمن الاستجابة، واستهلاك الذاكرة مع تشغيل الباكند والواجهة. نموذج أصغر أو قوالب تفسير حتمية بديل إذا لم يحقق الاختبار.
- Spring Boot يمكن أن يتصل بـOllama داخل شبكة خاصة مباشرة. FastAPI اختياري عندما نحتاج خدمة Python أو معالجة خاصة، وليس سببًا لاستبدال الباكند أو إعادة بناء المصادقة.
- يبدأ الترشيح بقواعد وقوالب مفيدة حتى دون نموذج؛ يضاف التفسير اللغوي بعد اجتياز بوابة الجودة.
- تدريب من الصفر ليس ضمان أمان أو دقة، وليس ضمن الخطة الحالية. نموذج تقدير سعر إحصائي لاحقًا يحتاج بيانات مرخصة واختبارًا مستقلًا عن النموذج اللغوي.

الأمان المقترح للخدمة الجديدة (غير منفذ):

- لا ترسل بيانات الحسابات أو أرقام الاتصال أو الأسرار إلى النموذج. أوصاف العقارات تعامل كبيانات غير موثوقة لا تعليمات.
- إرسال حزمة صغيرة من متطلبات غير معرفة بهوية المستخدم وحقائق المرشحين ونتائج الحسابات، لا تفريغ قاعدة البيانات.
- مخرجات منظمة تتحقق منها خدمة الباكند، ومعرفات عقارات مسموحة فقط؛ بلا وصول للنموذج إلى SQL أو تعديل البيانات أو نشر العقارات أو تنفيذ أدوات. عرض النص بأمان دون HTML غير موثوق.
- منع إتاحة Ollama أو FastAPI مباشرة للعامة؛ الطلبات تمر بالباكند مع حدود طول وتكرار وتزامن ومهلة، واتصال خاص موثق عند فصل الخدمة.
- الوضع المحلي فقط وتعطيل ميزات Ollama السحابية؛ الاستضافة الذاتية على سحابة لا تعني أن البيانات لا تغادر جهاز المستخدم. التشغيل المحلي يزيد التحكم بالبيانات لكنه لا يضمن الأمان تلقائيًا.
- مخرج بديل يعرض الترتيب والأسباب المحسوبة عند فشل النموذج. حفظ احتياجات المستخدم ومدتها يحتاج موافقة وقرارًا؛ السجلات لا تحفظ المحتوى الحساس افتراضيًا.
- ربط النتيجة بنسخة بيانات العقار والمراجع والقواعد والنموذج وتاريخها؛ إبطال التخزين المؤقت عند التغيير والتحقق من صلاحية النشر قبل إعادة نتيجة قديمة.

مصادر التقنية والاستضافة راجعت في 6 أكتوبر 2026، وتحتاج مراجعة عند التنفيذ:

- [FastAPI](https://fastapi.tiangolo.com/): إطار Python لبناء API، لا نموذج ولا استضافة مجانية بحد ذاته.
- [Qwen3-4B](https://huggingface.co/Qwen/Qwen3-4B): نموذج متعدد اللغات بترخيص Apache 2.0. [نسخة Ollama](https://ollama.com/library/qwen3:4b) المضغوطة `Q4_K_M` حجم تنزيلها نحو 2.5 GB، وليس هذا إجمالي ذاكرة التشغيل.
- [Ollama FAQ](https://docs.ollama.com/faq): التشغيل المحلي لا يرسل المدخلات إلى Ollama؛ يمكن تعطيل ميزات السحابة بـ`OLLAMA_NO_CLOUD=1`. الجهاز يجب أن يبقى يعمل لخدمة الطلبات؛ ليست استضافة عامة مضمونة 24/7.
- [Hugging Face Spaces](https://huggingface.co/docs/hub/spaces-overview): إنشاء Gradio/Docker compute Space جديد يحتاج خطة مدفوعة حاليًا، رغم عدم وجود تكلفة بالساعة لـCPU Basic. لذلك لا نعتمده كاستضافة FastAPI مجانية لحساب جديد.
- [ZeroGPU](https://huggingface.co/docs/hub/main/spaces-zerogpu): استثناء للتجارب؛ حتى مساحتين للحساب الشخصي المؤهل (بريد موثق وعمر أكثر من 30 يومًا)، Gradio فقط، حصص يومية وطوابير. ليس خدمة استدلال إنتاجية مضمونة.
- [Oracle Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): مرشح سحابي مشروط بتوافر الموارد؛ الحد المنشور حاليًا لـARM هو 2 OCPU و12 GB RAM، وقد تسترد الموارد الخاملة. [إنشاء الحساب](https://www.oracle.com/cloud/free/faq/) يحتاج عادة تحقق بطاقة وهوية. الأداء والصلاحية لهذا المشروع لم يختبرا، ولا ينشأ حساب أو مورد الآن.

التشغيل بلا فاتورة للنموذج على الجهاز الحالي ممكن للتطوير، لكنه يستهلك موارد وكهرباء. الاستضافة العامة للباكند وقاعدة البيانات والصور والخرائط تحتاج خطة موارد منفصلة؛ الميزانية الصفرية لا تضمن كل الميزات وخدمة مستمرة مجانًا. اختيار مزود الخريطة مؤجل، ولا إضافة مفتاح Google أو Gemini خلال التخطيط.

## 7. شروط قبول مقترحة

- لا يمكن لغير الأدمن إنشاء أو تعديل العقارات عبر HTTP، لا مجرد إخفاء أزرار.
- لا تظهر المسودات أو الصور الخاصة للعامة، ورفع الملفات يتحقق من النوع والحجم والمحتوى والصلاحية.
- العقارات دون صور أو موقع تفصيلي تبقى قابلة للعرض.
- المقارنة تبين الاختلاف في الأنواع والفترات ولا تقدم أسعارًا مختلطة كمقارنة عادلة.
- الترشيح لا يتجاوز الشروط الإلزامية؛ حالات عدم وجود تطابق ونقص المواصفات مختبرة لكل نوع.
- الترتيب قابل لإعادة الإنتاج، والتفسير مرتبط بمعرفات وحقائق عقارات منشورة فقط؛ الطلب لا يكشف المسودات أو بيانات حسابات الإدارة.
- العقار الذي يختاره المستخدم يقيم حتى إن كان غير مناسب، دون مجاملة أو تحويل نقص البيانات إلى حكم إيجابي.
- AI لا يخترع متوسط السوق أو يكتم نقص البيانات أو يجعل الدرجة حقيقة مؤكدة.
- مجموعة اختبار عربية تشمل اختلاف الميزانية والأنواع وفترات الإيجار، ووصفًا يحاول حقن تعليمات، وتغيير بيانات العقار ونتيجة قديمة.
- تعطل AI/الخرائط لا يمنع عرض المواصفات والتواصل.
- PDF يعكس نفس نسخة البيانات والنتائج المعروضة، مع تاريخ ومصدر وتنبيه تقديري.
- اختبار متكامل على PostgreSQL وHTTPS والمتصفح والجوال قبل الإطلاق، مع إعداد النسخ الاحتياطي والمراقبة.

## 8. خارج النطاق الحالي

- نشر بائع، محادثة داخلية، دفع أو تحصيل أو إدارة عقود إيجار.
- الطلبات داخل الموقع مرحلة مستقبلية وفق قرار المستخدم.
- تدريب من الصفر، اشتراك AI مدفوع، أو توسيع المدن لا يعتمد دون قرار منفصل.

## 9. قرارات مفتوحة

1. المواصفات التفصيلية والأوزان الخاصة بكل نوع؛ طريقة الإدخال حسمت كنموذج أسئلة واضح.
2. حفظ الاحتياجات مستقبلًا بموافقة ومدد واضحة؛ الوصول حسم للمسجلين فقط، ولا حفظ دائم في R1.
3. توفر مصادر مرجع السوق وحجمها وتواتر تحديثها؛ يمكن بدء الملاءمة دون حكم على السعر إن لم تتوفر.
4. عدد ساعات العمل في كل يوم من الأيام الثلاثة، ومن يشارك في التنفيذ.
5. التجربة محليًا أولًا أم تجربة عامة محدودة؟ هل يوجد حساب أو مورد استضافة مجاني قائم، وما حدود خصوصية بيانات الاحتياجات؟
6. مزود الموقع والخرائط وتخزين الصور واستضافة بقية المنصة ضمن الموارد المتاحة، وأرقام الاتصال الفعلية.
7. قواعد الملاءمة وحدود التصنيف ومعايير قبول النموذج النهائي؛ لا يختار النموذج نهائيًا قبل تجربة فعلية.

راجع [خطة العمل المبدئية](roadmap.md). هذه وثيقة تخطيط، لا تعني تنفيذ الترشيح أو AI؛ لا تنزيل نموذج أو إنشاء استضافة أو إضافة مفاتيح خلال جمع المتطلبات.

اكتمل أول متطلب محليًا: [R1 — احتياجات المستخدم العقارية](requirement-01-user-needs.md)، مع [عقد التحقق](api-property-needs.md). النموذج والتحقق لا يعنيان تنفيذ محرك الترشيح أو AI أو جاهزية PostgreSQL والنشر.
