# R2 — قواعد المطابقة الأساسية وR3 — تنفيذها

تاريخ البدء: 13 أكتوبر 2026.
الحالة المحدثة في18 أكتوبر2026: القواعد والمطابقة الأساسية منفذتان ومتحققتان على H2 وPostgreSQL16.11 محلي معزول والمتصفح وفق [P02](p02-postgres-matching-verification.md). ليست النسخة جاهزة للنشر بمجرد ذلك. نتائج13 أكتوبر أدناه سجل تاريخي سابق لا حالة التحقق الحالية.
المرجع: [المتطلبات](requirements.md)، [الخطة](roadmap.md)، [مدخلات R1](api-property-needs.md).

## القرارات المعتمدة

1. تعرض العقارات المجتازة للشروط الأساسية بترتيب عدد التفضيلات المتحققة تنازليًا، ثم الأحدث. كل تفضيل له وزن واحد؛ لا درجة من 100.
2. توحيد المسافات وإزالة بادئة «حي» مرة واحدة من بداية اسم الحي عند المقارنة فقط. مثال: «حي الياسمين» يطابق «الياسمين».
3. لا تغيير تلقائي للسجلات القديمة، ولا تشابه تخميني أو Google أو AI أو حكم على عدالة السعر.

المطابقة في هذه النسخة تتناول المواصفات المشتركة الموجودة فقط. «مطابق للشروط الأساسية» لا تعني «أفضل استثمار» أو «مناسب جدًا» أو تحققًا ميدانيًا للمواصفات.

## نتيجة فحص البيانات

- `Property` يحفظ النوع، حالة النشر، نوع العرض وفترة الإيجار، المدينة، الحي، السعر والمساحة.
- توجد حقول اختيارية منفصلة للموقع (`neighborhood` وغيره)؛ ليست بديلًا تلقائيًا عن `district`.
- لا معرف حي معياري ولا تعريف منفصل لمساحة الأرض والصافي والبناء، ولا مواصفات غرف أو مصعد أو مواقف أو وحدات.
- `searchGoal` في R1 نية المستخدم؛ `purpose` استخدام مسجل للعقار. لا يمكن مساواتهما أو إثبات جدوى الاستثمار منهما.
- السعر المعلن يعتبر SAR وفق نموذج المنصة الحالي؛ لا يوجد حقل عملة أو تحويل عملات. الرسوم والضرائب والتكاليف الإضافية ليست ضمن مطابقة الميزانية.
- استجابات المطابقة تعيد السعر والمساحة كسلاسل دقيقة. بعد تغيير T01/T02 المعتمد أصبحت حقول العقار العشرية الخمسة في التصفح/CRUD أيضًا نصوصًا دقيقة وفق [عقد العقارات](api-properties.md)؛ لم يضف P02 تغييرًا جديدًا للعقد.
- قائمة التصفح الحالية لا تنفذ هذه القواعد؛ لا ترتب أول صفحة منها وتسمي الناتج «أفضل العقارات».
- لم يفحص مخزون قاعدة المشروع الفعلية أو يعدل. أمثلة الاختبارات صناعية فقط.
- افتراض توافق البيانات: ترقية البيع/الإيجار السابقة تطبق على القواعد القديمة وتجعل `listingType=SALE` للسجلات التراثية. R3 لا يجري هذه الترقية ولا يستنتج نوع عرض لسجل SQL ما زال null؛ تشغيل قاعدة قديمة يبقى مرتبطًا بترقيتها الموثقة.

## شروط الأهلية الدائمة

| الشرط | القاعدة |
|---|---|
| حالة النشر | `ACTIVE` فقط، حتى لو كان طالب المطابقة أدمنًا؛ لا `DRAFT/INACTIVE/SOLD` |
| المدينة | نطاق مكة وفق قائمة أسماء صريحة أدناه؛ غياب مدينة معروفة لا يحقق النطاق |
| النوع | نفس `type` المطلوب من الأنواع السبعة؛ لا بديل تلقائي |
| نوع العرض | نفس `SALE/RENT`، مع إبقاء توافق البيع التراثي الموثق للعقار |
| فترة الإيجار | نفس `MONTHLY/YEARLY` تمامًا؛ لا تحويل سعر شهري إلى سنوي أو العكس |
| السعر | معلوم وموجب، وأقل من الميزانية أو مساوٍ لها؛ المقارنة بـ`BigDecimal` |

الطلب نفسه يعاد التحقق منه بقواعد R1 في الخادم. لا تعتمد المطابقة على أن المستخدم ضغط زر المراجعة أولًا، ولا على تحقق الواجهة فقط.

## الحي والمساحة

| الاختيار | بيانات متوافقة | بيانات مختلفة | بيانات مجهولة |
|---|---|---|---|
| `REQUIRED` | يبقى العقار، والشرط متحقق | يستبعد العقار | يستبعد؛ المجهول ليس تطابقًا |
| `PREFERRED` | يبقى ويحتسب تفضيلًا واحدًا | يبقى مع توضيح الاختلاف، دون نقطة | يبقى مع توضيح النقص، دون نقطة |
| غير مطلوب | لا شرط ولا نقطة | لا شرط ولا نقطة | لا شرط ولا عقوبة |

- الحي يقارن مع `Property.district` فقط، وليس `neighborhood` أو العنوان أو الوصف أو معرف Google. التعارض لا يحل باختيار النص الذي يحسن النتيجة.
- نطاق المساحة حدوده شاملة، وكل حد يعمل منفردًا. الحد الأدنى والأعلى معًا يمثلان تفضيل مساحة واحدًا، لا تفضيلين.
- المساحة المجهولة أو غير الموجبة لا تحقق شرط المساحة. تقارن المساحة المسجلة في الإعلان داخل النوع نفسه؛ لا تحويل لمعنى الأرض أو الصافي أو البناء.
- طلب بلا حي أو بلا نطاق لا يتحول إلى شرط ضمني. افتراضات R1 تبقى: الحي تفضيل، والمساحة شرط عند توفيرها دون تحديد الأهمية.
- `searchGoal` يعاد ضمن ملخص الاحتياجات، لكنه لا يستبعد عقارًا ولا يمنحه نقطة أو سبب ملاءمة. تظهر حدود تقييم هذا الهدف بوضوح.

## أسماء الموقع — مقارنة فقط

تزيل دالة مقارنة مشتركة المسافات الطرفية، وتوحد متتابعات whitespace Unicode إلى مسافة واحدة. لا تعدل النص الأصلي أو قاعدة البيانات أو `/api/properties` القديم.

قائمة أسماء مكة المحدودة للمخزون في النسخة الأولى: `مكة`، `مكة المكرمة`، `Makkah` (دون حساسية لحالة الأحرف اللاتينية). لا استنتاج للمدينة من الإحداثيات أو العنوان أو الحي؛ أي اسم آخر يحتاج alias صريحًا ومراجعة لاحقة. مدخل `city` في R1 يظل `مكة المكرمة` بالضبط أو null/غائبًا.

في الحي، بعد توحيد المسافات، تزال كلمة `حي` مرة واحدة فقط إذا كانت كلمة منفصلة في البداية. الاسم `حي` وحده لا يصبح حيًا متطابقًا صالحًا. لا إزالة داخل الكلمة أو تكرار حذف البادئة، ولا تحويل ة/ه أو ي/ى أو الهمزات، ولا حذف التشكيل أو علامات الترقيم. `%` و`_` نصوص حرفية وليستا wildcard.

هذه مساواة نصية محافظة، لا إثبات أن الاسم مسجل رسميًا. لا يدّعي النظام امتلاك سجل حكومي للأحياء. تبقى أسماء الأحياء الأصلية ظاهرة للمستخدم، حتى عندما تتساوى مفاتيح المقارنة.

## الترتيب والصفحات وحد المعالجة

1. تستبعد مخالفة الشروط الأساسية و`REQUIRED` أولًا.
2. يحسب `preferredMatchedCount` من `PREFERRED` المتحقق فقط، و`preferredCount` من التفضيلات المطلوبة فقط. كلاهما من صفر إلى اثنين؛ ليسا درجة ملاءمة أو نسبة نجاح.
3. يرتب العدد المتحقق تنازليًا، ثم `createdAt` تنازليًا (التاريخ المجهول أخيرًا)، ثم `id` تنازليًا لحسم التعادل.
4. عند غياب التفضيلات أو تعادلها يصبح الترتيب بالأحدث ثم المعرف. السعر الأرخص أو المساحة الأكبر لا يمنحان وزنًا خفيًا.
5. يحسب ترتيب كامل مجموعة المطابقة قبل تقسيمها إلى صفحات. حجم الصفحة لا يغير ترتيب النتائج ما دامت البيانات ثابتة. لا snapshot دائم؛ قد تتغير الصفحات إذا عدل الأدمن المخزون بين الطلبات.

حد وقائي تقني للنسخة الأولى: الاستعلام الأولي يرشح `ACTIVE` والنوع ونوع العرض وفترة الإيجار والسعر والمساحة الإلزامية، ويحمل بحد أقصى 1001 سجل. إذا تجاوز المرشحون الأوليون 1000، يعيد `422` برسالة تضييق البحث، ولا يعرض عينة أو نتيجة فارغة أو يدعي ترتيب كامل المخزون. هذا الحد يطبق **قبل** تطبيع المدينة والحي، وقد يحتسب عقارات خارج مكة؛ ليس عدد النتائج النهائية.

هذا حد لحجم العمل في الطلب الواحد، وليس rate limit لكل مستخدم ولا حماية مكتملة من إساءة الاستخدام؛ حدود التكرار والأداء على بيئة النشر تبقى ضمن تجهيز الإطلاق.

عند تجاوز الحد يمكن تضييق الميزانية أو المساحة الإلزامية. تحويل الحي إلى شرط وحده لا يضمن تقليل المجموعة الأولية في هذه البنية. دعم مخزون أكبر يتطلب نقل التطبيع والترتيب إلى استعلام/فهارس مختبرة على PostgreSQL لاحقًا؛ لا تحميل غير محدود ولا تخمين بأن أول ألف يمثلون الأفضل.

## عقد تنفيذ R3

- مسار جديد: `POST /api/property-needs/matches?page=0&size=10`؛ `page >= 0` و`size` من 1 إلى 20. تفاصيل الجسم والاستجابة في [عقد المطابقة](api-property-matching.md)؛ الإنجاز لا يثبت إلا بنتائج التحقق النهائية أدناه.
- الجسم هو `PropertyNeedsRequest` الحالي. `/validate` يبقى للتحقق والملخص فقط، ولا يغير استجابته.
- الوصول لكل حساب مسجل ضمن المصادقة الحالية، مع CSRF؛ لا تغيير صلاحيات إدارة العقارات ولا توفير مسار ضيف.
- الاستجابة: ملخص `needs`، قائمة `content`، `page/size/totalElements/totalPages`، و`rulesVersion=matching-v1` و`sort=PREFERENCES_THEN_NEWEST`.
- كل نتيجة تعرض هوية العقار وعنوانه ونوعه وعرضه وفترته ومدينته وحيه، `price/area` كسلاسل دقيقة (المساحة المجهولة null)، تاريخ الإضافة، عددي التفضيلات، `districtMatch/areaMatch` وأسبابًا واقعية بقوالب ثابتة.
- حالات المعيار: `MATCHED/MISMATCHED/UNKNOWN/NOT_REQUESTED`. لا أسماء حسابات أو بريد أو رموز دخول ضمن عقد المطابقة.
- `401/403/400` كما في R1، و`422` للنطاق الأوسع من حد المعالجة. صفر نتائج فعلية يعيد `200` وقائمة فارغة وعددًا صفرًا؛ لا تخفيف تلقائي للشروط.
- الواجهة تحتفظ بزر المراجعة، وتضيف عرض النتائج والصفحات. أي تعديل أو مسح أو خروج أو تغير حساب يلغي الطلب المعلق ويمسح النتائج والملخص. الصفحات تستخدم نسخة الاحتياجات المرسلة، لا خليطًا مع مدخلات أحدث.

تقييم عقار مختار بمعرفه، وتصنيفات «مناسب جدًا» والأوزان التفصيلية، ومرجع السوق وAI والمواصفات الخاصة بالأنواع خارج R3 الأساسي هذا.

## مصفوفة القبول

| المجموعة | الحالات | النتيجة المنتظرة |
|---|---|---|
| الوصول | زائر برمز صالح / رمز غائب أو خاطئ | `401` / `403`؛ لا نتائج خاصة أو بيانات حساب |
| التحقق | جسم R1 غير صالح، enum رقمي، حقول مجهولة، أرقام ضخمة | `400` قبل استعلام المرشحين |
| النشر | سجلات متطابقة بـACTIVE/DRAFT/INACTIVE/SOLD، بطلب أدمن أيضًا | ACTIVE فقط، ولا أعداد أو أسباب تكشف حالات خاصة |
| النوع | الاختبار لكل نوع من السبعة | نفس النوع فقط |
| العرض | بيع/إيجار/فترة مختلفة، إيجار دون فترة، بيع بفترة غير صالحة | لا خلط أو تحويل؛ السجل غير القابل للمقارنة لا يرشح |
| السعر | عند الحد، أقل بـ0.01، أعلى بـ0.01، مجهول/غير موجب، فوق دقة JS | حد شامل ومقارنة وعرض دقيقان، ولا سعر سوقي مختلق |
| المدينة | الأسماء الصريحة، مسافات زائدة، مدينة أخرى، اسم مجهول/null | نطاق مكة فقط دون إعادة كتابة المخزون |
| الحي | «حي الياسمين»/«الياسمين»، Unicode whitespace، «حي» وحده، بادئة مكررة، `%/_`، تعارض neighborhood | مقارنة محافظة حرفية من district فقط |
| المساحة | حد واحد، حدان، تساوي الحدود، القيم عند الحدود، مجهول/غير موجب | المقارنة شاملة والمجهول لا يحقق شرطًا |
| الأهمية | كل من REQUIRED/PREFERRED وغير المطلوب مع match/mismatch/unknown | طبق جدول الأهمية، دون خلط شرط وتفضيل |
| الترتيب | صفر/واحد/تفضيلان، شرط مطلوب لا يحتسب، نطاق بحدين، أفضل تطابق بعد أول 100 | العد الصحيح ثم ترتيب كامل قبل الصفحات |
| التعادل | تاريخان متساويان، تاريخ مجهول، لا تفضيلات، أحجام صفحات مختلفة | createdAt ثم id كما هو موثق، وترتيب ثابت لبيانات ثابتة |
| الهدف | INVESTMENT مع purpose RESIDENTIAL أو غيره | لا فلتر أو نقطة أو ادعاء جدوى أو قرب خدمات |
| الفراغ | لا مرشحين / صفحة بعد النهاية | قائمة فارغة صريحة، ولا تغيير احتياجات المستخدم |
| الحدود | 1000/1001 مرشح أولي، page كبير، size 0/21، قيمة سالبة | نجاح داخل الحد، 422 فوقه، 400 لمعلمات غير صالحة، دون overflow |
| الخصوصية | تكرار الطلب، تغيير الحساب، الخروج، الرد المتأخر، تعديل الاحتياجات | لا حفظ دائم أو نتائج قديمة أو خلط حسابات |
| التوافق | /validate والتصفح وCRUD والمصادقة السابقة | تبقى العقود والصلاحيات القديمة تعمل |

## بوابة الإنجاز

- اكتمال عقد R3 واختباراته وربطه بالواجهة وتجربة الجوال، مع مراجعة أمان ودقة.
- تشغيل `mvn clean test` واختبارات وبناء وفحص الواجهة؛ توثيق الأعداد النهائية، لا إعادة استخدام أعداد R1 كدليل على R3.
- تجربة PostgreSQL في قاعدة مؤقتة معزولة عند توفر البيئة، دون تطبيق ترقية أو بيانات تجريبية على قاعدة المشروع الفعلية.
- التحقق من H2 وحده لا يغلق اختبار PostgreSQL أو جاهزية النشر. لا commit أو push تلقائيًا لهذا العمل.

## نتيجة التحقق — 13 أكتوبر 2026

- `mvn clean test`: نجح 199 اختبارًا، بلا فشل أو أخطاء أو تخطٍّ. تشمل 49 حالة جديدة لمطابقة HTTP والتحقق قبل الاستعلام وحدود الخدمة وتطبيع الموقع؛ اختبارات R1 والعقارات والمصادقة السابقة ما زالت ناجحة.
- `npm test`: نجح 26 اختبارًا، بينها 8 لحالات العرض والصفحات ونسخة الاحتياجات وإلغاء الردود القديمة. `npm run build` و`npm run lint` نجحا.
- تجربة HTTP بباكند H2 مؤقت وcookies ورمز CSRF حقيقيين: ترتيب التفضيلات، السعر الدقيق، الشروط الأساسية، المجهول، الصفحات، الإيجار الشهري والسنوي، `400/401/403`، وصفر النتائج و`422` فوق الحد نجحت. طلب الأدمن بقي ACTIVE فقط، وR1 بقي ملخصًا دون نتائج.
- تجربة متصفح بحساب اختباري: الأرقام العربية، ترتيب تفضيلين قبل تفضيل واحد، التنقل بين صفحتين، إزالة النتائج عند التعديل، صفر النتائج دون تخفيف، خطأ البحث الواسع دون ادعاء انعدام المخزون، مراجعة R1، الإيجار الشهري والسنوي، المسح والخروج نجحت.
- فحص تصميم عند `1280×900` و`390×844` بلا تجاوز أفقي، مع عرض الأرقام كسلاسل دقيقة وأسباب الاختلاف والمجهول.
- بيئة المعاينة والبيانات والحسابات كانت صناعية ومؤقتة داخل الذاكرة وعلى loopback؛ أوقفت بعد التحقق، ولم تستخدم أو تعدل قاعدة المشروع الفعلية.
- Docker Desktop موجود، لكن daemon لم يجب على أوامر القراءة أو `_ping` عبر socket خلال مهلة الفحص. لا تتوفر أدوات PostgreSQL محلية في PATH. لم يعاد تشغيل Docker أو تمس حاوياته؛ **لم ينفذ اختبار PostgreSQL**. الخطوة المتبقية تشغيله في قاعدة معزولة عند توفر البيئة، لا إغلاقه استنادًا إلى H2.
- لا أعمدة أو dependencies أو مفاتيح أو Google/AI أو صور أو خرائط أو حفظ دائم أضيفت، ولا commit أو merge أو push أجري لهذا العمل.
