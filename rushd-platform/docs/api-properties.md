# عروض العقارات — يشمل مواصفات P04 وربط الواجهة P05

P10 يضيف `primaryImage` descriptor أوnull فقط إلى الاستجابة، دون تغيير الحقول القديمة أو المطابقة. [عقد الصور والتفعيل المنفصل](api-property-images.md). P11/P12 منفذتان ومختبرتان معزولًا؛ الصور معطلة افتراضيًا، ولم تعتمد ترقية قاعدة المشروع وتفعيلها. [مرجع التشغيل الحالي](local-development-setup.md).

## الصلاحيات

GET /api/properties عام ويعرض ACTIVE فقط. GET /api/properties/{id} عام للحالات ACTIVE وSOLD؛ المسودات والحالات غير المنشورة متاحة للأدمن فقط، وغيره يحصل على 404.

POST /api/properties وPUT /api/properties/{id} يتطلبان access cookie لحساب ADMIN مع CSRF. الأدمن يستطيع تعديل جميع العقارات، بما فيها القديمة، دون تغيير ناشرها الأصلي. الحساب غير المسجل يحصل على 401 وغير الأدمن على 403.

GET /api/admin/properties للأدمن فقط، يعرض جميع الحالات بصفحات من 20 سجلًا، page يبدأ من صفر، وترتيب createdAt ثم id تنازليًا.

## البيع والإيجار

تحديث عقد25أكتوبر2026 معتمد من المستخدم: حقول`type/listingType/rentalPeriod/facade/purpose/status` فيCreate/Update تقبل أسماءenum النصية المعروفة فقط، بحالتها الدقيقة، مثل`LAND` و`ACTIVE`. الأرقام مثل`0`، والنص`"0"`، والقيم المنطقية والأسماء غير المعروفة ترفض400. هذا لا يغيرrequired/null/default لكل حقل، ولا إعداداتJackson العامة، ولا قبول أرقامJSON الصحيحة للأسعار والمساحات والإحداثيات أو نصوصها العشرية الدقيقة. عميل يرسلordinal رقميًا يحتاج تحديثًا؛ الواجهة الحالية ترسل الأسماء أصلًا.

- listingType: SALE أو RENT، الافتراضي SALE عند غياب الحقل؛ null غير مقبول.
- rentalPeriod: MONTHLY أو YEARLY؛ مطلوب للإيجار، ويجب أن يكون null أو غائبًا للبيع.
- price: قيمة موجبة؛ إجمالي سعر البيع أو قيمة الإيجار للفترة المحددة. لا تحويل آلي بين الشهري والسنوي.
- purpose يبقى استخدام العقار، ولا يستبدل نوع العرض.
- status يبقى ACTIVE/DRAFT/INACTIVE/SOLD؛ حالة «مؤجر» ليست منفذة.

### اتساق حالة العرض — P01

| نوع العرض | الحالات المقبولة في Create/Update |
|---|---|
| SALE | ACTIVE / DRAFT / INACTIVE / SOLD |
| RENT (MONTHLY أو YEARLY) | ACTIVE / DRAFT / INACTIVE |

`RENT + SOLD` يعيد `400` قبل أي وصول إلى PropertyRepository، برسالة في `message.listingStatusValid`: «حالة مباع لعروض البيع فقط. اختر حالة مناسبة للإيجار قبل الحفظ.». هذا المفتاح خطأ تحقق مشتق، وليس حقلًا جديدًا في الطلب أو الاستجابة؛ إرسال `listingStatusValid: true` لا يتجاوز القاعدة. غياب أو null لحالة الإنشاء يبقى ACTIVE افتراضيًا، بينما حالة التعديل مطلوبة كما كانت.

السجلات القديمة غير المتوافقة تبقى قابلة للقراءة دون تعديلها من مجرد العرض. قواعد القراءة لا تتغير: SOLD متاح في التفاصيل العامة، وليس ضمن قائمة ACTIVE أو المطابقة؛ يشمل ذلك سجل RENT+SOLD قديمًا. عند تحريره يطلب الفورم اختيار حالة صحيحة صراحة، ولا يحوله إلى ACTIVE. تحول الأدمن من SALE+SOLD إلى RENT يحافظ على SOLD مع خطأ واضح حتى التصحيح، فلا يعاد النشر تلقائيًا. لا تعديل enum أو schema أو قيود القاعدة في P01؛ التحقق هنا في حدود API، وليس قيد DB جديدًا على الكتابة المباشرة.

الطلب يحافظ على الحقول المطلوبة السابقة: title,type,city,district,area,price,purpose. PUT هو تعديل كامل للحقول السابقة، وليس PATCH؛ omission لحقول الموقع الاختيارية يزيل قيمها، وغياب listingType يجعله SALE. الاستثناء الإضافي المقصود: قسم `specifications` الجديد يدمج الحقول المقدمة فقط، كما هو موضح أدناه؛ لا تتغير دلالة أي حقل قديم.

مثال إنشاء إيجار:

```json
{
  "title":"شقة في حي الياسمين",
  "type":"APARTMENT",
  "city":"الرياض",
  "district":"الياسمين",
  "area":"150.00",
  "price":"4500.00",
  "purpose":"RESIDENTIAL",
  "listingType":"RENT",
  "rentalPeriod":"MONTHLY",
  "status":"ACTIVE",
  "neighborhood":"حي الياسمين"
}
```

## الموقع المنظم

googlePlaceId (255 حرفًا)، formattedAddress (500)، neighborhood (150)، latitude من -90 إلى 90، longitude من -180 إلى 180. جميعها اختيارية وتقبل null. المدينة والحي يبقيان مطلوبين.

التخزين latitude/longitude من نوع numeric(10,7). يوجد فهرس غير فريد على google_place_id؛ عدة عقارات يمكن أن تشترك في الموقع نفسه. لا خرائط ولا URL موقع ولا اتصال بخدمات Google ولا مفتاح API.

## المواصفات بحسب النوع — P04

تستخدم [واجهة P05](p05-property-specifications-ui-verification.md) هذا العقد دون تغييره: ترسل الحقول المتغيرة فقط، وتحول الإدخال العربي/الفارسي محليًا، وتعرض أثر تغيير النوع/النطاق قبل الإزالة. بقاء الحقول القديمة كاملة في PUT واستثناء الدمج للمواصفات كما أدناه؛ لا صلاحيات جديدة ولا تفعيل تلقائي لترقية قاعدة المشروع.

تضاف `specifications` إلى Create/Update/PropertyResponse، دون تغيير أسماء الحقول القديمة أو مساراتAPI أو صلاحياتها. جميع الإضافات اختيارية، بحدود وانطباق [P03](p03-property-specifications-draft.md). [قاموس الحقول الـ37 وأسمائها وأنواعها](p04-property-specifications-proposal.md#3-قاموس-الحقول-والتمثيل-المقترح) هو المرجع التفصيلي.

- غياب القسم من الإنشاء يعني مجهولًا؛ غيابه من التعديل يحفظ كل مواصفاته السابقة. `{}` بلا أثر. `specifications: null` يرفض400 بدل مسح جماعي.
- داخل القسم: الغائب محفوظ، وnull صريح يمسح الحقل الفردي. null ليسfalse ولا0. كل مفتاح غير معروف أو مكرر داخل القسم يرفض400؛ لا تغيير لسياسة JSON العامة للطلبات القديمة.
- المساحات الأربع نصوصASCII عشرية plain أوnull في الطلب والاستجابة، precision12/scale2، من0.01 إلى9999999999.99. لا أرقامJSON أو أس أو فواصل تجميع للحقول الجديدة. تبقى أرقام JSON والنصوص القديمة الصحيحة في الحقول القديمة مقبولة كما كانت.
- العدادات JSON integers فقط ضمن مجالاتها؛ `"3"` و`3.0` و`3e0` لا تقص أو تحول. التجهيزات JSON boolean/null فقط؛ enums أسماء حساسة للحالة لاordinal. العربية/الفارسية تحولها واجهةP05 قبل الإرسال، لا تخمين داخلAPI الجديد.
- استجابةProperty دائمًا تتضمن كائنspecifications بالمفاتيح الـ37 وnull للمجهول/غير المنطبق، بما فيها السجلات القديمة. لا backfill ولا كتابة من مجردGET. لا إضافات إلى DTO نتيجةR3 أو طلبR1 ولا مرشحات جديدة.
- مصدر المساحة الرئيسية null يعني معلنة غير مصنفة في السجل المحفوظ. المصدر المحدد LAND/UNIT_NET/UNIT_GROSS/TOTAL_BUILT يجب أن توجد مساحته وتطابقarea عددياً؛ `500` يطابق`500.00`. تعديل قديم متعارض يرفض400 دون فك ربط تلقائي. المسح أو تغيير المصدر صريح.
- العمر وسنة التقدير يقدمان/يمسحان معًا؛ لا سنة بناء مشتقة أو زيادة عمر تلقائية. سنة التقدير لا تتجاوز السنة الحالية فيAsia/Riyadh. لا استنتاج تأثيث من مطبخ أوخصوصية مسبح أو حالةNEW من عمر0.
- الانطباق والاتساق يراجعان على النتيجة النهائية بعد الدمج؛ false/0 غير المنطبق يرفض أيضًا. تغيير النوع أو نطاق التجاري يحتاج مسح غير المنطبق صراحة، لا تحويل أو حذف ضمني. لا شرط بناء≤أرض؛ صافي الوحدة≤إجماليها، والأجزاء لا تتجاوز إجمالي وحدات معلوم.
- تعديلات العقار نفسه تقرأ تحت قفل صف حتى نهاية المعاملة لحماية دمج المواصفات من كتّاب متزامنين. لا قفل إضافي للقراءات العامة، ولا version أوETag جديد؛ دلالة PUT الكاملة للحقول القديمة لم تتغير.

مثال جزء من طلب إنشاء شقة (تضاف إليه بقية الحقول المطلوبة):

```json
{
  "area": "150.25",
  "specifications": {
    "primaryAreaSource": "UNIT_NET",
    "unitNetArea": "150.25",
    "unitGrossArea": "180.00",
    "bedrooms": 3,
    "floorNumber": 0,
    "hasElevator": true,
    "parkingSpaces": 0
  }
}
```

لتغيير المصعد وحده ضمن PUT الكامل: `"specifications":{"hasElevator":false}`؛ ولجعله مجهولًا: `"specifications":{"hasElevator":null}`. لا تتغير بقية المواصفات. أخطاء اتساق/مجال المواصفات في خريطة `message` بمفاتيح مثل`specifications.primaryAreaSource`؛ أخطاء الشكل والأنواع400 بصيغة الطلب غير صالحة. جميعها قبل الحفظ؛ تحقق القيم والشكل قبلPropertyRepository، والقواعد المعتمدة على حالة محفوظة بعد القراءة المقفلة وقبل أي تعديل للكيان.

## الاستجابة والمرشحات

الاستجابة تعيد listingType,rentalPeriod وجميع حقول الموقع السابقة. بيانات الناشر أصبحت publisher وpublisherId وpublisherName بدل seller؛ publisher يحتوي id,name,role. هذا تغيير مقصود لعقد الاستجابة؛ جميع مستهلكي العقد يجب تحديثهم، والواجهة الحالية محدثة.

القائمة العامة تدعم listingType وrentalPeriod إضافة إلى city,district,type,minPrice,maxPrice,page,size,sort. size من 1 إلى 100. minPrice/maxPrice يرشحان القيمة المسجلة، لذلك يفضل تحديد فترة الإيجار عند مقارنة أسعار الإيجار.

### P08 — مرشح مكة وثبات الصفحات

اعتمد المستخدم في 20 أكتوبر 2026 توسيع `city` لأسماء مكة المحددة فقط: «مكة»، «مكة المكرمة»، و«Makkah». طلب أي منها يجمع السجلات المسماة بهذه الصيغ مع تجاهل حالة الأحرف والمسافات الزائدة، قبل العد والصفحات، دون إعادة كتابة البيانات. لا تخمين «Mecca/مكه» ولا تغيير لمطابقة المدن الأخرى. غياب city في API المباشر ما زال يعني عدم ترشيح المدينة؛ الواجهة تضيف نطاق مكة.

عند تعادل حقل الترتيب الأساسي يضاف `id,desc`؛ طلب الترتيب بالمعرّف صراحة يحتفظ باتجاهه. هذا لا يغير شكل الاستجابة ولا يمنح snapshot ثابتًا عبر تغير المخزون. القائمة تبقى ACTIVE فقط.

واجهة `/properties` تعرض الحي والنوع والسعر والعرض والفترة، وتحفظ البحث والصفحة في URL، بحجم 12 والأحدث أولًا. لا تطبق نطاق سعر إلا للبيع أو للإيجار مع فترة صريحة، وتطلب مراجعة المبالغ عند تبديل الوحدة. هذا حاجز واجهة لتجنب المقارنة المضللة، **وليس تشديدًا لقبول الطلبات القديمة على API**؛ التحقق العددي الأصلي في API لم يتغير. [التنفيذ وحدود الواجهة ونتائج 502/193 والمتصفح](p08-catalog-filters-verification.md).

## عقد الأرقام العشرية — T01 وT02

اعتمد تغيير نوع الحقول الخمسة `price`, `area`, `streetWidth`, `latitude`, `longitude` في **استجابات العقارات** من أرقام JSON إلى نصوص عشرية plain، دون صيغة أسية. يشمل ذلك الإنشاء والتعديل والتفاصيل والقائمة العامة وقائمة الأدمن. `null` يبقى `null`، والمعرّفات وأرقام الصفحات والعدادات لا تتغير. أي مستهلك خارجي يتوقع `number` لهذه الحقول يحتاج تحديثًا؛ جميع المستهلكين داخل واجهة المشروع يستخدمون القيم الدقيقة مباشرة.

| الحقل | precision / scale في JPA | المجال المسموح | null |
|---|---|---|---|
| `price` | 19 / 2 | `0.01` إلى `99999999999999999.99` | لا |
| `area` | 12 / 2 | `0.01` إلى `9999999999.99` | لا |
| `streetWidth` | 10 / 2 | `0.01` إلى `99999999.99` | نعم |
| `latitude` | 10 / 7 | `-90` إلى `90` شاملًا | نعم |
| `longitude` | 10 / 7 | `-180` إلى `180` شاملًا | نعم |

Create وUpdate يطبقان القواعد نفسها قبل الحفظ. لا يتم قص الكسور أو تقريبها: الكسور الأكثر من scale المحدد، أو تجاوز المجال/الخانات، أو الصيغ غير القابلة للتحليل تعيد `400`. حتى الكسور الزائدة التي تنتهي بأصفار ترفض بدل تعديلها بصمت. الإحداثيات السالبة والصفرية صحيحة ضمن المجال. تبقى الحقول الاختيارية اختيارية، وPUT يبقى استبدالًا كاملًا وليس PATCH.

الطلب الموصى به يرسل نصوصًا عشرية (كما في المثال أعلاه)، خصوصًا عندما تتجاوز القيمة دقة JavaScript. تستمر أرقام JSON القديمة الصحيحة والنصوص العددية التي يقبلها BigDecimal ضمن الحدود في العمل، بما فيها الصيغ الأسية المنضبطة. التمثيلات الأسية الضخمة ترفض قبل الحفظ، مع حساب آمن للخانات دون overflow. لا يمكن استعادة دقة فقدها عميل سبق أن حوّل القيمة إلى `Number` قبل إرسالها.

مثال جزء من استجابة عقار:

```json
{
  "price": "9007199254740993.01",
  "area": "150.25",
  "streetWidth": null,
  "latitude": "-21.4225000",
  "longitude": "39.8262000"
}
```

الأصفار النهائية قد تختلف بين استجابة الحفظ وإعادة القراءة حسب scale الذي تعيده JPA؛ القيمة العددية نفسها لا تتغير. لا يوجد ضمان بالحفاظ على التهجئة الأصلية (`150` مقابل `150.00`)، وإنما الحفاظ على القيمة دون تقريب.

نموذج الأدمن يحتفظ بالقيم كنصوص، ويحوّل الأرقام العربية `٠١٢٣٤٥٦٧٨٩` والفارسية `۰۱۲۳۴۵۶۷۸۹` والفاصل العشري العربي `٫` إلى تمثيل ASCII قبل الإرسال. لا يقبل فواصل التجميع أو الصيغ الأسية في الإدخال المرئي، لتجنب التخمين؛ تظهر رسالة تحقق بدل القص أو التقريب. العرض يستخدم تنسيقًا نصيًا دقيقًا داخل RTL، دون المرور عبر `Number` أو تحويل null إلى صفر. لا تتغير عقود R1/R3 العشرية الحالية.

هذا التغيير لا يضيف أعمدة أو migration، ولا يغير المصادقة أو ADMIN أو CSRF أو قواعد النشر. تحقق الواجهة لتحسين تجربة المستخدم؛ تحقق الباكند هو الحاجز الإلزامي قبل الكتابة، وقيود قاعدة البيانات تبقى خط الدفاع الأخير وليست آلية التقريب المقبولة.

## ترقية PostgreSQL

إصدارP04 يحتاج [الترقية الإضافية](../backend/db/20261018-property-specifications.sql) بعد المخطط السابق وقبل تشغيل الكود الجديد على قاعدة فعلية. لا توجد ترقية تلقائية: لم يطبق هذا الملف على`db_rushd`. تشغيل كودP04 على المخطط القديم دون الترقية سيؤدي إلى أخطاء أعمدة مفقودة؛ لا تعتمد عليه لتعديل قاعدة البيانات بنفسه. تؤخذ نسخة احتياطية وتراجع الترقية وتطبق فقط باعتماد تشغيل منفصل. ترفض الترقية التكرار والمخطط الجزئي قبلDDL، وتترك البيانات القديمة دون إعادة تفسير. [تقرير الاختبارات والترقية المعزولة](p04-property-specifications-verification.md).

للتهيئة الأولى لقاعدة فارغة فقط، استخدم [baseline الصريح](../backend/db/20261013-empty-database-baseline.sql) بعد المراجعة والنسخة الاحتياطية. يرفض وجود جداول التطبيق مسبقًا ولا يضيف بيانات أو حسابات. تفاصيل التهيئة المحلية والتحقق في [دليل التطوير المحلي](local-development-setup.md).

إعداد JPA هو ddl-auto: none؛ لا تتم ترقية القاعدة تلقائيًا. قبل تشغيل الإصدار على قاعدة قديمة، راجع وخذ نسخة احتياطية ثم طبّق [ملف SQL](../backend/db/20261006-admin-sale-rent.sql) عبر أداة PostgreSQL المعتمدة. الملف يفترض وجود جدول properties ومخطط الإصدار السابق؛ ليس إنشاءً لقاعدة فارغة.

الترقية تضيف أعمدة الموقع ونوع العرض وفترة الإيجار، وتعتبر السجلات القديمة للبيع، وتضيف تحققًا وفهرسًا. لا تغير seller_id ولا الحسابات القديمة. لم يُطبق الملف تلقائيًا على قاعدة فعلية.

حساب أدمن موجود أو تهيئة إدارية موثوقة مطلوب للإدارة؛ التسجيل العام لا ينشئ أدمن.
