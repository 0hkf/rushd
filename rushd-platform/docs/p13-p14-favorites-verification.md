# P13/P14 — المفضلة الشخصية: التنفيذ وشرح الأكواد والتحقق

التاريخ: 21 أكتوبر 2026. النتيجة: اكتملت P13 وP14 ضمن العقد المعتمد والاختبار المعزول. **لا SQL أو تفعيل على قاعدة المشروع، ولا commit/merge/push أو dependency أو مفتاح جديد.** المفضلة معطلة افتراضيًا، وليست جاهزية إطلاق إنتاج شامل.

## 1. الفحص والاعتماد

الفرع `feature/property-google-location`؛ dirty tree سابق كبير محفوظ، لا ينسب كله لهذه الحزمة. لم توجد AGENTS.md محلية. فُحصت المتطلبات والخطة وProperty/Mapper/Service والقراءة العامة، وUserRepository وSecurityConfig وCSRF وعميل Axios وAuthProvider وصفحات التصفح والتفاصيل والمطابقة والصور والتنقل والدخول، والاختبارات وDDL والـrunner المعزول.

لم يكن تنفيذ مفضلة سابقًا. اعتمد المستخدم [العقد](p13-p14-favorites-proposal.md) وجدولًا واحدًا، وأزرارًا وصفحة شخصية، وACTIVE/SOLD، وإبقاء خانة دون بيانات للعقار المخفي مع الإزالة. الحذف الفعلي المستقبلي يزيل العلاقة فقط. الاعتماد لا يشمل قاعدة المشروع الفعلية.

## 2. النتيجة الوظيفية

- حفظ وإزالة من القائمة والتفاصيل ونتائج المطابقة للمسجل؛ الزائر يحصل على دعوة دخول وعودة محلية آمنة، دون حفظ تلقائي بمجرد تسجيل الدخول.
- صفحة `/favorites` بحجم12 وترتيب الأحدث حفظًا، مع صفحات وحالات تحميل وفشل وفراغ وإعادة محاولة. إزالة آخر عنصر من صفحة تنقل إلى صفحة صالحة.
- العقار المخفي يحتفظ بمكانه وعدده دون بيانات، ويمكن إزالته. SOLD يظهر بوسمه، ولا تعني المفضلة توافرًا للبيع أو ضمان ملاءمة.
- قوائم المفضلة في القاعدة؛ حالة الأزرار مؤقتة في ذاكرة جلسة الواجهة وتمسح عند تغير الحساب/الخروج. لا localStorage/sessionStorage ولا JWT في JavaScript.
- لا تغيير في ترتيب R3 أو احتياجات المستخدم، أو الثيم/الخط، أو المصادقة وADMIN وقواعد النشر أو CSRF.

## 3. شرح Java ملفًا ملفًا

### `favorites/Favorite.java` و`FavoriteId.java`

`@Entity` يعرّف صف علاقة في `property_favorites`، وليس عقارًا جديدًا. `@IdClass` يجعل `(userId, propertyId)` هوية مركبة: المستخدم لا يحفظ العقار مرتين. `createdAt` من نوع Instant لتسجيل الوقت UTC، دون عنوان أو سعر قديمين في الصف.

علاقتا JPA بالـUser/Property للقراءة وFK، ولا نضيف قائمة مفضلة داخل الكيانين القديمين أو cascade Java يزيلهما. `ON DELETE CASCADE` في SQL/@OnDelete يزيل علاقات المفضلة عندما يحذف الأب فعليًا؛ لا يحذف عقارًا أو حسابًا عند إزالة favorite.

### `favorites/Favorites.java`

Repository مبني على JpaRepository. كل query تشمل userId المستخرج من الجلسة:

- `pageFor`: صفحة علاقات مع fetch للـProperty مرة واحدة، وcount مستقل؛ لا query لكل بطاقة.
- `savedIds`: membership للدفعة المطلوبة فقط؛ لا تحميل جميع مفضلة الحساب إلى الواجهة.
- `removeFor`: حذف علاقة المالك ومعرف العقار فقط، دون فحص يكشف مفضلة شخص آخر. الغياب أيضًا نجاح.

### `favorites/FavoriteService.java`

الخدمة هي قواعد العمل:

1. `requireEnabled` يرفض503 قبل الوصول إلى repositories عندما الميزة معطلة.
2. المستخدم من email المصدق في Authentication، لا userId من المتصفح. كل الأدوار المسجلة تحصل على مفضلتها الشخصية فقط.
3. `add` يقفل صف المستخدم، ثم العقار ويفحص ACTIVE/SOLD. بعدها يفحص وجود العلاقة ويحفظ إن لم توجد. تكرار PUT لا يغير وقت الإضافة. قفل المستخدم يسلسل الكتابات المتزامنة لنفس حسابه، والمفتاح الفريد دفاع إضافي.
4. `remove` يستخدم قفل المستخدم نفسه، ويحذف العلاقة دون اشتراط بقاء العقار عامًا. لهذا يمكن إزالة العقار المخفي.
5. `list` يستخدم read-only REPEATABLE_READ لقراءة snapshot متسقة. لا يصنع summary للمخفي أصلًا، ولا يطلب صورته. lookup الصور الرئيسي bulk مرة للصفحة العامة فقط.
6. `status` يتحقق من1–100 معرف ومن مجال Long وصيغة عشرية موجبة، ثم يعيد معرفات المحفوظ في الدفعة لهذا المستخدم فقط.

`@Transactional` يحدد حدود العملية والالتزام/التراجع. لا نعالج التكرار باستثناء قاعدة ينتهي500، ولا نستعمل toggle غير محدد في الباكند؛ PUT يعني «احفظ» وDELETE يعني «أزل»، فتكون إعادة نفس العملية آمنة عند ضياع الرد.

### `favorites/FavoriteResponse.java`

Java records لعقد استجابة محدد. العنصر يحمل propertyId نصيًا ووقت الإضافة وavailable وsummary أوnull. summary يختار حقول البطاقة فقط؛ لا يسرّب بيانات ناشر أو مستخدم. السعر والمساحة BigDecimal وتستخدمان PlainDecimalStringSerializer الموجود، فتخرجان كنصين دقيقين. لم نغير JSON العام أو عقود PropertyResponse/المطابقة القائمة.

### `favorites/FavoriteController.java` و`FavoriteFailure.java`

Controller يربط HTTP بالخدمة، ويستخدم Authentication.getName، ويضع no-store للردود. لا يستقبل userId. PUT/DELETE يعيدان204. FavoriteFailure يحمل status ورسالة معالجين ضمن ErrorResponse القائم في GlobalExceptionHandler، دون stack trace أو تفاصيل SQL للعميل.

أضيفت `findByEmailForUpdate` فقط إلى UserRepository؛ لا تغيير في تسجيل الدخول أو إنشاء الحساب. SecurityConfig لم يعدل في هذه الحزمة: المسارات الجديدة تقع تحت anyRequest.authenticated القائم، والكتابة تحت CSRF القائم.

## 4. شرح الواجهة

- `services/favorites.js`: تحقق IDs وعقد القائمة والدفعة، ومخزن membership وطلبات الصفحة. ID القديم الآمن رقميًا يقبل كمدخل من مستهلك عقار قائم؛ ردود المفضلة الجديدة تتطلب نصوصًا، ولا تحول رقم Long فقد دقته.
- `createFavoritesStore`: يحتفظ بحالة كل زر، ويرسل GET دفعة واحدة للمجموعة. لا تغيير متفائل: `saved` لا يتغير قبل204. الضغط المتكرر أثناء الطلب لا يرسل طفرة ثانية.
- عند رد غامض بعد PUT/DELETE، يحتفظ بـtarget للعملية؛ إعادة المحاولة تكرر PUT أوDELETE نفسها، ولا تعكس الحالة المحلية. زر مستقل للتحقق يقرأ الحالة الحالية من الخادم.
- لكل طلب generation/ticket وAbortController. `dispose` يمسح حالة الحساب ويلغي طلباته، والاستجابة المتأخرة لا تعيدها حتى لو تجاهل العميل abort. خطأ القائمة لا يتحول إلى «مفضلتك فارغة» ولا يعرض قائمة سابقة كأنها حديثة.
- `FavoritesContext.jsx`: مخزن جديد لكل هوية حساب/دور وحالة استعادة الجلسة، مع useSyncExternalStore. فصلت تعريف السياق والـhooks إلى `favoritesState.js` لتبقى Fast Refresh سليمة؛ `useFavoriteBatch` يربط مجموعات البطاقات بطلب الحالة الواحد، لا GET لكل زر.
- `FavoriteButton.jsx`: دعوة دخول للزائر، ثم حفظ/إزالة/انتظار/خطأ وتحقق للمسجل. aria-pressed يبين الحالة المعروفة، ولا زر حفظ للعقار الخاص داخل الإدارة.
- `pages/Favorites.jsx`: صفحة خاصة، بطاقات عامة أو placeholder مخفي، صفحات وتصحيح الصفحة بعد حذف آخر عنصر. metadata الصفحة لا تحفظ في مخزن membership أو browser storage.
- `loginDestination.js`: قائمة مسارات محلية صريحة أضيفت لها `/favorites` و`/properties/{positiveLong}`، دون query/fragment أو بروتوكول خارجي أو traversal. العودة لا تنفذ حفظًا تلقائيًا.
- App/Navbar/Login/Properties/PropertyDetails/PropertyNeeds تربط المسار والأزرار والعودة. Home حدّثت عبارتها التي كانت تصف المفضلة بأنها غير منفذة. `Favorites.css` تنسيق محدود يستخدم ألوان وخط ومتغيرات الموقع نفسها.

## 5. العقد وقاعدة البيانات والحماية

[API كامل بالأمثلة والأخطاء والتفعيل](api-favorites.md). المسارات: GET القائمة وGET status، ثم PUT/DELETE معرف عقار ضمن `/api/me/favorites`.

ملف `backend/db/20261021-property-favorites.sql` مراجع ولا يعمل تلقائيًا. جدول واحد بثلاثة أعمدة، PK مركب، FK للمستخدم والعقار مع CASCADE، وفهرس صفحات. لا تعديل rows أو أعمدة في الكيانات الحالية، ولا تغيير نوع السعر أو قواعد المطابقة.

تحقق الواجهة للتجربة ويمكن تجاوزه. الباكند يعيد التحقق ويستخرج الملكية من الجلسة ويطبق الإتاحة والتزامن؛ DB تفرض uniqueness والربط والوقت غير الفارغ. CSRF وHttpOnly cookies وتجديد الجلسة كما هي. لا الأسرار أو البطاقات الشخصية في localStorage، ولا endpoint لصلاحية إدارية على مفضلة الآخرين.

### المتصفح الفعلي

بيئة مؤقتة على 127.0.0.1:5176/18086 مع PostgreSQL بـtmpfs، حسابين BUYER صناعيين وحساب ADMIN صناعي و13 عقارًا صناعيًا. لا بيانات/قاعدة حقيقية أو صور مستخدم؛ الصور معطلة فظهرت placeholders. تحقق صور P10/P11 السابق والاختبارات الكاملة ما زال قائمًا؛ لم يُرفع مصدر صور في تجربة P14.

- أخفى ADMIN عقارًا عبر API العادي في البيئة المؤقتة وغيّر عنوانه إلى علامة خاصة. بعد reload ظهرت خانة غير متاحة بلا عنوان أو سعر أو صورة أو رابط؛ أزيلت من الواجهة بنجاح.

## 8. التجربة اليدوية والقيود

في بيئة اختبار مفعلة ومعتمدة فقط: سجل كـBUYER، احفظ من بطاقة ثم افتح «مفضلتي»، جرب التفاصيل والإزالة وإعادة الدخول. جرّب حسابًا ثانيًا، ثم إخفاء عقار بحسابADMIN وإعادة قراءة المفضلة. لا يفترض أن يبقى محتواه مرئيًا. عند انقطاع رد كتابة أعد العملية نفسها أو تحقق؛ لا نجاح وهميًا محليًا.

المفضلة افتراضيًاfalse حتى اعتماد الترقية والتفعيل منفصلًا؛ ظهور503 في بيئتك غير المفعلة متوقع. لم تُعد تشغيل خدمات المستخدم لعرض التغيير. إدارة الصور إعداد مستقل، ولا يلزم تفعيلها للمفضلة.

الصفحات offset وليست snapshot ممتدة عبر عدة زيارات؛ التغييرات المتزامنة بين الصفحات قد تغير العناصر، وإعادة القراءة تجلب الحالي. ليست هناك مزامنة مباشرة بين تبويبات مختلفة أو polling؛ لا ندعي إخفاء بكسلات سبق تنزيلها فورًا. توجد إعادة قراءة وحالة مرجعية من الخادم.

لم تختبر ترقية أو نشر القاعدة الفعلية، أو ضغط إنتاج طويل أو جميع المتصفحات أو screen reader فعليًا. قفل المستخدم يسلسل كتاباته، وقفل العقار يحمي فحص إتاحته وقد يحد معدل الكتابة على العقار الشعبي؛ قياس الحمل وrate limiting أوسع عند الحاجة ضمن بوابة التشغيل P30/P31. ليس نجاح الاختبارات ضمانًا شاملًا أو تصريح نشر.

التالي P15 للمقارنة وP16 لاعتماد قواعد تقييم العقار المختار، وكلاهما يحتاج قراراته قبل التنفيذ. المتبقي17 حزمة P15–P31، لا17 يومًا.
