# P06 وP07 — مقترح التنفيذ وبوابات الاعتماد

التاريخ: 19 أكتوبر 2026. الحالة: **اعتمد المستخدم المقترح وعقده التفصيلي لـP06، وإعداد P07 العام وACTIVE فقط، ثم نُفذا**. أبقي اسم الملف وروح المقترح كسجل القرار؛ نتائج التنفيذ في [P06](p06-type-matching-verification.md) و[P07](p07-administration-contact-verification.md). طلب المستخدم إنجاز تاسكين مع أولوية الدقة، وفق [الخطة](execution-prompts.md).

## الفحص المختصر

- R1/R3 الحاليان يدعمان الحي ومدى المساحة المعلنة، مع وزن واحد لكل تفضيل وترتيب الأحدث ثم المعرف عند التعادل. `PropertyNeedsRequest` يرفض المفاتيح غير المعروفة، ولذلك تحتاج إضافة المعايير عقدًا صريحًا قبل التنفيذ.
- `PropertyMatchingSpecification` يرشح الشروط الأساسية والمساحة الإلزامية قبل حد 1000 مرشح؛ لا يصح ترتيب عينة أو تحميل كل المخزون عند إضافة معايير.
- الواجهة الحالية تتوقع حتى تفضيلين، ونسخة احتياجات الصفحات نسخة سطحية. إضافة كائنات متداخلة تستلزم تحديث عدد المعايير ونسخة عميقة مستقلة وإلغاء الطلبات عند تغييرها.
- مواصفات P04/P05 موجودة، ولا نضيف حقول تخزين لتكرارها. العمر تقدير مؤرخ، وليس عمرًا حاليًا محسوبًا.
- لا اتصال أو واتساب أو أرقام إدارة عامة مهيأة في الكود. بيانات حساب الناشر ليست مصدرًا بديلًا للأرقام.
- الفرع `feature/property-google-location` وشجرة Git تحتوي عملًا سابقًا محفوظًا. لا إعادة تشغيل أو SQL أو فحص مخزون على قاعدة المشروع الفعلية.

## P06 — المقترح الدلالي المطلوب اعتماده

1. نضيف المعايير المنظمة المنطبقة: الغرف والحمامات والصالات والأدوار والوحدات والمواقف والآبار؛ الحالة والتشطيب والتأثيث والتصنيف التجاري ومصدر الماء؛ والتجهيزات والخدمات. تؤجل مطابقة العمر المؤرخ والوصف الحر، فلا نشتق عمرًا حاليًا أو نوعًا من النص.
2. يختار المستخدم معنى واحدًا لمدى المساحة: المعلنة الحالية، الأرض، صافي الوحدة، إجمالي الوحدة، أو إجمالي البناء عند انطباقه. لا رجوع من مساحة مسماة مفقودة إلى `area`، ولا تحويل أو تخمين. القديم دون اختيار جديد يبقى على المساحة المعلنة.
3. كل معيار جديد اختياري، لكن عند إضافته يحدد المستخدم `REQUIRED` أو`PREFERRED` صراحة. العداد مدى شامل بحد واحد أو حدين، والمجال من P03؛ boolean قيمة مطلوبة true أوfalse، والقائمة اختيار واحد بمساواة صريحة، دون ترتيب جودة ضمني.
4. المخالف أو المجهول في الإلزامي يستبعد. في التفضيل يبقى مع توضيح MATCHED/MISMATCHED/UNKNOWN ولا نقطة للمجهول. كل معيار تفضيل له وزن واحد، مساويًا للحي والمساحة؛ المدى معيار واحد لا نقطتان، ولا نقاط لشيء لم يطلبه المستخدم. الأحدث ثم المعرف يحسمان التعادل، بلا درجة من 100 أو تقييم سوقي.
5. نطاق التجاري اختياري، لكنه إذا اختير يصبح شرط نطاق ثابتًا لا تفضيلًا موزونًا؛ يلزم بيانه عند طلب مساحة/دور/وحدات تعتمد عليه. لا مقارنة مساحة وحدة بمبنى كامل ولا غرف نوم للتجاري.
6. يبقى ACTIVE ومكة ونفس النوع والعرض والفترة والميزانية الإلزامية والمستخدم المسجل وCSRF، دون تخفيف تلقائي. لا فهارس أو schema أو بيانات ترحيل جديدة ضمن المقترح.

## P06 — أثر API المقترح

تظل مسارات `/api/property-needs/validate` و`/matches` الحالية. تضاف مفاتيح اختيارية:

- `areaBasis`: أحد ADVERTISED/LAND/UNIT_NET/UNIT_GROSS/TOTAL_BUILT؛ الغائب أوnull يحفظ معنى ADVERTISED القديم. المعنى المسمى دون مدى مساحة يرفض400 بدل طلب ملتبس.
- `commercialScope`: UNIT/WHOLE_BUILDING أوnull، للتجاري فقط؛ يفحص مع انطباق المعايير.
- `specificationCriteria`: كائن اختياري بمفاتيح معلومة فقط. الغائب أو`{}` يعني عدم طلب معايير جديدة؛ null للقسم كله أو معيار بلا قيمة/حد أو بلا أهمية يرفض400. المفاتيح والأنواع غير الصالحة أو المكررة ترفض موضعيًا، دون تغيير إعداد JSON العام.

مثال جزء جديد من طلب شقة؛ تضاف إليه الحقول القديمة المطلوبة:

```json
{
  "areaBasis": "UNIT_NET",
  "minArea": "120.00",
  "maxArea": "180.50",
  "areaRequirement": "REQUIRED",
  "specificationCriteria": {
    "bedrooms": { "min": 3, "max": 5, "requirement": "REQUIRED" },
    "hasElevator": { "value": true, "requirement": "PREFERRED" },
    "finishing": { "value": "FULL", "requirement": "PREFERRED" }
  }
}
```

المفاتيح الجديدة للمعايير 28 كحد أقصى قبل انطباق النوع: 10 عدادات و13 boolean و5 قوائم؛ النطاق الهيكلي خارج عدّ التفضيلات. الحي ومدى المساحة يضيفان معيارين محتملين، فيصبح السقف التقني 30، لا ثقلًا ثابتًا لكل طلب. جميع حدود العدادات من P03، والمساحات تظل نصوصًا دقيقة، ولا صيغ أسية أو تحويلات ضمنية للحقول الجديدة.

الاستجابة تحتفظ بالحقول القديمة، وتضيف ملخص الخيارات الجديدة وأدلة المعايير المطلوبة: اسم الحقل، المطلوب، الفعلي، الأهمية، والنتيجة. تبقى `area` مساحة الإعلان القديمة، وتضاف `matchedArea` للقيمة التي قورنت فعليًا وفق `areaBasis`، حتى لا يعرض العميل مساحة أخرى كدليل نجاح. عدم وجود قيمة يعرض null/UNKNOWN، لا صفرًا. الطلب القديم المتوافق يحتفظ بقواعد matching-v1؛ تميّز الطلبات ذات المعاني الجديدة بـmatching-v2. العملاء الخارجيون ذوو مخطط استجابة مغلق قد يحتاجون تحديثًا بسبب الحقول الإضافية؛ جميع مستهلكي المشروع سيحدثون واختباراتهم معًا.

تنقل الشروط الإلزامية المنطبقة إلى استعلام المرشحين قبل حد المعالجة، وتبقى التفضيلات مرتبة على المجموعة المحدودة كاملة قبل الصفحات. يبقى حد 1000 و422 المعلن، دون ادعاء أنه إجمالي المخزون أو نتيجة أفضل عينة. تختبر الاستعلامات على PostgreSQL المعزول، والقديم/المجهول/false/0/الحدود والتعادل والصفحات ونسخة الاحتياجات وإلغاء الطلبات والأرقام الدقيقة والصلاحيات.

## P07 — المقترح المطلوب اعتماده

- يزود المستخدم رقم الاتصال ورقم واتساب للإدارة بصيغة دولية، ويؤكد أنهما للنشر العام. لا رقم وهمي أو قراءة لحساب الناشر أو بيانات مستخدم آخر.
- مصدر الأرقام إعدادات واجهة عامة وقت البناء: `VITE_PUBLIC_CONTACT_PHONE` و`VITE_PUBLIC_WHATSAPP_PHONE`، بقيم فارغة افتراضيًا. الأرقام عامة وليست أسرارًا، وتغييرها يتطلب إعادة بناء/تشغيل الواجهة. لا صفحة إعدادات أو endpoint أو جدول جديد في هذه الدفعة.
- تظهر الإجراءات للعقار ACTIVE فقط؛ لا للمسودات أوغير المنشور أوSOLD. هذا لا يغير إتاحة تفاصيل SOLD العامة الحالية.
- الاتصال عبر tel لرقم دولي متحقق الصيغة، والواتساب عبر نطاق ثابت `https://wa.me/` ورقم من أرقام فقط ورسالة عربية مرمزة تحتوي معرف العقار ورابط تفاصيله العام فقط. يبنى الرابط من أصل الموقع ومسار معرف صالح، لا URL عشوائي من العقار أو API.
- لا إرسال آلي أو API مدفوع أو بيانات حساب/احتياجات في الرسالة. التحقق من الصيغة لا يثبت أن الخط يعمل أو أن الرقم مسجل في واتساب. غياب رقم صالح يخفي زره دون تعطيل الصفحة.
- تختبر الصيغ والبروتوكول والترميز وغياب الأرقام وحالة النشر وRTL والجوال. اختبار الرابط لا يتصل بالرقم أو يرسل رسالة فعلية.
