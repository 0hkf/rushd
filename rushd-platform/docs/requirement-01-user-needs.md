# R1 — احتياجات المستخدم العقارية

تاريخ البدء: 6 أكتوبر 2026.
الحالة: منفذ ومتحقق محليًا. اعتمد صاحب المشروع نموذج أسئلة واضحًا (`1A`) للمسجلين فقط (`2B`). يشمل الإنجاز واجهة الإدخال وعقد التحقق والملخص، لا محرك الترشيح.
المرجع: [المتطلبات](requirements.md) و[المرحلة الأولى](roadmap.md).

## الهدف

جمع احتياجات المستخدم بصورة يمكن التحقق منها قبل البحث والترشيح، لجميع أنواع العقارات الحالية وفي مكة أولًا. يفصل الطلب بين شروط ملزمة وتفضيلات مرنة، ولا يجمع اسمًا أو هاتفًا أو بيانات حساب لمجرد الترشيح.

هذا المتطلب ينفذ جمع المدخلات والتحقق منها وملخصًا مؤقتًا. بناء محرك الترتيب وتقييم السعر وربط AI أعمال لاحقة؛ لا يقدم R1 ترشيحات أو تقييمًا عقاريًا.

## نتيجة الفحص قبل تنفيذ R1

- بيانات العقار موجودة: النوع، بيع/إيجار، فترة الإيجار، المدينة، الحي، السعر، المساحة، الاستخدام، وواجهة وعرض شارع اختياريان.
- قائمة العقارات الحالية ترشح النوع والمدينة والحي ونوع العرض وفترة الإيجار وحدود السعر، وتعرض `ACTIVE` فقط.
- القائمة الحالية لا تدعم مرشحات المساحة أو الاستخدام أو الواجهة أو عرض الشارع، ولا شروطًا مرنة أو ترتيبًا بحسب الملاءمة.
- أنواع العقارات السبعة موجودة، لكن المواصفات التفصيلية للغرف والمصعد والدور والوحدات وغيرها غير مخزنة.
- لم يكن هناك نموذج احتياجات أو DTO أو API أو حفظ تفضيلات أو ترشيح شخصي. أضاف R1 الإدخال والتحقق فقط، لا حفظًا أو ترشيحًا.
- المدينة والحي نصوص؛ المطابقة الحالية لا توحد «مكة» و«مكة المكرمة». يلزم تحديد أسماء معيارية دون حذف أو تغيير السجلات القديمة تلقائيًا.

## المنفذ في R1

- صفحة `/property-needs` نموذج عربي RTL على الهوية الحالية، مع بوابة دخول للمسجلين فقط.
- الحقول المشتركة المدعومة: النوع، بيع/إيجار وفترته، الميزانية، حي اختياري، نطاق مساحة اختياري، وهدف بحث اختياري.
- تحديد أهمية الحي والمساحة كشرط أو تفضيل، دون حساب درجة أو وزن للملاءمة حتى الآن.
- `POST /api/property-needs/validate` محمي بالمصادقة وCSRF، ويعيد مدخلات متحققة مع `SAR/SQUARE_METRE` ومكة المكرمة كنطاق ثابت. التفاصيل في [عقد API](api-property-needs.md).
- القيم العشرية تبقى سلاسل دقيقة بين الواجهة والخادم؛ لا تقريب عبر `Number`، والحدود والدقة تطبق في الخادم أيضًا.
- النموذج والملخص في React memory فقط. تعديل المدخلات أو مسحها يزيل الملخص؛ تغير الحساب/الخروج يلغي الطلب المعلق ويمسح بيانات الصفحة.
- بعد الدخول يعاد المستخدم إلى النموذج عبر مسار محلي مسموح فقط. لا نموذج للزوار ولا حفظ أو استعلام عقارات أو ربط AI.

## المدخلات المشتركة

| المدخل | المطلوب في البداية | المعنى والتحقق |
|---|---|---|
| نوع العرض | مطلوب | `SALE` أو `RENT`؛ يختاره المستخدم صراحة |
| فترة الإيجار | مطلوبة للإيجار فقط | `MONTHLY` أو `YEARLY`؛ ترفض مع البيع، وتوضح وحدة الميزانية |
| نوع العقار | مطلوب | اختيار من الأنواع السبعة؛ اختيار عدة أنواع يحتاج عقدًا جديدًا ولا تدعمه القائمة الحالية |
| الحد الأعلى للميزانية | مطلوب | مبلغ موجب بالريال، إجمالي للبيع أو قيمة الفترة المختارة للإيجار؛ لا يتجاوز الترشيح هذا الحد |
| المدينة | مكة في النسخة الأولى | عرض واضح للمستخدم وتطبيق النطاق في الخادم؛ اختيار اسم معياري لا يعني تعديل المدن في العقارات القديمة |
| الحي | اختياري | يمكن اختيار «أي حي» أو حي، مع بيان هل الحي شرط ملزم أم تفضيل؛ تعدد الأحياء يحتاج توسعة الاستعلام |
| نطاق المساحة | اختياري | حدود موجبة بالمتر المربع، والأدنى لا يتجاوز الأعلى؛ توضح أنها المساحة المسجلة في الإعلان، لا مساحة صافية أو بناء موثقة تلقائيًا |
| الغرض من البحث | اختياري | مثل السكن أو الاستثمار؛ نميز نية المستخدم عن استخدام العقار `purpose`، ولا نساوي الاستثمار تلقائيًا بقيمة `INVESTMENT` في السجل |
| واجهة العقار وعرض الشارع | للمرحلة التالية | بياناتهما موجودة للعقار، لكن لا حقول لهما في نموذج R1 أو عقده؛ الطلب يرفضهما بدل الادعاء بدعمهما |

حدود طول النص والأرقام مفصلة في عقد API، وتطبق على الخادم والواجهة. لا تقص المدخلات بصمت أو تستخدم وصفًا حرًا كبديل لحقول موثقة.

## الشروط والتفضيلات

- نوع العرض والنوع والميزانية شروط واضحة في البداية؛ لا تحويل بيع إلى إيجار أو تعديلها للوصول إلى نتائج أكثر.
- في الإيجار تقارن نفس الفترة في النسخة الأولى؛ تحويل شهر/سنة ليس موجودًا حاليًا ولا يفترض ضمن هذا المتطلب.
- الحي والمساحة في النموذج لهما اختيار إلزامي/مرن؛ الافتراضي للحي تفضيل، وللمساحة شرط عند تحديدها. الأوزان والدرجات ليست معتمدة الآن.
- أي شرط إلزامي غير قابل للتحقق من بيانات العقار لا يعد متحققًا. يوضح النقص بدل وضع علامة تطابق.
- عند انعدام النتائج تعرض الحالة بوضوح، مع اقتراح تعديل احتياجات يوافق عليه المستخدم؛ لا توسع القيود تلقائيًا.
- أي استخراج للاحتياجات من نص أو محادثة يجب أن يعرض على المستخدم للتأكيد قبل الترشيح.

## تفاصيل الأنواع — تحتاج نمذجة واعتمادًا منفصلين

كل الأنواع مطلوبة؛ الجدول يحدد فجوات البيانات ولا يضيف حقولًا إلى قاعدة البيانات الآن.

| النوع | أمثلة مواصفات مقترحة | الملاحظة |
|---|---|---|
| أرض | الأبعاد، استخدام مسموح موثق، الخدمات | عرض الشارع والواجهة موجودان؛ لا استنتاج تراخيص أو خدمات من الوصف |
| شقة | غرف، حمامات، دور، مصعد، موقف | غير مخزنة حاليًا |
| فيلا | غرف، أدوار، عمر، مساحة أرض وبناء منفصلتان | غير مخزنة حاليًا؛ المساحة الحالية وحدها لا تميز الأرض والبناء |
| عمارة | أدوار، وحدات، نوع الوحدات، عمر | غير مخزنة؛ لا اختلاق دخل أو إشغال لتقييم الاستثمار |
| تجاري | نوع الاستخدام، الواجهة التجارية، الخدمات | لا يفترض أن كل تجاري محل، وتحتاج تفاصيل بحسب النوع |
| مزرعة | خدمات، مصدر ماء موثق، استخدام | غير مخزنة، ولا حكم زراعي أو قانوني دون مصدر |
| أخرى | المواصفات المشتركة وما يوثق لاحقًا | لا حكم تفصيلي من نوع غير محدد |

## الخصوصية والأمان

- الاحتياجات تستخدم للطلب الحالي فقط في البداية؛ لا حفظ دائم أو سجل نصوص أو ربط بملف المستخدم دون قرار وموافقة واضحة.
- طريقة الإدخال وإتاحة الميزة معتمدتان: نموذج أسئلة للمسجلين فقط. لم تتغير صلاحيات التصفح أو إدارة العقارات القديمة.
- يعاد استخدام العميل الحالي للمصادقة وCSRF والأخطاء؛ رموز المصادقة في cookies الحالية وليست في localStorage، ولا يفتح مسار غير محمي.
- أصلح حذف CSRF cookie عند كل إعادة بناء لمصادقة JWT. الطلبات العادية تحتفظ بالرمز؛ الدخول والتجديد والخروج ما زالت تمسحه صراحة. اختبار cookies حقيقي يثبت الإرسال المتكرر ورفض الرمز الغائب أو الخاطئ.
- لا ترسل المدخلات إلى مزود AI، ولا تحتاج R1 مفتاح API أو FastAPI أو تنزيل نموذج.
- الترشيح لاحقًا يأخذ `ACTIVE` فقط، لا قائمة إدارة العقارات. إتاحة تفاصيل `SOLD` للعامة لا تجعله مرشحًا متاحًا.
- لا يحسب ترتيب «الأفضل» من أول صفحة في القائمة؛ يلزم استعلام مرشحين محدود وموثق في الخادم قبل بناء الترتيب.

## معايير قبول الإدخال والتحقق في R1

1. كل نوع من الأنواع السبعة يمكن اختياره دون الحاجة إلى إنشاء دور بائع.
2. البيع لا يقبل فترة إيجار، والإيجار لا يقبل ميزانية دون فترة واضحة.
3. الميزانية غير الموجبة ونطاق المساحة المعكوس وقيم enum غير الصالحة تنتج خطأ واضحًا، ولا يستدعى الترشيح عند فشل التحقق.
4. الحدود الرقمية الصالحة تقبل دون فقدان الدقة؛ القيم الضخمة بصيغ أسية لا تتجاوز تحقق الخادم. لا تحويل شهري/سنوي أو بيع/إيجار.
5. عدم تحديد حي أو مساحة لا يتحول إلى شرط ضمني، ويظهر ما اختاره المستخدم قبل البحث.
6. الاستجابة ملخص فقط؛ لا نتائج أو تقييم ولا استدعاء لمستودع العقارات أو حفظ للمتطلبات.
7. النموذج عربي RTL ومناسب للجوال، وله labels ورسائل أخطاء واضحة.
8. الوصول يتطلب تسجيل الدخول في الخادم، وCSRF يطبق على POST؛ لا حماية بإخفاء النموذج فقط.
9. الاحتياجات لا تحفظ دائمًا؛ الخروج أو تغير الحساب يمسح الحالة ويلغي الطلبات، وتغيير المدخلات يزيل الملخص القديم.
10. المصادقة وCRUD والتصفح القديم تبقى تعمل، وإعادة التوجيه بعد الدخول لا تسمح بعنوان خارجي.

## معايير معلقة لمحرك الترشيح التالي، وليست منفذة في R1

- قبول الحدود في المقارنة وإخراج مرشحين من `ACTIVE` فقط، لا المسودات أو غير المنشور أو المباع حتى عند اختيار معرف مباشرة.
- العقار دون بيانات اختيارية لا يسبب خطأ ولا يصنف أنه يحقق متطلبًا مجهولًا.
- عدم وجود نتائج لا يسمح بإخراج عقارات تخالف شرطًا ملزمًا دون موافقة المستخدم.
- عدم خلط سعر/مساحة غير قابلة للمقارنة أو ربط الغرض بتقييم سوقي بلا أدلة.

## نتائج التحقق — 6 أكتوبر 2026

- `mvn clean test`: نجح 150 اختبارًا، بلا فشل أو أخطاء أو تخطٍّ؛ منها 58 حالة لعقد R1 و3 اختبارات تكامل CSRF بـcookies ورمز مقنع فعليين.
- `npm test`: نجح 18 اختبارًا. `npm run build` و`npm run lint` نجحا أيضًا.
- تجربة HTTP على باكند مؤقت بـH2: الزائر `401`، الطلب الصحيح والمتكرر `200`، نطاق معكوس وenum رقمي وعدد بأس ضخم `400`، ورمز CSRF الغائب/الخاطئ `403`، والخروج يلغي الدخول.
- تجربة متصفح بحساب اختباري: الدخول يعيد للنموذج، الأرقام العربية تعمل، بيع وإيجار شهري/سنوي يظهران بالوحدة الصحيحة، تغيير المدخلات يزيل الملخص، والتحويل للبيع يمسح فترة الإيجار، ومسح النموذج والخروج يعملان.
- التصميم فحص عند `1280×900` و`390×844` بلا تجاوز أفقي. أوقفت بيئة المعاينة المؤقتة بعد التحقق، ولم تستخدم قاعدة بيانات المشروع الفعلية.

الاختبارات وبيئة المعاينة تستخدم H2 داخل الذاكرة؛ لا تثبت جاهزية PostgreSQL أو النشر. لم تضف أعمدة أو ترقية قاعدة بيانات أو dependency أو مفتاح API، ولم ينفذ ترشيح أو AI.

## القرارات المعتمدة والمتابعة

1. `1A`: نموذج أسئلة واضح، لا محادثة.
2. `2B`: الميزة للمسجلين فقط، بما فيها الترشيح اللاحق؛ لا مسار ضيف.

الخطوة التالية تنفيذ مطابقة الاحتياجات مع العقارات المنشورة وفق قواعد واضحة، دون انتظار نموذج AI. توفر مراجع السوق والساعات اليومية ومواصفات الأنواع التفصيلية تبقى قرارات مفتوحة للمراحل التالية، ولا تختلق بيانات لإغلاقها.
