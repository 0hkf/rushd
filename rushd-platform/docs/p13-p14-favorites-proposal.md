# P13/P14 — مقترح المفضلة لاعتماد العقد قبل التنفيذ

التاريخ: 21 أكتوبر 2026. الحالة: **اعتمد المستخدم العقد والاختبار المعزول، وسياسة إبقاء خانة بلا بيانات للعقار المخفي مع إمكانية الإزالة. اكتمل التنفيذ ضمن هذا النطاق؛ لا تفعيل أو SQL على قاعدة المشروع الفعلية.** [النتائج وشرح الأكواد](p13-p14-favorites-verification.md) و[العقد المنفذ](api-favorites.md). بدائل هذه الوثيقة وعناوين القرار تسجل الاقتراح قبل الاعتماد ولا تغير القرار المعتمد.

## 1. نتيجة الفحص

- المشروع الحالي `/Users/azzam/Documents/rushd/rushd-platform` على `feature/property-google-location`، مع تعديلات سابقة كثيرة محفوظة. لم توجد AGENTS.md محلية في المشروع أو أسلافه.
- لا entity أو repository أو خدمة أو endpoint أو صفحة مفضلة حاليًا؛ الإشارة إليها في الرئيسية والمتطلبات ميزة مخططة فقط.
- التسجيل العام BUYER؛ هناك ADMIN وحسابات SELLER قديمة. المصادقة بالكوكيز HttpOnly، وCSRF للكتابة، وعميل Axios يدعم التجديد. لا تغيير في هذه القواعد.
- قائمة العقارات ACTIVE فقط، والتفاصيل العامة ACTIVE/SOLD. DRAFT/INACTIVE للأدمن؛ لا نجعل المفضلة طريقًا لرؤية بياناتها.
- توجد صورة رئيسية في استجابات العقار والمطابقة ومكونات عرض مشتركة من P11/P12؛ نعيد استعمالها.
- `spring.jpa.hibernate.ddl-auto=none` في إعداد التطبيق وcreate-drop للاختبارات؛ لا تشغيل SQL تلقائي. التفعيل على قاعدة المستخدم غير معتمد.
- رجوع تسجيل الدخول محصور حاليًا في dashboard/property-needs. تمديده لصفحة المفضلة أو تفاصيل عقار سيكون بقائمة مسارات محلية موثوقة، دون قبول رابط خارجي أو open redirect.

## 2. السياسة الموصى بها — قرار مطلوب

- المفضلة شخصية لأي حساب مسجل حالي: BUYER وADMIN وSELLER القديم. ليست صلاحية نشر أو لوحة للاطلاع على مفضلة الآخرين.
- تضاف عقارات ACTIVE أوSOLD فقط، اتساقًا مع التفاصيل العامة. المفضلة ليست حكم توافر للبيع، وSOLD يظهر بوسمه ولا يظهر تواصل ACTIVE له.
- إذا صار العقار DRAFT/INACTIVE: تبقى علاقة المستخدم به، وتظهر خانة «العقار غير متاح حاليًا» مع إزالة فقط. لا عنوان أو حي أو سعر أو صورة أو مواصفات أو رابط تفاصيل أو حالة النشر الخاصة.
- الخانة غير المتاحة تحتوي معرف العلاقة بالعقار ووقت إضافتها المعلومين للمستخدم من حفظه السابق، و`available=false` و`property=null`. لا تنشأ خانة لعقار خفي لم يحفظه المستخدم وهو عام.
- إذا عاد العقار إلى الحالة العامة تظهر بياناته الحالية في القراءة التالية؛ لا استعادة نسخة قديمة من عنوانه أو صورته.
- إن حُذف العقار أو الحساب حذفًا فعليًا مستقبلًا، تحذف علاقات المفضلة التابعة له بواسطة FK CASCADE فقط. لا حذف عقار أو حساب أو endpoint حذف جديد ضمن هذه الحزمة. إخفاء العقار لا يحذف العلاقة.
- الحفظ المكرر لا يكرر الصف أو يغير وقت الإضافة والترتيب. الإزالة المكررة ناجحة أيضًا. إزالة ثم إضافة عملية جديدة بوقت جديد.

البديل عند اختيار المستخدم سياسة أبسط: استبعاد العناصر غير العامة من القائمة والعدد مؤقتًا مع إبقاء العلاقة داخليًا؛ تعود عند إعادة النشر. هذا يخفي مكان إزالة العنصر المخفي، لذلك التوصية إبقاء خانة بلا بيانات.

## 3. schema المقترح — قرار مطلوب

جدول إضافي واحد `property_favorites`:

| العمود/القيد | التعريف |
|---|---|
| `user_id` | bigint مطلوب؛ FK إلى users(id)، ON DELETE CASCADE |
| `property_id` | bigint مطلوب؛ FK إلى properties(id)، ON DELETE CASCADE |
| `created_at` | timestamptz مطلوب؛ وقت UTC يولده الخادم |
| المفتاح | PRIMARY KEY(user_id, property_id) لمنع التكرار |
| فهرس الصفحات | user_id, created_at DESC, property_id DESC |

لا أعمدة إضافية في users أو properties، ولا نسخ سعر أو عنوان أو صورة إلى المفضلة. ملف ترقية مستقل مراجع يرفض غياب الجداول الأساسية أو إعادة/ترقية جزئية، ويختبر على PostgreSQL مؤقت فقط. لا تطبيق على قاعدة المشروع.

تسلسل المعاملات يحمي التزامن، مع القيد الفريد كدفاع إضافي. لن يُعالج تكرار الحفظ بخطأ 500. القراءات مجمعة حسب الصفحة، دون استعلام خصائص/صور لكل بطاقة على حدة.

## 4. API المقترح — قرار مطلوب

كل المسارات للمستخدم الحالي من جلسة الخادم. لا `userId` في العقد، ولا endpoint للأدمن يقرأ مفضلة مستخدم آخر. لا تغيير في عقود العقار والمطابقة القائمة.

| العملية | الطلب والنتيجة |
|---|---|
| قائمة المفضلة | GET `/api/me/favorites?page=0&size=12`؛ 200 بهيئة PageResponse الحالية، بترتيب وقت الإضافة تنازليًا ثم معرف العقار تنازليًا |
| حالة أزرار مجموعة بطاقات | GET `/api/me/favorites/status?propertyIds=15,16`؛ 200 `{ "favoritePropertyIds": ["15"] }`؛ ملكية المستخدم فقط، وليس استعلام إتاحة أو وجود عقار |
| إضافة | PUT `/api/me/favorites/{propertyId}` بلا body؛ 204 للجديد والموجود، دون تغيير وقت الإضافة في التكرار |
| إزالة | DELETE `/api/me/favorites/{propertyId}`؛ 204 للموجود والغائب، بما فيه العقار الذي أخفي أو لم يعد موجودًا |

- page عدد صحيح ≥0؛ size من 1 إلى100، الافتراضي12. ترتيب ثابت؛ لا sort حر جديد. حجم12 للواجهة.
- status يقبل 1–100 معرف Long موجب صالح، ويعالج التكرار دون طلب لكل بطاقة. لا تعاد معرفات مفضلة غير الموجودة في الدفعة المطلوبة.
- معرفات المفضلة الجديدة في الردود **نصوص عشرية** لتفادي فقدان دقة Long في JavaScript؛ لا تغيير عالمي أو تغيير نوع معرفات عقود موجودة.
- عنصر القائمة: `{propertyId:"15",createdAt:"2026-10-21T10:00:00Z",available:true,property:{...summary}}`.
- summary عامة محدودة للبطاقة: `id` كنص، title/type/listingType/rentalPeriod/city/district/price/area/status/primaryImage. السعر والمساحة نصوص عشرية دقيقة، ولا بريد أو هاتف أو بيانات ناشر. التفاصيل الكاملة تبقى في endpoint العقار الحالي.
- غير المتاح: نفس معرف العلاقة ووقت الإضافة، `available:false,property:null` فقط؛ لا cache لحقائق قديمة.
- PUT على عقار غائب/خاص يعيد404، بما فيه محاولة ADMIN حفظ DRAFT من شاشة الإدارة. القائمة/status لا يكشفان مفضلة حساب آخر.
- المدخل غير الصالح400؛ غير المسجل401 عند اجتياز CSRF؛ CSRF المفقود/الخاطئ403 حسب ترتيب الحماية الحالي. لا تعطيل CSRF للحصول على401 في طلب كتابة غير صالح أصلًا.
- الردود الشخصية `Cache-Control: no-store`. لا cookies أو tokens أو حقائق خاصة في رابط أو سجل جديد.
- إعداد محلي `rushd.favorites.enabled=false` افتراضيًا يحمي البيئة غير المُرقاة: بعد فحص المصادقة/CSRF يرجع503 دون استعلام الجدول عند التعطيل. الواجهة تعرض تعذرًا واضحًا؛ لا مفضلة وهمية أو fallback في localStorage. التفعيل مع اعتماد تشغيل منفصل.

## 5. الواجهة P14

- صفحة `/favorites` ورابط واضح في التنقل؛ للزائر دعوة دخول ثم عودة آمنة للمفضلة أو تفاصيل العقار، دون تنفيذ حفظ تلقائي بمجرد الدخول.
- زر حفظ/إزالة في بطاقات التصفح والتفاصيل ونتائج المطابقة. لا زر حفظ للعقارات الخاصة في لوحة الإدارة؛ المفضلة تخص التجربة العامة فقط.
- تحميل حالات الأزرار بدفعة محدودة لكل مجموعة نتائج، لا تنزيل المفضلة كاملة ولا استعلام منفصل لكل بطاقة.
- لا optimistic update في النسخة الأولى: تعطيل الزر أثناء الطلب وإظهار حالته، ولا إعلان نجاح قبل الرد. الخطأ يبقي الحالة السابقة ويتيح إعادة المحاولة أو التحقق من الخادم عند نتيجة غامضة.
- بعد إزالة آخر عنصر في صفحة تعاد مراجعة الصفحة المناسبة. تعديل المفضلة لا يعيد ترتيب قائمة المطابقة أو يغير احتياجات المستخدم.
- الحالة في ذاكرة الجلسة فقط، وتمسح عند الخروج أو تغير الحساب؛ الاستجابات المتأخرة لا تعيد حالة الحساب السابق. لا تخزين tokens أو قائمة المفضلة في localStorage/sessionStorage.
- إعادة استعمال تنسيق الأرقام والصور والهوية والخط وRTL؛ لا تغيير ثيم أو إعادة تصميم خارج الحاجة. إمكانية وصول للأزرار والرسائل والجوال.

## 6. التنفيذ والتحقق بعد الاعتماد

1. نموذج JPA/Repository وDTOs وخدمة وController للمستخدم الحالي، إضافة إلى ملف ترقية اختباري وإعداد التعطيل الآمن.
2. اختبارات نجاح وتكرار وإزالة وقيد FK والتزامن والصفحات والتعادل وملكية الحساب، و401/403/CSRF وحقن userId، وACTIVE/SOLD/DRAFT/INACTIVE والإخفاء ثم الإظهار، ودقة الأرقام والصور.
3. مكونات الواجهة ومخزنها ودفعات الحالة والصفحة والعودة الآمنة، واختبارات الضغط السريع والرد الضائع والفشل وتغير الحساب والطلبات المتأخرة.
4. `mvn clean test` على H2 مؤقت وPostgreSQL معزول بـvalidate وترقية مراجعة، ثم `npm test/build/lint`.
5. تجربة متصفح معزولة بحسابين صناعيين: حفظ وإزالة وإعادة دخول وعزل الحسابين وإخفاء العقار وعرض خانته وإزالة آخر عنصر والجوال، ثم تنظيف الموارد المملوكة فقط.
6. شرح عربي للأكواد، توثيق العقود والنتائج والقيود، وتحديث الخطة بعد الإنجاز الفعلي فقط.

لا مكتبات أو مفاتيح أو خدمات جديدة، ولا إشعارات أو مقارنة أو AI أو تعديل R1/R3 أو صلاحيات ADMIN أو المصادقة. لا تشغيل على قاعدة المشروع أو إعادة تشغيل خدمات المستخدم، ولا commit أو merge أو push.

## 7. حدود الاعتماد

الاعتماد المطلوب الآن هو سياسة العناصر غير العامة/المحذوفة، وإضافة الجدول والعقد والإعداد المعطل واختبارهما المعزول، ثم واجهتهما. لا يعني اعتماد SQL على القاعدة الفعلية أو نشرًا أو تفعيلًا أو تغيير بيانات المستخدم.

سجل مرحلة الاقتراح فقط: لم تُشغل اختبارات التطبيق أو تتغير ملفاته آنذاك، ولا تنسب أرقام P11/P12 لها. بعد اعتماد المستخدم نُفذ التطبيق واختبر؛ النتائج الفعلية في التقرير المرتبط أعلاه.
