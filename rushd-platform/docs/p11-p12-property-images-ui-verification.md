# P11 + P12 — إدارة صور الأدمن والعرض العام

التاريخ: 21 أكتوبر 2026. النتيجة: اكتملت الحزمتان برمجيًا واختباريًا ضمن بيئة معزولة. **لم تُفعّل الصور أو تُطبّق أي ترقية على قاعدة المشروع الفعلية.** لا commit أو merge أو push، ولا مكتبة جديدة أو مزود أو مفتاح.

## 1. الفحص والنطاق

الفرع `feature/property-google-location`، مع تعديلات سابقة كبيرة محفوظة لا تنسب كلها لهذه الحزمة. لم توجد تعليمات AGENTS.md محلية. روجعت خطة P11/P12، وعقد P09 وAPI P10، وخدمة الصور وصلاحياتها وCSRF، وعميل Axios، وفورم الأدمن وDashboard والتصفح والتفاصيل ونتائج المطابقة والاختبارات.

كان P10 يجهز الباكند فقط: endpoints للرفع والقائمة والترتيب والحذف ونسختي JPEG. لم تكن الواجهة تتيح إدارة هذه الصور أو تعرضها. الحل هنا يستهلك العقد القائم؛ **لا تعديل Java أو schema أو صلاحيات أو خوارزمية المطابقة في P11/P12**. تحديث حالة P10 في الخطة يصحح توثيقًا متأخرًا، ولا يعيد نسبة كوده إلى هذه الحزمة.

## 2. ماذا أصبح متاحًا؟

- يحفظ الأدمن مواصفات العقار أولًا، ثم يبقى محرره مفتوحًا ويظهر قسم صور مستقل. فشل الصور لا يعيد ضبط السعر أو المساحة أو الموقع أو بقية الفورم.
- اختيار عدة ملفات مع معاينات محلية صغيرة، ثم رفع ملف واحد في كل طلب. كل ملف له وصف اختياري ومصدر حق وإقرار نشر، ومرجع مطلوب عند اختيار الترخيص.
- رفع متتابع يتوقف عند أول فشل ويبقي الملفات الأخرى. تقدم إرسال البايتات لا يسمى حفظًا؛ النجاح يحتاج رد الباكند.
- تعديل وصف الصورة وترتيبها والرئيسية كمسودة، مع زر حفظ مستقل أو تراجع. لا تحفظ الرئيسية بمجرد اختيارها.
- حذف بتأكيد، وبديل صريح عند حذف الرئيسية مع صور باقية. نتيجة 202 تظهر كتنظيف معلق، لا نجاح كامل.
- صورة رئيسية مصغرة في قائمة العقارات ولوحة الإدارة ونتائج المطابقة، ومعرض داخل التفاصيل بأزرار ومصغرات ولوحة مفاتيح. العقارات القديمة بلا صور تبقى صالحة.
- الثيم البيج/العنابي والخط المحلي وRTL لم تتغير. لا محرر صور أو تكبير منبثق أو خرائط أو AI أو مفضلة.

## 3. دليل قراءة الأكواد

### أ. `services/propertyImages.js`: العقد والتحقق والاتصال

هذا الملف لا يرسم واجهة؛ يجمع قواعد الصور المشتركة بدل تكرارها في كل صفحة:

- `imagePropertyId` يقبل معرف Long نصيًا، أو رقمًا صحيحًا آمنًا فقط. لا يحاول استعادة معرف فقد دقته أصلًا في JavaScript.
- `imagePath` يبني مسارًا محليًا ثابتًا من معرف عقار وUUID ونوع `thumbnail/display`. `readImageDescriptor` يقارن الرابط القادم بهذا المسار ويتحقق من الأبعاد والوصف، فلا ينفذ رابطًا عشوائيًا.
- `readImageManifest` يتحقق من قائمة بحد 12 وترتيب فريد متتابع ورئيسية تنتمي إليها. `revision` يبقى نصًا، مثل `"9007199254740993"`، دون تحويله إلى Number.
- `validateImageFile` و`inspectImage` يفحصان الحجم والنوع والامتداد ورؤوس الملف والأبعاد قبل المعاينة. هذا **فحص أولي للتجربة فقط**؛ ليس فكًا كاملًا أو فحص أمان بديلًا عن Java.
- `createImagePreview` يصنع JPEG محلية حتى 320px من الصورة المفكوكة، ويغلق `ImageBitmap`. لا يحفظ الملف الأصلي أو يرسله لمزود. يحتفظ بالأصل في ذاكرة الصفحة لإرساله للباكند دون إعادة ترميزه من الواجهة.
- `createImagesApi` يعزل GET/POST/PUT/DELETE. الرفع يستخدم `FormData`؛ يزيل Content-Type الموروث من JSON ليضع المتصفح multipart boundary الصحيح. يبقى عميل Axios نفسه للكوكيز وCSRF وتجديد الجلسة.
- `createImageLoader` يطلب بايتات JPEG عبر Axios، ثم ينشئ `blob:` للعرض. `URL.revokeObjectURL` يحرر الرابط عند التبديل أو الإلغاء أو تغير الحساب. لا cache مشتركة أو localStorage للصور.

`Blob URL` رابط مؤقت لبيانات داخل ذاكرة المتصفح، وليس عنوان مجلد التخزين. استخدامه هنا يسمح بمرور قراءة الصورة عبر عميل المصادقة المعتاد، بدل تحميل رابط قرص عام.

### ب. `services/adminImages.js`: منطق إدارة العملية

`createAdminImagesManager` مخزن حالة مستقل عن React وقابل للاختبار. أهم أجزائه:

| الحالة | معناها |
|---|---|
| `manifest` | آخر مجموعة أكدها الخادم |
| `draft` | مسودة ترتيب/رئيسية/أوصاف لم تُحفظ بعد |
| `queue` | الملفات المحلية ومعايناتها وحقوقها ورموز إعادة المحاولة |
| `pendingDeletes` | عمليات حذف مؤكدة أو غير مؤكدة تحتاج متابعة |
| `busy` / `batch` | عملية واحدة أو سلسلة رفع قيد التنفيذ |
| `conflict` | توقف الكتابة حتى قراءة نسخة حديثة بعد تعارض |

`subscribe/getSnapshot` يسمحان للمكون بالاشتراك عبر `useSyncExternalStore`: عندما تتغير الحالة يعاد رسم القسم فقط، دون وضع كل قواعد الشبكة داخل JSX.

مثال مهم: وصل رفع الصورة إلى الخادم وحفظها، لكن انقطع الرد. إعادة الرفع برمز جديد قد تصنع نسخة ثانية. لذلك ننشئ `uploadToken` مرة، ونثبت الملف والحقوق والوصف عند النتيجة غير المؤكدة. زر إعادة المحاولة يعيد **نفس الرمز والبيانات**؛ عقد P10 يعيد الصورة المحفوظة بدل تكرارها. إيقاف الانتظار يلغي انتظار العميل، ولا يَعِد بإلغاء transaction في الخادم.

للتعديل يستخدم `save()` نسخة `expectedRevision`. إذا حفظت نافذة أخرى أولًا يرجع 409؛ تبقى المسودة ولا نعيد إرسالها فوق النسخة الجديدة. إعادة القراءة تحتاج تأكيدًا إن كانت ستستبدل مسودة محفوظات محلية، لكنها لا تمس ملفات الرفع المختارة أو مواصفات العقار.

الحذف مختلف: نسجل معرف المحاولة ونسختها قبل الطلب. 204 يعني اكتمالًا؛ 202 يعني إبطال القراءة وبقاء تنظيف. حتى إن نجح DELETE وفشل GET التالي، لا نفقد سجل التنظيف. الصورة المعلقة ما زالت تحتسب من الحد، ويمنع رفع جديد قبل إكمال متابعتها. لا حذف جماعي ضمني بسبب إغفال صورة من المسودة.

`createRequestGate` الموجود يمنع استجابة قديمة من تغيير حالة محرر أحدث، مع AbortController وإغلاق الموارد. أما `dispose()` فيحرر المعاينات والملفات المحلية عند إغلاق المحرر.

### ج. `components/AdminPropertyImages.jsx`: ربط الحالة بالأزرار

المكون يرسم الصور المحفوظة وقائمة الملفات والحقوق والتقدم والأخطاء والتأكيدات. كل زر يستدعي عملية محددة من المدير؛ لا يغير DB مباشرة. تعطيل الأزرار أثناء العملية أو المسودة يمنع أوامر محلية متداخلة، لكن الخادم هو الذي يفرض الصلاحية والتزامن فعلًا.

تأكيد الحذف يعرض اختيار البديل عند الحاجة، ويُنقل إليه التركيز بلوحة المفاتيح. يوجد تحذير قبل إغلاق الصفحة وروابط المغادرة العادية، وحارس لتغيير العقار أو إلغاء محرره داخل Dashboard. **مسودة الصور مؤقتة؛ الرجوع/التقدم في سجل المتصفح ليس مسار حفظ دائمًا أو منعًا مضمونًا للمغادرة.** يوجد تنبيه واضح بهذا القيد في القسم.

### د. `components/PropertyImage.jsx`: عرض موحد وآمن بالنسبة للجلسة

هذا المكون مستخدم في أربع واجهات بدل تكرار طلب الصورة وحالاتها. يحمل المصغرة عند اقترابها من الشاشة، والعرض الكبير مباشرة عند اختياره. يرفض descriptor غير صالح، ويعرض تحميلًا أو بديلًا أو إعادة محاولة.

مفتاح العرض يتضمن العقار والصورة والحالة والحساب والدور. عند تغير الحساب لا تعرض استجابة قديمة أو رابط Blob سابق للحساب الجديد؛ يلغى الطلب ويحرر الرابط. يبقى الباكند مسؤولًا عن التأكد من الحالة الحالية عند كل قراءة. تغيير حالة العقار لا يسحب صورة سبق للزائر تنزيلها، وليس هذا ادعاء منع نسخ الصور.

### هـ. `components/PropertyGallery.jsx`: اختيار صورة دون تعديل البيانات

يقرأ المجموعة المسموح بها، ويبدأ بالرئيسية المحفوظة. التالي/السابق أو اختيار مصغرة يغير `selected` محليًا للعرض فقط؛ لا يرسل PUT ولا يغير الترتيب والرئيسية. الأسهم تراعي RTL، وHome/End للأولى/الأخيرة، مع نص بديل وحالة اختيار معلنة. لا تشغيل تلقائي.

فشل المجموعة أو صورة منها لا يفشل صفحة المواصفات. المعرض مستقل عن طلب تفاصيل العقار، ويحتوي إجراءات إعادة محاولة.

### و. ربط الصفحات والتنسيق

- `Dashboard.jsx`: إبقاء محرر العقار بعد حفظه لإتاحة الصور فورًا، منع ترك مسودة الصور دون تأكيد، وتحديث القائمة بعد نجاح عملية صورة دون إعادة تركيب فورم المواصفات.
- `Properties.jsx`: المصغرة الرئيسية بدل الزخرفة القديمة داخل مساحة البطاقة نفسها.
- `PropertyDetails.jsx`: المعرض قبل المواصفات؛ المواصفات والسعر والتواصل مستقلون عنه.
- `PropertyNeeds.jsx`: مصغرة نتيجة المطابقة. `publicListing` هنا يستند إلى عقد المطابقة ACTIVE فقط؛ ليس إذنًا يتجاوز فحص الخادم.
- `PropertyImages.css`: تنسيق محلي للمكونات باستخدام متغيرات الهوية القائمة، شبكة متجاوبة وأهداف تفاعل مناسبة ولمسات RTL. البطاقة قد تقص المصغرة بصريًا، بينما صورة التفاصيل تستخدم contain دون قص محتواها.

## 4. API وجافا: ما الذي أعدنا استخدامه؟

لا مسار API جديد أو تغيير عقد استجابة في هذه الحزمة. التفاصيل في [عقد الصور](api-property-images.md). التدفق هو:

1. React يرسل صورة واحدة إلى `POST /api/admin/properties/{id}/images` مع الكوكيز وهيدر CSRF وحقول multipart.
2. `PropertyImageController` الموجود يحدد الطلب، و`PropertyImageService` يتحقق من الأدمن والعقار والحقوق والحد والرمز والمعاملة.
3. `ImageProcessor` الموجود يفحص المصدر ويصحح الاتجاه ويعيد نسختي JPEG دون metadata. `PrivateImageStorage` يحفظ الناتج خارج المجلد العام؛ DB تحفظ الوصف والروابط المنطقية لا الملف الأصلي.
4. الاستجابة تعيد manifest؛ الواجهة لا تعتبر البايتات المرسلة دليل نجاح قبلها.
5. القراءة تمر عبر backend الذي يفحص العقار وربط الصورة وREADY؛ ليس رابط static يستطيع تجاوز المسودات.

مثال جسم تعديل (المعرفات توضيحية):

```json
{
  "expectedRevision": "3",
  "primaryImageId": "11111111-1111-4111-8111-111111111111",
  "images": [
    {"id": "11111111-1111-4111-8111-111111111111", "altText": "واجهة العقار"}
  ]
}
```

القائمة تشمل كل الصور الحالية بالترتيب المطلوب؛ هذا ليس طلب حذف بإغفال بقية الصور. رد PUT الناجح هو manifest ذو revision أحدث، والقديم 409 بلا تغيير. رفع multipart لا يستخدم JSON أو Base64. حقوق النشر ومرجعها داخليان؛ لا تعرضها الواجهة العامة.

## 5. الحماية وحدود الثقة

- بقيت ADMIN وHttpOnly cookies وCSRF وCORS والتسجيل وقواعد النشر كما هي. لا تخزين JWT في JavaScript. اختبار إضافي يؤكد احتفاظ FormData بالملف والرمز وCSRF عبر تجديد الجلسة.
- تحقق الواجهة يمنع أخطاء مبكرة ويشرحها؛ يمكن تجاوزه ولا يحمي DB وحده. الباكند يعيد التحقق من كل طلب وبايتات الصورة والحقوق والصلاحيات.
- قيود القاعدة وقفل العقار وrevision وuploadToken هي حماية الاتساق المعتمدة في P10؛ ليست بديلًا لفحص الملف أو صلاحية القراءة.
- الواجهة لا تثق برابط صورة عشوائي، ولا تجعل اسم الملف مسارًا، ولا تضع نصوصه في HTML خام.
- معايير المصدر القائمة: JPEG/PNG ثابتة 8-bit، حتى 8MiB و16 مليون بكسل و8000px للضلع؛ قصير ≥480 وطويل ≥640. 12 صورة غير DELETED، والحذف المعلق يحتسب.
- لا فاحص فيروسات أو عزل decoder كامل أو مزود سحابي أو نسخ احتياطي جديد. إزالة EXIF لا تزيل وجوهًا أو لوحات أو أوراقًا داخل البكسلات؛ يراجعها الأدمن.

### تجربة المتصفح المعزولة

حاوية PostgreSQL مملوكة ومؤقتة بـtmpfs، backend على 127.0.0.1:18085، frontend على 127.0.0.1:5175، مجلد خاص مؤقت وحساب صناعي. لم تستخدم بيانات عقار أو صورة حقيقية أو أي ملف مستخدم. أوقفت العمليات والحاوية المملوكة بعد التحقق؛ حاوية المستخدم `rushd_postgres` وخدماته لم تُعد تشغيلها.

- أنشئ عقار فعليًا من الفورم بسعر `9007199254740993.01` ومساحة `500.25`. رفع صورتين أفقية ورأسية ثم تغيرت الرئيسية والترتيب والوصف، وحفظت مواصفات العقار ثم أعيد فتحه. بقيت القيم الدقيقة والترتيب والرئيسية.
- اختيار 13 ملفًا رفض محليًا قبل قائمة الرفع. رفع صورتين مقبولتين بالتتابع نجح.
- عُطل جذر التخزين المؤقت بإزالة صلاحية الكتابة، فأعاد 503. بقيت المعاينات والملفات والعنوان والوصف غير المحفوظين والسعر دون تغيير. أعيدت الصلاحية المملوكة ونجح الرفع.
- اختُبر تعارض نافذتين: الثانية حفظت أولًا، فرفضت الأولى وبقيت مسودتها حتى تأكيد استبدالها بنسخة الخادم.
- حذف الرئيسية لم يسمح بالتأكيد دون بديل. افتُعل فشل تنظيف في الملف الصناعي فقط باستخدام symlink إلى canary مملوك: ظهرت 202 وأصبحت الصورة 404 وبقي canary سليمًا. أزيل الرابط الصناعي وأكملت إعادة المحاولة التنظيف.
- إلغاء المحرر مع ملف مختار أظهر تأكيد ترك المسودة؛ اختيار البقاء احتفظ بالملف والحقوق، ثم نجح رفعه.
- الزائر رأى الرئيسية والمعرض، والعقار القديم ظهر بلا صور. جُرب التالي وHome وEnd. على 390×844 كان عرض المستند 390px دون overflow أفقي، وبقيت الصورة والأزرار والمصغرات قابلة للاستخدام.
- عند تعطل التخزين ظهرت رسالة معرض وإعادة محاولة دون فقدان المواصفات والسعر، وبعد الاستعادة عادت الصور.
- بعد تحويل العقار إلى DRAFT بقيت صوره للأدمن؛ بعد الخروج لم تظهر تفاصيله، وGET manifest والصورة المباشر أعادا 404.

لقطات الإثبات المحلية: `/tmp/rushd-p11-admin-images.png` و`/tmp/rushd-p12-mobile-gallery.png`. السجلات: `/tmp/rushd-p11-p12-{pg,h2}.log` و`/tmp/rushd-p11-p12-{test,build,lint}-final.log`. اللقطات تحتوي صورًا صناعية موسومة وليست عروضًا فعلية. تبقى السيناريوهات الأخرى مثل SOLD/INACTIVE وIDOR ضمن اختبارات Java، لا ادعاء تجربة كل حالة يدويًا في المتصفح.

## 8. تجربة يدوية وقيود باقية

في بيئة اختبار **مفعلة ومعتمدة** بالمخطط والجذر الخاص في [عقد P10](api-property-images.md):

1. ادخل بحساب ADMIN، أضف عقارًا واحفظه؛ يظهر قسم الصور أسفل الفورم.
2. اختر JPEG/PNG مملوكة ضمن الحدود، اكتب الوصف وحدد حق النشر والإقرار، ثم ارفعها. راقب رسالة قبول الخادم.
3. قدم/أخر صورة واختر الرئيسية واحفظ ترتيب الصور، ثم أعد فتح العقار للتأكد.
4. افتح التفاصيل كزائر لعقار ACTIVE واستخدم المصغرات والأسهم وHome/End، ثم جرب عقارًا قديمًا بلا صور.
5. احذف الرئيسية: اختر بديلًا صريحًا. إن ظهر تنظيف معلق فلا تغادر؛ أصلح سبب التخزين وأعد المتابعة. تغيير ترتيب العرض في المعرض لا يغير الرئيسية المحفوظة.

التفعيل على قاعدة المشروع يحتاج اعتمادًا منفصلًا للترقية ومجلد التخزين وإعداداته؛ التنفيذ الحالي لا يقوم بذلك. لذلك قد يظهر تعذر خدمة الصور في بيئتك الحالية، مع بقاء مواصفات العقار صالحة.

الطابور والمعاينات ورموز المحاولات وسجل متابعة 202 **في الذاكرة فقط**. عند مغادرة الصفحة تُفقد مسودتها، ولا تُلغى عملية خادم بدأت. GET يعرض READY فقط ولا يكتشف محاولات DELETING القديمة تلقائيًا؛ فقدان متابعة 202 يحتاج مسؤول تشغيل يراجع السجل الخاص ويكمل حذفًا موجّهًا. لم نضف API صيانة عامة أو اكتشافًا أو تخزين ملفات محليًا دائمًا خارج العقد.

لم تختبر استضافة إنتاج أو ضغط طويل أو جميع المتصفحات/أجهزة الهواتف أو screen reader فعليًا، ولا سحابة أو backup/restore. دعم لوحة المفاتيح والجوال اختبر ضمن المتصفح والأبعاد المذكورة. التحقق ناجح ضمن هذه الحدود، وليس ضمانًا أمنيًا شاملًا أو تصريح إطلاق.

أغلقت P10/P11/P12 ضمن نطاقها المعزول. التالي P13/P14 للمفضلة بعد اعتماد API/schema وسياسة العقارات غير المتاحة؛ لا تُنفّذ تلقائيًا هنا. المتبقي في الخطة 19 حزمة P13–P31، وليس تقدير أيام.
