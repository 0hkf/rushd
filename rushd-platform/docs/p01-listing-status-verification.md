# P01 — اتساق حالات البيع والإيجار

التاريخ: 14 أكتوبر 2026. الفرع: `feature/property-google-location`.

## النتيجة

أُغلق P01 ضمن نطاقه: رفض إنشاء/تعديل RENT+SOLD، وإيقاف تحويل SOLD إلى ACTIVE تلقائيًا في الفورم. لا تغيير في قاعدة البيانات أو enum أو قواعد القراءة العامة أو المصادقة. بقيت التعديلات السابقة غير الملتزمة محفوظة؛ ليست كلها جزءًا من P01.

## المشكلة الأصلية

- الباكند كان يقبل «إيجار + مباع»، مع أن SOLD حالة بيع وليست «مؤجر».
- الواجهة كانت تجعل SOLD → ACTIVE عند تبديل نوع العرض من بيع إلى إيجار، دون اختيار حالة نشر صريح؛ عند الحفظ يمكن أن يعاد نشر عقار كان مباعًا.
- تحرير سجل إيجار قديم SOLD كان يخفي الخيار من القائمة دون تغيير القيمة الداخلية، فيبدو الاختيار مختلفًا عن الحقيقة.
- رسالة Dashboard كانت تصف كل حالة غير ACTIVE بأنها غير متاحة للزوار، مع أن رابط تفاصيل SOLD عام بحسب السياسة الحالية.

## التغيير في الطبقات

1. CreatePropertyRequest وUpdatePropertyRequest: تحقق `@AssertTrue` مع `@JsonIgnore` وفق النمط الموجود للتحقق من فترة الإيجار. يمنع RENT+SOLD قبل الوصول إلى PropertyRepository. لا حقل DTO مخزن جديد ولا تعديل serialization عام.
2. adminProperty.js: منطق مشترك للحالات المقبولة ورسائلها، والتحقق من payload، وتغيير قيم الفورم دون تحويل الحالة تلقائيًا، ورسائل حفظ دقيقة لكل حالة.
3. AdminPropertyForm: خيار تعارض معطل لكنه محدد يعكس القيمة الحالية، ورسالة خطأ حقل/ملخص مع ARIA. منع الإرسال حتى اختيار حالة صحيحة صراحة. لا تمسح الأرقام أو الوصف أو بيانات الموقع عند الفشل.
4. Dashboard: رسالة SOLD توضح أن التفاصيل عامة لكنه لا يظهر في قائمة العروض المتاحة. DRAFT/INACTIVE يبقيان غير متاحين للعامة.

لم تتغير Property/Mapper/Service أو أي SQL أو إعدادات cookies/CSRF/ADMIN. تحقق الواجهة لتحسين التجربة ويمكن تجاوزه بعميل آخر؛ تحقق API هو الحاجز الإلزامي لهذه الطلبات. قيود DB الحالية لم تُمدد بهذه القاعدة، لذلك ليست حماية من كتابة مباشرة إلى القاعدة؛ أي مسار كتابة جديد يجب أن يلتزم بالعقد.

## أثر API والتوافق

لا تغيير أسماء أو أنواع حقول الطلب/الاستجابة. التغيير المقصود في القبول: RENT+SOLD أصبح خطأ400. SALE يقبل الحالات الأربع؛ RENT يقبل ACTIVE/DRAFT/INACTIVE للفترتين. status غائب أو null في Create يبقى ACTIVE، وفي Update يبقى مطلوبًا. الطلبات القديمة الصحيحة وتخزين الأرقام العشرية ونصوص الاستجابة تستمر.

جزء الطلب غير الصالح (مع بقية الحقول المطلوبة):

```json
{"listingType":"RENT","rentalPeriod":"MONTHLY","status":"SOLD"}
```

يرجع HTTP400، وضمن جسم الخطأ الحالي:

```json
{
  "message": {
    "listingStatusValid": "حالة مباع لعروض البيع فقط. اختر حالة مناسبة للإيجار قبل الحفظ."
  }
}
```

المثال يعرض جزء الجسم المتعلق بالتحقق، لا يلغي حقول الخطأ العامة الموجودة. `listingStatusValid` ليس مدخلًا يضبطه العميل؛ إرسال true له لا يتجاوز التحقق.

السجلات القديمة RENT+SOLD تبقى قابلة للقراءة كما هي ولا تتغير بمجرد عرضها أو فتح تعديلها. SOLD يبقى عامًا في التفاصيل، حتى لسجل قديم غير متوافق، كما كان؛ ليس ضمن قائمة ACTIVE أو مطابقة R3. تغيير سياسة إتاحة القديم أو إضافة RENTED يحتاج مهمة وقرارًا منفصلين. حفظ تعديل لهذا السجل يتطلب تصحيح الحالة أو نوع العرض صراحة.

## التجربة اليدوية التالية

على قاعدة تطوير معزولة أو عقار تجريبي تقبل تعديله:

1. أضف بيعًا بحالة مباع، ثم افتح التعديل.
2. اختر للإيجار؛ تأكد أن «مباع — غير صالح للإيجار» ما زال ظاهرًا، وليس «منشور».
3. اضغط حفظ؛ تظهر الرسالة ولا يحفظ التعارض، ولا تختفي المدخلات.
4. اختر مسودة وفترة شهرية أو سنوية، واحفظ وأعد فتح العقار؛ راجع الأرقام والموقع.
5. للبيع ما زال مباع خيارًا صالحًا، وتوضح رسالة الحفظ معنى إتاحته.

لا تستخدم بيانات الإنتاج للتجربة. إن كان backend المحلي القديم ما زال شغالًا، يحتاج إعادة تشغيل مقصودة ليقرأ DTO الجديد؛ لم نعد تشغيل خدمة المستخدم تلقائيًا في هذه الدفعة.

## الحدود والعمل التالي

- التحقق الكامل لـR3 على PostgreSQL لم يغلق بهذه50 حالة؛ P02 التالي مخصص له. الحزمة الكاملة266 تعمل على H2.
- لا schema migration أو إصلاح بيانات قديمة أو حالة «مؤجر» أو تغيير صلاحيات/CSRF/نشر.
- لم ننفذ صورًا أو خرائط أو مفضلة أو AI أو مواصفات أنواع جديدة. هذه حزم منفصلة في الخطة.
- الاختبار محلي ومعزول، وليس اختبار HTTPS أو استضافة أو حمل إنتاجي. حساب الديمو المحلي وتقييد منفذ PG الفعلي يبقيان إجراءي جاهزية نشر منفصلين موثقين سابقًا.
- افتراض P01: SOLD يخص البيع؛ إيقاف عرض إيجار يتم بـINACTIVE أو DRAFT حاليًا، لا إدارة عقود أو توافر إيجار.
- لا commit أو merge أو push.
