# T01 وT02 — دقة الأرقام العشرية والتحقق منها

تاريخ التحقق: 13 أكتوبر 2026. النطاق: حقول العقار العشرية الخمسة فقط، مع تحديث المستهلكين والتوثيق والاختبارات. لا تنفيذ لـT03 أو أي ميزة جديدة.

تحديث لاحق في اليوم نفسه: بعد اكتمال T01/T02، وافق المستخدم على تهيئة قاعدة التطوير الفارغة. اختُبر baseline على PostgreSQL 16 معزول، ونجحت 25 حالة للدقة وround-trip وCSRF مع Hibernate validate. ثم أُخذت نسخة احتياطية وطُبقت التهيئة يدويًا على قاعدة التطوير. تفاصيل هذا العمل المنفصل في [دليل التطوير المحلي](local-development-setup.md). عبارات عدم اختبار PostgreSQL أدناه توثق حالة تسليم T01/T02 الأصلية؛ الحزمة الكاملة ما زالت تستخدم H2، ولا نزعم أنها اختُبرت كلها على PostgreSQL.

## النتيجة

القيم المقبولة تبقى دقيقة في الرحلة: إدخال الأدمن كنص → طلب JSON بنصوص عشرية → BigDecimal والتحقق → أعمدة JPA الحالية → نصوص عشرية في الاستجابة → تنسيق نصي في الواجهة. تم التحقق من الحفظ وإعادة القراءة على H2 معزول؛ **لم يُختبر PostgreSQL**، ولا يُعتبر نجاح H2 دليلًا على نجاحه.

## الفحص قبل التنفيذ

- الفرع: `feature/property-google-location`. وُجدت تعديلات سابقة غير committed، بينها R2/R3 والتوثيق؛ حُفظت ولم تُستبدل. لا تعليمات AGENTS.md محلية في مسار المشروع أو آبائه الذين جرى فحصهم.
- جميع الملفات المطلوبة موجودة: Property وCreate/UpdatePropertyRequest وPropertyResponse وPropertyMapper وPropertyService واختبارات العقار وAdminPropertyForm وخدمات الأرقام ومستهلكو Dashboard وProperties وPropertyDetails وR1/R3.
- Property وMapper وService يستخدمون BigDecimal بالفعل ولا ينفذون تقريبًا صريحًا؛ لذلك لم نكرر mapping أو نغيرها. المشكلة كانت تحويل النموذج إلى Number، ثم عودة BigDecimal كأرقام JSON يقرأها JavaScript كـNumber، مع غياب التحقق من precision/scale قبل الحفظ.
- مثال فعلي: `Number("9007199254740993.01")` ينتج `9007199254740994`. تنسيق القيمة بعد ذلك لا يعيد الخانات المفقودة. كما أن الكسور الزائدة قد تصل إلى numeric في القاعدة بدل رفضها في API.
- استُخرجت الحدود من تعريفات JPA والقواعد القائمة. لم تتغير أعمدة القاعدة أو migrations. لم نفحص مخطط قاعدة PostgreSQL الفعلية.

## العقد والقرارات

العقد الكامل وحدوده وأمثلة الطلب والاستجابة في [api-properties.md](api-properties.md#عقد-الأرقام-العشرية--t01-وt02).

| الحقل | precision / scale | المجال | null |
|---|---|---|---|
| price | 19 / 2 | 0.01 … 99999999999999999.99 | مرفوض |
| area | 12 / 2 | 0.01 … 9999999999.99 | مرفوض |
| streetWidth | 10 / 2 | 0.01 … 99999999.99 | مقبول |
| latitude | 10 / 7 | −90 … 90 شاملًا | مقبول |
| longitude | 10 / 7 | −180 … 180 شاملًا | مقبول |

- اعتمد المستخدم صراحة تحويل نوع الحقول الخمسة في استجابات Property من number إلى string. أسماء الحقول وBigDecimal داخل Java لا تتغير. يلزم تحديث أي مستهلك خارجي يتوقع number، ونشر الواجهة والباكند بعقد متوافق.
- تستمر الطلبات الرقمية القديمة الصحيحة في العمل، بما فيها الصيغ الأسية المنضبطة التي يقبلها BigDecimal ضمن الحدود. يوصى بالنصوص للطلبات الجديدة كي لا يفقد العميل الدقة قبل الإرسال.
- الكسور الزائدة مرفوضة حتى إن كانت أصفارًا نهائية؛ لا قص أو تقريب صامت. الصيغ غير الصالحة وتجاوز الحدود والخانات والأسس الضخمة ترجع 400 قبل الحفظ.
- الاستجابة plain decimal لا أسية؛ `0.0000001` لا تتحول إلى `1E-7`. null يبقى null. قد تختلف الأصفار النهائية بعد إعادة القراءة، لكن القيمة العددية نفسها ثابتة.
- الإدخال المرئي يقبل أرقام ASCII والعربية والفارسية والفاصل `٫`، ويزيل المسافات الخارجية ويوحّد الأصفار البادئة دون تغيير القيمة. يرفض فواصل الآلاف والأسس و`+` والصيغ الناقصة مثل `.5` و`1.` بدل التخمين، ويحتاج النقطة العشرية مع رقم على جانبيها.
- المحلل النصي في الواجهة يرفض الإدخال الأطول من 128 رمزًا دون قصه؛ جميع القيم الطبيعية ضمن حدود الحقول أقل من هذا الحد بكثير. هذا حد إدخال محلي وليس تغييرًا لإعداد JSON العام.
- السعر بالريال، المساحة بالمتر المربع، وعرض الشارع بالمتر وفق الواجهة الحالية؛ سعر الإيجار يبقى للفترة المحددة بلا تحويل شهري/سنوي.

## ما تغير في كل طبقة

1. **الطلب:** Create وUpdate يحويان التحقق نفسه للمجال والدقة. SafeDecimalPrecision يحسب الخانات باستخدام long قبل طرح scale، لعدم overflow مع قيمة مثل `0E+2147483647`؛ حد الإحداثيات العددي وحده لا يرفض صفرًا بهذا التمثيل.
2. **الحفظ:** BigDecimal وMapper وService وJPA تبقى كما هي، بعد تحقق الطلب. اختبارات JPA تستخدم flush وclear ثم قراءة جديدة، وليست assertions على الكائن قبل الكتابة فقط.
3. **الاستجابة:** PlainDecimalStringSerializer محلي على الحقول الخمسة في PropertyResponse يستخدم toPlainString. لا تعديل عام لـObjectMapper؛ اختبار مستقل يثبت أن BigDecimal غير المرتبط بالعقار ما زال JSON number.
4. **الإدخال:** AdminPropertyForm يستخدم text مع inputMode decimal، وحالة نصية وpayload نصي/null. القيم لا تمر عبر Number. تظهر أخطاء الحقول دون تعديل قيمها، ولا تمسح عند رفض الخادم للحفظ.
5. **التحويل والعرض:** decimal.js مشترك، يستخدم BigInt للمقارنات وعمليات نصية للتنسيق دون تقريب. adminProperty.js يفصل إنشاء حالة النموذج والـpayload القابلين للاختبار. إذا استقبلت الواجهة رقمًا بدل النص المتوقع، تمنع إعادة حفظه بوصفه قيمة دقيقة أو تحويله خفية إلى null.
6. **المستهلكون:** Dashboard وProperties وPropertyDetails يستخدمون التنسيق الدقيق وbdi باتجاه LTR مع الوحدات خارجه. عولج قص السعر الطويل على بطاقات الهاتف بتصغير الأرقام الطويلة فقط والسماح للوحدة بالالتفاف. R1/R3 يستخدمان المنطق المشترك دون تغيير عقدهما أو قواعد المطابقة.

تحقق الواجهة للتغذية الراجعة وتجهيز الطلب، ويمكن تجاوزه بعميل خارجي. تحقق الباكند إلزامي قبل الكتابة. قيود القاعدة دفاع أخير وليست بديلًا للتحقق، ولا نعتمد على تقريب القاعدة لقبول قيمة غير صالحة.

## الأمان والتوافق

لم تتغير المصادقة أو cookies أو JWT أو CSRF أو صلاحية ADMIN أو قواعد النشر. الإضافة هي تحقق عددي محلي صارم قبل الوصول إلى المستودع. اختُبرت 401 لغير المسجل، و403 للمشتري عند الإنشاء/التعديل وقائمة الإدارة، و403 عند غياب CSRF. لا أسرار أو مفاتيح أو dependencies جديدة، ولا اتصال بخدمات Google.

العقارات القديمة التي حقول موقعها null تبقى صالحة. PUT لا يزال تعديلًا كاملًا: حذف حقل اختياري من الطلب يزيله؛ النموذج يحافظ على قيمه عند فتح التعديل وإعادة الإرسال. لا تمثل هذه المهمة إصلاحًا لبيانات سبق أن فقدت دقتها.

## تجربة يدوية

نفذها على بيئة اختبار منفصلة بحساب ADMIN موجود، لا على بيانات فعلية:

1. افتح لوحة الإدارة وأدخل بيانات عقار صحيحة؛ السعر `٩٠٠٧١٩٩٢٥٤٧٤٠٩٩٣٫٠١`، المساحة `۱۵۰٫۲۵`، عرض الشارع `١٢٫٣٤`، وخط العرض `-٢١٫٤٢٢٥٠٠١` وخط الطول `٣٩٫٨٢٦٢٠٠١`.
2. احفظ وافتح القائمة والتفاصيل. يجب أن ترى السعر `9٬007٬199٬254٬740٬993٫01` والمساحة `150٫25`، دون خسارة آخر خانة أو الكسور.
3. افتح التعديل: يجب أن تجد `9007199254740993.01` و`150.25` والإحداثيات ذاتها، مع بقاء بيانات الموقع النصية الاختيارية. غيّر قيمة صحيحة واحفظ ثم أعد القراءة.
4. جرب السعر `1.001` أو عرض الشارع `0` أو latitude `90.0000001`: تظهر رسالة ولا يتم الحفظ أو التقريب. جرّب تغيير عنوان العقار إلى مسافات فقط مع أرقام صحيحة؛ الباكند يرفض الطلب وتبقى المدخلات.
5. أنشئ عقارًا آخر دون عرض شارع أو إحداثيات. افتح تعديله وتأكد أن الحقول بقيت فارغة وليست أصفارًا.
6. راجع Network: الحقول العشرية نصوص في الطلب الجديد والاستجابة. يمكن لعميل API إرسال الأرقام القديمة الصحيحة، لكنه لا ينبغي أن يستخدم Number لقيم حساسة كبيرة.

## القيود المتبقية

- يلزم تحقق PostgreSQL معزول قبل اعتماد النشر عليه؛ لم يُطبق أي SQL على القاعدة الفعلية، ولم تُفحص مطابقة أعمدتها الفعلية لتعريفات JPA.
- لا نستطيع استعادة دقة فقدت سابقًا في بيانات محفوظة أو لدى مستهلك خارجي. تغيير الاستجابة يحتاج تنسيق نشر مع أي عميل خارج هذا المشروع.
- ضمان الاختبار للقيمة العددية لا للتهجئة الأصلية والأصفار النهائية. null لا يساوي صفرًا.
- اختبارات الواجهة الآلية تختبر الخدمات النقية والمنطق القائم؛ تجربة المتصفح مكمّلة يدوية بهذه الأدوات، وليست حزمة E2E آلية مضافة إلى CI. لم نضف dependency لاختبارات المتصفح.
- نتائج الفحص والبناء لا تعني تدقيقًا أمنيًا شاملًا أو توافقًا مع كل متصفح/بيئة نشر.
- لا commit أو merge أو push.
