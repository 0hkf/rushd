# P16 — قواعد تقييم عقار مختار المعتمدة

التاريخ: 27 أكتوبر 2026. الحالة: **مكتمل كحزمة قرار وتوثيق: اعتمد المستخدم D01–D05 وأمثلة الأنواع السبعة والحالات الحدية. لا تنفيذ كود أو API بعد**.

هذه حزمة قرار وتوثيق فقط. لا Java أو React أو API أو schema أو بيانات أو dependencies أو تشغيل خدمات ضمن P16. يبدأ تنفيذ الباكند في P17 والعرض في P18 بعد إغلاق القرارات والأمثلة.

## 1. الهدف والفرق عن الموجود

المستخدم المسجل يختار عقارًا واحدًا، ثم نقارنه باحتياجاته المؤكدة ونوضح الحقائق والمخالفة والمجهول. لا يشترط أن يكون العقار ضمن نتائج R3 حتى نقيمه؛ فقد يكون أعلى من الميزانية أو مخالفًا لشرط مهم.

- R3 الحالي يبحث ويستبعد المخالف ثم يرتب العقارات المؤهلة.
- P16 يفسر عقارًا بعينه حتى عند المخالفة، ولا يغير ترتيب R3.
- تقييم السعر بالنسبة إلى السوق ليس ضمن P16؛ كون السعر ضمن ميزانية المستخدم لا يجعله رخيصًا أو عادلًا.
- لا AI أو تقدير استثمار أو قرب خدمات أو مسافة قيادة أو تحقق ميداني من الإعلان.

المرجع التنفيذي: [P16 في الخطة](execution-prompts.md#p16--اعتماد-قواعد-تقييم-عقار-مختار)، [عقد الاحتياجات](api-property-needs.md)، [المطابقة الحالية وP06](api-property-matching.md).

## 2. الفحص: ما سنبني عليه لاحقًا دون إعادة تنفيذه

- `PropertyNeedsRequest` يتحقق من النوع والبيع/الإيجار والفترة والميزانية، ومن الحي والمساحة ومعناها ومعايير المواصفات وأهميتها.
- `PropertyNeedsResponse.from` يثبت الافتراضات الحالية: مكة المكرمة، SAR، المتر المربع؛ الحي تفضيل عند غياب الأهمية، ومدى المساحة إلزامي عند غيابها. لا نغير تلك الافتراضات في P16.
- `PropertyMatchingFields` يقارن المعايير المنطبقة فقط، ويميز null عن false وعن0. نطاق العداد معيار واحد، وكل تفضيل بوزن واحد.
- `PropertyNeedsAreaBasis` يقرأ معنى المساحة المختار فقط، دون الرجوع إلىarea عند غياب مساحة مسماة.
- `PropertyLocationComparison` يملك مساواة أسماء مكة الثلاثة وتوحيد الحي المحافظ؛ لا Google أو تشابه تخميني أو تغيير للسجلات.
- `PropertyMatchingService` يستبعد المخالف مسبقًا؛ لذلك لا يجوز استدعاؤه ثم البحث عن العقار المختار في أول صفحة. بعض دوال الدليل فيه خاصة؛ استخراج منطق مشترك في P17 يجب أن يثبت بقاء R3 بلا تغيير، لا نسخ خدمة كاملة.
- `Property` لديهupdatedAt لكنه ليس رقم إصدار تفاؤليًا؛ لا نعتمد الطابع الزمني وحده ضمانًا لعدم تغير البيانات.

الحقول المستبعدة من P06 تبقى مستبعدة: العمر المؤرخ، الوصف الحر، هدف الاستثمار كدليل جدوى، أو اشتقاق معنى مساحة غير معلوم. لا نضيف معيارًا جديدًا لمجرد وجوده في الإعلان.

## 3. سجل القرارات المعتمدة

| القرار | القاعدة | الحالة |
|---|---|---|
| D01: إتاحة العقار | ACTIVE فقط لكل الأدوار؛ SOLD والخاص لا يقيمان | معتمد صراحة في27أكتوبر |
| D02: المجهول | مخالفة إلزامية معروفة تكفي لـ«غير مناسب»؛ دونها أي معيار مطلوب مجهول يمنع حكمًا إيجابيًا نهائيًا | معتمد: حكم محافظ، لا تصنيف مبدئي عند جهل التفضيلات |
| D03: حدود الفئات | كل التفضيلات/نصفها على الأقل/أقل من النصف، بأوزان واحدة؛ دون تفضيلات لا «مناسب جدًا» | معتمد، بما فيه أمثلة الأنواع والحدود والتفضيل الواحد |
| D04: اختلاف السياق | النوع والعرض والفترة ونطاق التجاري شروط ثابتة؛ لا مقارنة أسعار بفترات مختلفة أو مساحات غير متجانسة | معتمد: فصل المقارنات دون تحويل تلقائي |
| D05: تغير البيانات | لقطة مؤرخة دون حفظ دائم؛ تعديل الاحتياجات يلغي النتيجة؛ كل إعادة تقييم تقرأ البيانات والإتاحة الحالية، دون متابعة لحظية لتعديلات الأدمن | معتمد: اللقطة المؤرخة وإعادة التقييم |

اختيارات المستخدم المسجلة في الجولة الأولى: «ACTIVE فقط، والمباع وغير المتاح بلا تقييم»، و«حكم محافظ عند أي معيار مطلوب مجهول»، و«أعتمد القواعد المقترحة، ثم نراجع أمثلتها لكل نوع». وفي جولة المراجعة أكد: «أعتمد الأمثلة والحدود المعروضة»، و«أعتمد الفصل وعدم التحويل التلقائي»، و«أعتمد اللقطة المؤرخة وإعادة التقييم». بذلك أغلقت بوابات القرار في P16؛ لا يستنتج منها إذن تنفيذ P17 أو تشغيل خدمات أو تطبيق SQL.

## 4. من يدخل التقييم وما الذي يبقى خاصًا؟

المعتمد D01: حساب مسجل مع CSRF، وعقارACTIVE عند قراءة الطلب، حتى لو كان الطالبADMIN. لا نوسع القراءة إلى المسودات بحجة أن الأدمن يستطيع رؤيتها في لوحة الإدارة.

المفقود أو غير المتاح للتقييم يرجع خطأ عامًّا واحدًا دون تفاصيل خاصة أو سبب يكشف حالة النشر. SOLD خارج التقييم المعتمد؛ أي إضافة مستقبلية له تحتاج قرارًا وعقدًا مستقلين، ولا تستنتج من إتاحة تفاصيله العامة.

العقار العامACTIVE الذي يخالف نوع الطلب أو ميزانيته لا يصبح404 لهذا السبب؛ تعرض مخالفته. المدينة خارج أسماء مكة المعتمدة لا تتحول إلى مدينة مقبولة؛ تظهر مخالفة نطاق البحث، دون ترشيح مدينة جديدة أو استنتاج الموقع من الإحداثيات.

لا نعرض بيانات ناشر أو حساب أو أدلة مخزنة لعقار أصبح غير متاح عند طلب تقييم جديد. الصورة ليست دليل ملاءمة، ولا يلزم إضافتها إلى استجابة التقييم.

## 5. معنى كل دليل

| دلالة النتيجة | معناها |
|---|---|
| MATCHED | معلومة قابلة للمقارنة تحقق المعيار |
| MISMATCHED | معلومة قابلة للمقارنة تخالف المعيار |
| UNKNOWN | المعلومة اللازمة غير معروفة أو غير صالحة للاستدلال |
| NOT_COMPARABLE | سياق المقارنة مختلف؛ مثل سعر شهري مقابل طلب سنوي أو معنى مساحة لنوع مختلف |
| NOT_REQUESTED | لم يطلب المستخدم المعيار؛ لا نقطة ولا عقوبة، ويمكن عدم تضمين سطره |

هذه دلالات الأدلة المعتمدة للتقييم الجديد؛ تثبت أسماءDTO/JSON التنفيذية في P17 قبل بناء العقد الجديد، دون تغيير معنى الدلالات أو إضافة قيمة إلىenum المطابقة الحالية عالميًا. لا تغيير لاستجابات المطابقة في P16.

كل دليل يربط اسم المعيار بما طلبه المستخدم، وأهميته، والقيمة المسجلة، والوحدة/معنى المساحة، والنتيجة وسبب ثابت قابل للاختبار. لا تستخرج الواجهة معنى برمجيًا من جملة عربية وحدها.

## 6. الشروط الدائمة والمقارنات

- نوع العقار ونوع العرض وفترة الإيجار عند انطباقها ونطاق مكة والميزانية شروط ثابتة؛ نطاق التجاري كذلك إذا اختاره المستخدم. لا يخففها محرك التقييم.
- ميزانية البيع تقارن بسعر البيع فقط؛ الإيجار يقارن بالفترة نفسها فقط. لا تحويل شهري/سنوي أو مقارنة سعر بيع بقيمة إيجار. السعر المجهول/غير الموجب ليس سعرًا داخل الميزانية.
- السعر عند الحد الأعلى يحقق الميزانية، وأعلى منه بـ0.01 يخالفها. المقارنة بـBigDecimal والنقل/العرض بنصوص عشرية دقيقة؛ لاNumber أو تقريب صامت.
- الحي منdistrict فقط وبالتوحيد المعتمد، لاneighborhood أو عنوان الوصف. اختيار الحي إلزاميًا أو تفضيلًا يحترم كما في P06.
- المساحة منareaBasis المختار، بحدود شاملة، والمدى كله معيار واحد. لا نقارن أرضًا بصافي وحدة، ولا نحول الرقم القديم إلى معنى مسمى.
- العدد0 معلومة عندما يسمح به العقد؛ false لا يساويnull. القوائم تطابق أسماءها، لا ترتيب جودة خفي بينها.
- عند اختلاف النوع أو نطاق التجاري، المواصفات أو المساحات التي لم تعد متجانسة توسمNOT_COMPARABLE، لا تطابقًا أو إخفاقًا مخترعًا. الاختلاف الهيكلي المعروف نفسه مخالفة إلزامية. إذا كان السياق مجهولًا، فلا نبني مقارنة مضمونة عليه.
- لكل معيار إلزامي/تفضيلي يرسله المستخدم قواعد الانطباق والحدود الحالية. طلب غرف نوم لأرض مثلًا يرفض كطلب غير صالح، وليس تقييمًا منخفضًا لعقار الأرض.
- المعلومات غير المطلوبة لا تخفض التقييم، ولا يتحول الوصف أو هدفINVESTMENT إلى شرط أو سبب إيجابي.

## 7. التصنيف المعتمد وترتيب الحسم

يطبق الترتيب التالي؛ لا تجمع نقاطًا تتجاوز شرطًا إلزاميًا:

1. عقار غير متاح وفقD01: لا تقييم أصلًا، ولا كشف أدلة خاصة.
2. أي مخالفة معروفة لشرط ثابت أوREQUIRED: **غير مناسب لمتطلباتك**، مع بقية المخالفات والمعلومات الناقصة؛ لا تمحو مخالفة معروفة بسبب وجود مجهول آخر.
3. دون مخالفة إلزامية، أي معيار مطلوبUNKNOWN أو مقارنة لا يمكن حسم سياقها: **بيانات غير كافية للحكم** وفقD02 المعتمد. هذه ليست فئة إيجابية أو حكمًا بأن العقار سيئ. اختلاف السياق المعلوم الذي يخالف شرطًا ثابتًا يحسم عدم الملاءمة في الخطوة2، ولا ينتج مقارنة مالية أو مساحية مضللة.
4. إذا اكتملت البيانات وتحققت الإلزاميات، نطبقD03 على التفضيلات فقط.

لتكنN عدد التفضيلات المطلوبة، وM عدد المتحقق منها. الحي معيار واحد، ومدى المساحة معيار واحد، ومدى كل عداد معيار واحد؛ لا أوزان أو درجات يرسلها العميل.

| الحالة بعد اجتياز الخطوات السابقة | التصنيف المعتمد |
|---|---|
| N=0 | مناسب للشروط الأساسية المدخلة، دون ادعاء «مناسب جدًا» |
| N>0 وM=N | مناسب جدًا لمتطلباتك المدخلة |
| M<N و2×M≥N | مناسب لمتطلباتك المدخلة |
| 2×M<N | مناسب جزئيًا لمتطلباتك المدخلة |

لا نحتاج قسمة أوfloat لحسم نصف العدد، ولا نعرض درجة من100. اعتمد المستخدم مثال التفضيل الواحد: تحققه «مناسب جدًا» ضمن هذا الطلب المحدود فقط، وعدم تحققه «جزئي» إذا تحققت الإلزاميات؛ لا يقدم التصنيف كتقييم شامل لكل جودة العقار أو سعره.

تغطية البيانات تعرض أعداد المعايير المتحققة والمخالفة والمجهولة وغير القابلة للمقارنة من المطلوب فقط، لا نسبة اكتمال كل حقول العقار. وفقD02 المعتمد، لا نعرض تصنيفًا إيجابيًا مبدئيًا لتجاوز تفضيل مجهول؛ نعرض الأدلة المعروفة و«بيانات غير كافية للحكم» ما لم توجد مخالفة إلزامية معلومة تحسم عدم الملاءمة.

## 8. أمثلة قبول لكل نوع — صناعية وليست عروضًا حقيقية

في الصفوف التي تصنف إيجابيًا: ACTIVE وفي مكة ونفس النوع والعرض/الفترة، والسعر ضمن الميزانية، وجميع الإلزاميات معلومة ومتحققة، ما لم يذكر خلاف ذلك. لا دليل سوقي في هذه العينات.

| النوع | الاحتياج والحقائق التوضيحية | الحكم المعتمد وسببه |
|---|---|---|
| أرضLAND | مساحة أرض≥500 إلزامية؛ المسجلة500. أربعة تفضيلات: الحي والكهرباء والمياه والصرف. الحي والكهرباء متحققان؛ المياه والصرف مسجلانfalse خلاف الطلبtrue | مناسب؛2/4، والمخالف تفضيل لا شرط |
| شقةAPARTMENT | صافي≥120 وغرف≥3 ومصعدtrue إلزامية؛ كلها متحققة. الحي وموقف≥1 وشرفةtrue وتأثيثFULL أربعة تفضيلات معلومة ومتحققة | مناسب جدًا لمتطلبات هذا الطلب؛4/4 |
| فيلاVILLA | ميزانية1,000,000؛ السعر1,000,000.01، ولو تحققت كل التفضيلات | غير مناسب؛ تجاوز إلزامي دقيق لا تعوضه التجهيزات |
| عمارةBUILDING | إجمالي الوحدات≥8 إلزامي؛ المسجلnull. كل التفضيلات المعروفة متحققة | بيانات غير كافية؛ لا نستنتج الإجمالي من عدد سكني منفرد أو من الأدوار |
| تجاريCOMMERCIAL | الطلبUNIT وصافي وحدة≥100؛ الإعلانWHOLE_BUILDING بإجمالي بناء1000 | غير مناسب لاختلاف النطاق؛ لا نقارن1000 بناء بصافي وحدة100 |
| مزرعةFARM | مساحة أرض≥5000 وكهرباءtrue إلزامية ومتحققة. ثلاثة تفضيلات: مصدرWELL ومواقف≥2 وحوشtrue. المصدرWELL، المواقف0، الحوشfalse | مناسب جزئيًا؛1/3، والصفر/false معلومتان لا مجهولان. لا إثبات ترخيص بئر أو جودة مياه |
| أخرىOTHER | ميزانية ونوع/عرض متحققان، ومساحة معلنة≥200 إلزامية والمسجلة250؛ لا تفضيلات | مناسب للشروط الأساسية فقط، لا حكم شامل على نوع غير موصوف ولا «مناسب جدًا» |

الحالات الحدية المشتركة المعتمدة:

- أربعة تفضيلات مع إلزاميات متحققة:4→جدًا،3 أو2→مناسب،1 أو0→جزئي؛ لا نطبقها على بيانات ناقصة في السياسة المحافظة.
- ثلاثة تفضيلات:2→مناسب،1→جزئي؛ لا تقريب نسبة.
- شرط مصعدtrue إلزامي والمسجلfalse: غير مناسب؛ إذاnull ودون مخالفة إلزامية أخرى: بيانات غير كافية.
- الحي تفضيل معلوم مخالف، والمصعد تفضيلnull، دون مخالفة إلزامية: بيانات غير كافية وفقD02 المعتمد؛ ليست نتيجة رفض إلزامي.
- سعر إيجار شهري4000 وطلب سنوي50000: الفترة مخالفة، والسعرNOT_COMPARABLE؛ لا ادعاء أن4000 داخل الميزانية السنوية.
- طلبLAND وإعلانAPARTMENT: النوع مخالف، ولا نستخدم مساحة وحدة كمساحة أرض لتجميل النتيجة.
- طلبUNIT_NET والمساحة المعلنة150 وصافي الوحدةnull: صافي المساحةUNKNOWN، لاfallback إلى150.
- طلب صحيح قديم دون معاييرP06 يبقى قابلًا للتقييم بالقواعد المشتركة؛ غياب التفضيلات لا يضيف تفضيلات افتراضية جديدة.

## 9. نتيجة مؤرخة وتغير الاحتياجات أو العقار

المعتمد D05: كل نتيجة تحمل نسخة احتياجات مؤكدة، وهوية العقار وحقائقه العامة المستخدمة، ووقت التقييم ونسخة قواعد مستقلة للتقييم المختار؛ الاسم الفني المقترح لـP17 هو`selected-property-evaluation-v1`. لا نعيد تسميةmatching-v1/v2 أو نغير سلوكهما بسبب التصنيف الجديد.

لا حفظ دائم للاحتياجات أو النتائج، ولا تعلم من مفضلة المستخدم. في P17 يثبت تمثيل بصمة نسخة الحقائق العامة أوsnapshot القابل للتحقق؛updatedAt وحده ليس ضمانًا. لا بيانات حساب أو أسرار ضمن البصمة أو الاستجابة.

تعديل الاحتياجات يلغي نتيجة الطلب القديم والرد المتأخر. فتح تقييم جديد يقرأ الإتاحة والحقائق الحالية، ولا يعيد نتيجة قديمة لعقار لم يعد متاحًا. تغيير العقار بعد إرسال نتيجة سابقة يجعلها لقطة تاريخية لا ضمانًا لاستمرار النشر أو السعر؛ تعرض إعادة تقييم واضحة. لا ندعي متابعة لحظية أو تحققًا مستمرًا دون طلب جديد.

إذا أضيفcache أو حفظ تاريخ أوإشعارات مستقبلًا، فذلك عقد جديد وليس افتراضًا ضمن هذه الحزمة.

## 10. بوابة تنفيذ P17 ومصفوفة الاختبار المطلوبة

اعتمدتD01–D05 والأمثلة. عند طلب بدء P17، يثبت مسارPOST وDTO التقييم الجديدان قبل التنفيذ، مع المصادقة وCSRF والتحقق من الطلب قبل قراءة العقار. لا معلمات صفحات أو ترتيب مرشحين أوحد1000 لتقييم هوية واحدة، ولا مسح المخزون أو سحب قائمةR3 ثم تصفية أول صفحة.

مصفوفة القبول: الأنواع السبعة والنطاقان التجاريان؛ كل إلزامي/تفضيل معmatch/mismatch/unknown؛ العدد0 وfalse؛ حدود الأسعار والمساحات والدقة العالية؛ المدينة والحي؛ اختلاف النوع والفترة؛ طلب قديم؛ غياب معايير إضافية؛ البيانات الناقصة؛ قواعد حسم الفئات؛ خاص/مفقود/مباع وأدمن؛ CSRF/401/403؛ تغير العقار والاحتياجات والرد المتأخر؛ بقاءCRUD وR1/R3 كما هي.

P17 يختبر الوظائف المشتركة والـHTTP وPostgreSQL المعزول؛ P18 يختبر عرض الأسباب والبيانات الناقصة وRTL والجوال والإلغاء. هذه **حالات قبول مكتوبة، وليست اختبارات منفذة الآن**. لا نعيد استخدام أعداد اختبارات الجولة الماضية كدليل تنفيذ لهذه الميزة.

## 11. نتيجة إغلاق P16 وتسليمها

- اعتمد المستخدم القرارات والأمثلة والحدود صراحة، بما في ذلك التفضيل الواحد والمجهول وعدم قابلية المقارنة وتغير البيانات.
- وثق ترتيب الحسم ومتطلبات نسخة القواعد والفصل عن R3 وعن السوق، وتسليم واضح إلىP17 ثمP18.
- لا تشترط الحزمة تغيير مخطط أو تشغيل خدمة أو تفعيل صور/مفضلة أو ترقية حزم أو إصلاح مسودة الأدمن. هذه مسارات منفصلة وتبقى بوابات أمان/إطلاق حيث تنطبق.

أغلقت P16 كحزمة قرار وتوثيق في27أكتوبر2026. التحقق هنا مراجعة اتساق الوثائق والروابط وفحصwhitespace فقط؛ لا اختبارات تطبيق جديدة أو ادعاء تنفيذ للتقييم. **التالي P17 للباكند، ثم P18 للواجهة، ولا يبدأ أي منهما تلقائيًا**. لا تغييرات قاعدة أو خدمات أوcommit/merge/push ضمن هذه الحزمة.
