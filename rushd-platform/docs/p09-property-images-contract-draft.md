# P09 — مسودة عقد صور العقارات والتخزين

التاريخ: 20 أكتوبر 2026؛ تحديث الحالة: 21 أكتوبر 2026. **الحالة: P09 معتمد ومغلق كقرار؛ اكتمل الباكند P10 وإدارة الصور والمعرض P11/P12 ضمن الاختبار المعزول.** اعتمد المستخدم التخزين المحلي الخاص للتطوير، 12 صورة و8MiB للمصدر، والعقد الفني كاملًا. اعتماد العقد لا يعني تفعيل الصور أو ترقية قاعدة المشروع. [نتيجة الباكند](p10-property-images-verification.md) و[نتيجة الواجهة وشرح الأكواد](p11-p12-property-images-ui-verification.md). الفحص أدناه يسجل نقطة البداية في P09، قبل إضافة التنفيذ.

## 1. نتيجة الفحص والنطاق

- الفرع `feature/property-google-location` مع تغييرات سابقة كثيرة محفوظة؛ ليست كلها من هذه الحزمة. لم توجد تعليمات AGENTS.md محلية في المشروع أو أسلافه.
- لا كيان صور أو خدمة تخزين أو upload controller أو multipart configuration حاليًا. docker-compose يشغل PostgreSQL فقط؛ لا خدمة تخزين صور قائمة في تعريف المشروع. لم نفحص حسابات المستخدم الخارجية أو ملفات أسراره، ولا نفترض وجود اشتراك تخزين.
- Property/DTO/Mapper/Service لا تحمل ملفات صور. توجد صور تصميم ثابتة بالواجهة؛ ليست صور عقارات ولا مصدرًا لحقوق نشرها. لا نعيد استخدامها كصور عروض.
- التسجيل العام BUYER، والكتابة ADMIN مع cookies وCSRF. قائمة التصفح ACTIVE؛ التفاصيل العامة ACTIVE أوSOLD؛ المسودات/INACTIVE للأدمن فقط. هذه الحدود لا تتغير.
- لا endpoint لحذف العقار حاليًا؛ لا نضيفه بسبب الصور. العقار بلا صور يظل صالحًا، ولا صور مطلوبة للنشر أو تغيير للعقارات القديمة.
- فحص القرص المحلي أظهر قرابة12GiB متاحة وقت الفحص؛ هذا قرص مشترك لا حجز مساحة أو ضمان استضافة. ترقية P04 لم تطبق على قاعدة المشروع، ولا يطبق P09/P10 أي SQL عليها تلقائيًا.

## 2. خيار التخزين — قرار مطلوب

| الخيار | المنفعة | القيود |
|---|---|---|
| A — ملفات محلية خاصة خلف Spring، المقترح للتطوير الآن | لا حساب أو مفتاح أو مزود خارجي؛ يبقى العقد قابلًا لاستبدال مزود التخزين لاحقًا | تحتاج قرصًا دائمًا ونسخًا احتياطية؛ ليست استضافة عامة مجانية، ولا تصلح تلقائيًا لخادم بقرص مؤقت أو عدة نسخ من التطبيق |
| B — Supabase Storage في bucket خاص | تخزين منفصل عن جهاز التطوير، مع صلاحيات خاصة | يحتاج حسابًا ومنطقة بيانات وإعداد أسرار خادم ومراجعة الحصص قبل P10؛ لا bucket عام ولا انتقال تلقائي لقاعدة PostgreSQL أو مصادقة Rushd إلى Supabase |

وفق [الأسعار الرسمية](https://supabase.com/pricing) عند المراجعة: المجاني يعرض1GB ملفات، و5GB نقل و5GB نقل مخبأ، وتوقف مشاريع بعد أسبوع خمول. الحصص وشروط الخدمة قد تتغير، وليست ضمان تشغيل دائم بلا تكلفة. [توثيق buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) يميز الخاص عن العام؛ العام يكشف الملف لمن يملك رابطه. لا نقل لصور أو بيانات إلى مزود أثناء P09.

التوصية A تنفيذ محلي معزول أولًا؛ اختيار B يستدعي استكمال المنطقة والحساب والحصص والنسخ دون مشاركة مفاتيح في الدردشة. لا اختيار Cloudinary/S3 أو خطة مدفوعة تلقائيًا.

### عقد المسار المحلي المقترح

- مجلد مطلق مستقل خارج Git وfrontend/public وwebroot، بصلاحيات حساب الخدمة فقط؛ لا عنوان static له. لا يؤخذ أي مسار من الطلب، ولا تتبع symlinks أو يسمح بالكتابة خارج الجذر.
- التفعيل opt-in: ميزة الصور غير مفعلة دون جذر خاص مهيأ صراحة. عند التعطيل لا يعرض primaryImage ولا تقرأ endpoints الصور ملفات أو metadata، بل تعيد503 بعد فحص الصلاحية المناسب. اختبارات P10 تستخدم مجلدات مؤقتة مملوكة لها فقط؛ لا إنشاء مجلد صور فعلية أو تشغيل مزود على بيانات المستخدم دون تفعيل منفصل.
- سقف أولي512MiB يشمل الملفات والتجهيز المؤقت والحذف المعلق، مع إبقاء2GiB حرة على القرص. حجز مساحة قبل القبول ومنع التجاوز المتزامن؛ الامتلاء يرفض الرفع ولا يحذف صورًا قديمة لإفساح مكان.
- نسخة تطبيق واحدة ومسار دائم هما نطاق أول نسخة؛ توزيع نسخ التطبيق أو حاويات بقرص مؤقت يحتاج عقد تشغيل آخر.

## 3. حدود الصور — قرار مطلوب

الحزمة A المقترحة: **12 صورة غير محذوفة لكل عقار، و8MiB للمصدر الواحد**. البديل B:20 صورة و10MiB. بقية القواعد مشتركة ما لم يطلب تعديلها:

| البند | العقد المقترح |
|---|---|
| وحدة الحجم | MiB = 1,048,576 بايت؛ لا تقريب لحد الحجم |
| الطلب | ملف واحد بالطلب، multipart؛ إجمالي الطلب9MiB للحزمة A أو11MiB للحزمة B، دون batch جزئي ملتبس |
| الأنواع | JPEG/PNG ثابتة8-bit RGB/RGBA/رمادي فقط؛ الامتداد وMIME والمحتوى المفكوك يجب أن تتوافق |
| غير المدعوم | SVG/GIF/APNG/WebP/HEIC/PDF/ZIP وCMYK/16-bit؛ ترفض بوضوح بدل تحويل غير موثوق. صور الهواتف HEIC تحتاج تصدير JPEG/PNG أولًا |
| الأبعاد | أقصر ضلع480px وأطول ضلع640px على الأقل، لا نسبة عرض مفروضة؛ كل ضلع حتى8000px ومجموع حتى16,000,000 بكسل، قبل فك كامل الصورة |
| النسخ المخزنة | JPEG عرض بأطول ضلع حتى2560px، ومصغرة حتى640px، بلا تكبير؛ جودة0.85 وخلفية بيضاء لشفافية PNG |
| سقف الناتج | عرض حتى2MiB ومصغرة حتى256KiB؛ تجاوز الناتج يرفض بوضوح، لا يخفض الجودة أو يقص الصورة مرارًا بصمت |
| الأصل | يحذف المصدر المؤقت بعد المعالجة ولا يحفظ أصل قابل للتنزيل؛ اتجاه EXIF يصحح، ثم تزال EXIF/GPS/XMP وبقية metadata من الناتج |
| المعالجة | طلب رفع واحد متزامن، يشمل استقبال multipart وفكه وتحويله، بحجز مورد قبل تجهيز multipart لا بعده، ودون طابور غير محدود؛ الزائد429، دون تعديل حدود تسجيل الدخول |
| النص البديل | اختياري، نص فقط حتى160حرفًا؛ لا HTML أو اسم ملف أصلي؛ fallback العرض لاحقًا من عنوان العقار لا من EXIF |

رفض ملف تالف أو غير قابل لفك موثوق قبل الحفظ. فحص signature وحده لا يكفي. لا رفع URL ولا جلب ملفات من روابط، ولا إرسال الصور إلى AI أو فاحص عام خارجي. لا وعد بفحص فيروسات أو عزل كامل لمعالج الصور في هذه النسخة؛ يجب توثيق هذه الحدود قبل النشر.

### مكتبة المعالجة المقترحة

إعادة الترميز بـJava ImageIO الحالي، مع **اعتماد مكتبة metadata-extractor المفتوحة المصدر لقراءة اتجاه EXIF فقط** بدل كتابة محلل TIFF يدوي. [المستودع الرسمي](https://github.com/drewnoakes/metadata-extractor) يوضح قراءة metadata وترخيص Apache-2.0. لم تضف المكتبة أو تنزل في P09. يفحص إصدار مثبت وتبعياته وثغراته قبل إضافته في P10؛ إن ظهرت مشكلة أو حاجة لمكتبة أخرى يعاد عرض القرار، لا إضافة تلقائية. المكتبة لا تعني أن كل صيغها أصبحت مدعومة.

## 4. العرض والخصوصية والرئيسية — قرار مطلوب

- ACTIVE وSOLD: صور READY عامة اتساقًا مع التفاصيل الحالية. DRAFT وINACTIVE: ADMIN فقط، حتى لو عرف الزائر imageId أو كان ناشرًا تراثيًا SELLER. لا توسيع لحقوق BUYER.
- جميع القراءة عبر endpoint الباكند الذي يفحص العقار والصورة في كل طلب. لا رابط تخزين مباشر أو public bucket أو signed URL موزع في أول نسخة.
- `Cache-Control: no-store` و`X-Content-Type-Options: nosniff` ونوع `image/jpeg` واسم مولد؛ أخطاء404 لا تكشف مسارًا أو اسمًا أو معلومة حساب. لا تخزين CDN عام أو تخزين صور خاصة في Service Worker.
- تغيير الحالة يمنع القراءات الجديدة غير المصرحة؛ لا يمكن سحب صورة سبق تنزيلها أو إيقاف كل استجابة كانت مصرحًا بها وبدأت بالفعل. لا ادعاء إبطال نسخ المستخدمين.
- أول رفع ناجح يصبح الرئيسية؛ الرفع اللاحق يضاف في النهاية ولا يبدلها. إعادة الترتيب لا تغير الرئيسية إلا باختيار صريح.
- حذف الرئيسية مع صور أخرى يتطلب تحديد بديل صريح من نفس العقار؛ لا يختار الخادم بديلًا عشوائيًا. حذف الصورة الوحيدة مسموح ويعيد العقار بلا صور.
- صور العقار لا تحذف لمجرد تغيير النوع أو إخفاء العرض. INACTIVE يخفيها عن العامة لكنه يبقيها للأدمن.
- مصدر الصور: تصوير يملك الأدمن حقوقه، تفويض صالح، أو ترخيص نشر مناسب. الرفع يتطلب rightsConfirmed=true وrightsBasis=`OWNED/AUTHORIZED/LICENSED`؛ LICENSED يحتاج مرجعًا نصيًا حتى500حرف، لا يجلب الخادم رابطه. الإقرار ومرجعه داخليان ولا يثبتان الحقوق قانونيًا بحد ذاتهما.
- يراجع الأدمن الوجوه ولوحات المركبات والأوراق والبيانات الظاهرة قبل الرفع؛ إزالة GPS لا تزيل المعلومات المرئية داخل الصورة. لا تحميل صور من Google/الإنترنت كعينات. fixtures P10 صور صناعية مملوكة للاختبار.

## 5. عقد API المقترح لـP10

كل المسارات **مقترحة غير منفذة**. mutations ADMIN وCSRF الحالي دون تغيير CORS للأصول أو طريقة المصادقة. الخاص يعيد404 لغير المصرح، والكتابة بلا حساب401/بلا ADMIN403 عند CSRF الصحيح؛ CSRF المفقود/الخاطئ403 وفق التسلسل الحالي.

| العملية | المسار | السلوك |
|---|---|---|
| manifest | `GET /api/properties/{propertyId}/images` | READY فقط بعد التحقق من عرض العقار؛ ترتيب ثابت ورئيسية وrevision؛ بلا صور: قائمة فارغة |
| محتوى | `GET /api/properties/{propertyId}/images/{imageId}/{variant}` | variant=`thumbnail/display` فقط؛ تحقق الربط والحالة في كل مرة، ولا streaming من مسار يرسله العميل |
| رفع | `POST /api/admin/properties/{propertyId}/images` | multipart ملف واحد file، وuploadToken UUID، وحقول الحقوق وaltText الاختياري؛201 للجديد |
| ترتيب/رئيسية/alt | `PUT /api/admin/properties/{propertyId}/images` | JSON كامل لمجموعة READY مع expectedRevision؛ كل المعرّفات الحالية مرة واحدة، ولا حذف ضمني بالإغفال |
| حذف | `DELETE /api/admin/properties/{propertyId}/images/{imageId}?expectedRevision=…&replacementPrimaryImageId=…` | تحقق النسخة والبديل عند الحاجة، ثم إبطال القراءة قبل حذف البايتات؛204 عند الإنجاز،202 إن بقي تنظيف قابل لإعادة المحاولة |

imageId UUID نصي، ومعرّف العقار يبقى Long الحالي. revision رمز عشري نصي لا يمر عبر Number. مثال manifest:

```json
{
  "revision": "3",
  "primaryImageId": "11111111-1111-4111-8111-111111111111",
  "images": [{
    "id": "11111111-1111-4111-8111-111111111111",
    "order": 0,
    "altText": "واجهة العقار",
    "thumbnail": {"url": "/api/properties/15/images/11111111-1111-4111-8111-111111111111/thumbnail", "width": 640, "height": 480},
    "display": {"url": "/api/properties/15/images/11111111-1111-4111-8111-111111111111/display", "width": 2560, "height": 1920}
  }]
}
```

PUT: `{expectedRevision:"3", primaryImageId:"…", images:[{id:"…",altText:"…"}]}`. الأهمية هنا مجموعة كاملة بالترتيب، لا patch ملتبس: حقل ناقص أو مكرر أو معرّف أجنبي400، ونسخة قديمة409 دون تغيير. الرفع يضاف تحت قفل العقار؛ لا يحتاج expectedRevision لكنه يعيد النسخة الجديدة.

uploadToken يحفظ إعادة المحاولة: نفس الرمز والمصدر والحقوق والنص يعيد الصورة القائمة200 دون نسخة أو احتساب حصة جديدة؛ اختلاف payload409. الرمز لا يعيد إحياء صورة حذفت، ويحفظ كسجل إبطال حتى30يومًا. المعرّف ليس إذن وصول.

أخطاء محددة:400 شكل/محتوى/أبعاد/نسخة مفقودة،413 حجم،415 صيغة غير مدعومة،409 حد العدد/نسخة متعارضة/رمز رفع مختلف،429 ازدحام المعالجة،503 تخزين غير مهيأ/غير متاح أو مساحة غير كافية. لا raw exceptions أو مسارات أو أسرار في الأخطاء.

### الإضافة المقترحة لاستجابات العقارات

حقل اختياري `primaryImage` كملخص الصورة السابقة أوnull في PropertyResponse وPropertyMatchResponse، دون إزالة حقول أو تغيير السعر/المساحة أو قواعد P06. باقي المجموعة في manifest، لا كل الصور في كل بطاقة. القراءة bulk للصور الرئيسية لنتائج الصفحة، لا N+1 ولا fetch-join يضاعف صفوف pagination. عملاء المخططات المغلقة قد يحتاجون تحديثًا. P10 يجهز العقد فقط؛ P11/P12 هما واجهة الرفع والعرض.

## 6. المخطط المفاهيمي المقترح — لا SQL منفذ

جدولان إضافيان، دون تعديل قيم Property القديمة:

- `property_image_collections`: property_id فريد/FK، revision، primary_image_id اختياري. لا صف للعقار القديم يعني manifest فارغًا وrevision0. قيد مركب يجعل الرئيسية تابعة لنفس العقار.
- `property_images`: UUID id، property_id/FK، storage_key مولد فريد، upload_token فريد مع property_id، fingerprint داخلي، الحالة READY/DELETING/DELETED، sort_order، alt_text، أبعاد/أحجام النسختين، timestamps، وإقرار مصدر الحق ومستخدمه المأخوذ من الجلسة. لا تخزين BLOB أو اسم أصلي أو EXIF أو URL خارجي.
- قيود للروابط وعدم التكرار والمجالات والحالات، وsort_order فريد للعقار على الصفوف ذات الترتيب؛ المحذوف لا يحتفظ بترتيب. READY فقط يدخل العرض. قفل صف Property الحالي يسلسل التعديلات وحد العدد، وrevision يمنع فقد تعديل من تبويب قديم. لا حذف cascade يفقد مفاتيح ملفات قبل تنظيفها.
- ترقية additive مراجعة، ترفض المخطط الجزئي/المكرر وتترك العقارات القديمة كما هي، وتختبر على PostgreSQL معزول. H2 مفيد لكنه لا يثبت DDL/القيود الفعلية. لا تطبيق تلقائي على db_rushd، ولا ddl-auto=update.

## 7. الفشل والحذف واليتيم والنسخ

- تجهيز خاص باسم UUID، ثم تحقق وإعادة ترميز، ثم قفل/فحص حدود ونقل ذري داخل نفس filesystem وإدخال READY. لا تثبيت READY قبل وجود النسختين. الفشل ينظف ملفات هذه العملية فقط ولا يعدل العقار.
- لا transaction ذرية بين DB والقرص؛ crash بعد النقل وقبل commit قد يترك يتيمًا. يجب اختبار هذه النوافذ، لا ادعاء أن rollback يحذف الملفات تلقائيًا.
- الحذف يغير الحالة إلىDELETING ويضبط الرئيسية/الترتيب/النسخة في DB أولًا؛ لا تقرأ الصورة بعده. تعذر unlink يبقي سجل التنظيف، وإعادة DELETE تكمل التنظيف دون حذف جديد. بعد النجاح DELETED يحتفظ بإبطال uploadToken30يومًا؛ تكرار حذف نفس السجل المنجز204، ومعرّف غير تابع للعقار404.
- أداة صيانة dry-run افتراضيًا: ملفات staging/يتيمة أقدم من24ساعة ولا يشير إليها أي سجل قائم، مع مطابقة storage_key والجذر وعدم اتباع الروابط. التنفيذ الفعلي باختيار operator صريح، وإعادة تحقق تحت قفل التخزين؛ لا job حذف تلقائي أو مسح مجلد شامل في P10. سجلات الحذف لا تزال قبل إزالة ملفاتها، ولا يزال token قبل مدة الاحتفاظ.
- حذف عقار كامل ليس ميزة P10؛ FK يمنع الحذف غير المنسق. عند تنفيذ ذلك مستقبلًا يجب إبطال الوصول وتنظيف الصور قبل إزالة روابطها، لا الاعتماد على CASCADE لملفات القرص.
- سياسة النسخ المقترحة: DB + مجلد الصور وmanifest متناسق أثناء نافذة صيانة معتمدة توقف كتابة الصور، وجهة منفصلة محمية واحتفاظ حتى30يومًا، مع اختبار استعادة معزول. لا نسخ آلي فعلي أو اشتراك جديد الآن؛ اختيار الوجهة وتشغيل النسخ العامة ضمن P31 قبل النشر. الصورة المحذوفة قد تبقى في نسخة محمية حتى نهاية الاحتفاظ. الاستعادة معزولة وميزة الصور معطلة حتى مراجعة النسخة والحذف وحالات النشر، ولا تنشر الصور من نسخة قديمة تلقائيًا؛ دون ذلك لا يمكن ضمان عدم إعادة صورة سبق حذفها.

## 8. التهديدات واختبارات القبول لـP10

خط الدفاع متعدد: صلاحيات وCSRF، allowlist وفك/إعادة ترميز، حدود بايتات وبكسلات وطلب، أسماء مولدة ومسار خاص، وصلاحية قراءة كل طلب. هذه مبادئ متوافقة مع [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)؛ ليست ضمانًا شاملًا أو بديلًا لتحديث المكتبات ومراجعة النشر.

اختبارات إلزامية:

1. ضيف/BUYER/SELLER لا يرفعون أو يغيرون، وCSRF مفقود/خاطئ يرفض، وADMIN يستطيع فقط ضمن العقار والمسار الصحيح؛ لا IDOR.
2. ACTIVE/SOLD عامان، DRAFT/INACTIVE لا يتسربان عبر manifest أو النسختين أو مفاتيح تخزين معروفة؛ تغيير الحالة يبطل الطلبات الجديدة، ولا cache عام.
3. JPEG/PNG صحيحان؛ ملفات مزيفة/تالفة/مقتطعة، polyglot، MIME/امتداد متعارض، SVG/GIF/APNG/HEIC/WebP، traversal وNUL وأسماء طويلة، وURL في موضع ملف، كلها ضمن سلوك الرفض المعلن.
4. حدود الحجم والبكسلات والأبعاد ومن بعدها مباشرة، orientation1–8، alpha على الأبيض، عدم التكبير أو قص الصورة، وإثبات إزالة metadata وعدم حفظ المصدر.
5. أول رئيسية وإضافة/ترتيب/تعديل alt/حذف مع بديل، آخر صورة، null/فارغ، full-set مفقود أو مكرر، النسخة القديمة، وتزامن تجاوز العدد أو اختيار رئيسيتين.
6. إعادة الرفع بنفس token، payload مختلف، ضياع الرد بعد commit، وعدم الإحياء بعد الحذف.
7. قرص ممتلئ/مجلد غير آمن/تعذر قراءة أو نقل أو unlink/فشل DB، ونوافذ crash واليتيم وdry-run الذي لا يحذف ملفًا مرجعيًا. فقد صورة لا يمنع عرض مواصفات العقار.
8. القيم العشرية والصلاحيات ومرشحات P08 وR1/R3/P06 لا تتراجع، وقراءة الرئيسية bulk لا تكسر الصفحات أو تزيد N+1.
9. `mvn clean test` وPostgreSQL المعزول و`npm test/build/lint`، وتجربة HTTP/متصفح مع fixtures صناعية فقط. لا تدعي تجربة فورم غير منفذ قبل P11 أو معرض قبل P12.

## 9. بوابة الإغلاق

اعتمد المستخدم **الخيار A المحلي وحزمة A: 12 صورة/8MiB، والعقد الفني للخصوصية والمعالجة والحقوق والرئيسية والحذف وAPI/schema والمكتبة**. أي تغيير مادي يحتاج اعتمادًا جديدًا. تشغيل SQL والتفعيل على قاعدة المشروع ليسا ضمن هذا الاعتماد.

التحقق في P09: فحص كود وتوثيق ومصادر رسمية وموارد محلية read-only، ثم اتساق الوثيقة والروابط وgit diff --check. لا تشغيل اختبارات التطبيق على تغيير توثيقي فقط، ولا نسبة نتائج502/193 السابقة لهذه الحزمة. لم ترفع أو تنزل صور، ولم تضف تبعيات أو مفاتيح أو migrations، ولم تعِد تشغيل خدمة أو Docker، ولا commit/merge/push.
