# مسودات الأدمن المرتبطة بالحساب — القرارات والتنفيذ المعزول

تحديث 10 نوفمبر 2026: اعتمد المستخدم حفظ نسختي التعارض حتى نهاية المسودة والدمج الصريح، ونُفذ واختبر معزولًا كما في [تقرير الحل وعقد API](admin-draft-conflict-resolution-20261110.md). ملاحظات «حل التعارض غير منفذ» أدناه تاريخية تخص النسخة السابقة؛ لا تزال الميزة غير مفعلة على قاعدة المشروع.

الحالة: **تنفيذ تجريبي معزول ومعطل افتراضيًا، وليس تفعيلًا على قاعدة المشروع أو نشرًا سحابيًا**. طلب المستخدم مسودات مرتبطة بالأدمن نفسه، متاحة من جهاز آخر بعد الاستضافة، وتُحذف عند نجاح حفظ العقار أو يدويًا. يختلف ذلك عن `Property.status=DRAFT`: مسودة التحرير بيانات غير منشورة، وقد تكون غير مكتملة أو غير صالحة للحفظ كعقار.

تحديث 4 نوفمبر 2026: اعتمد المستخدم **الحفظ التلقائي مع إظهار حالته**، و**منع الاستبدال الصامت عند تعارض جهازين أو تغير العقار**، و**عدة مسودات إضافة ومسودة تعديل واحدة لكل عقار**، والتنفيذ والاختبار على بيئة معزولة بجداول وواجهات جديدة مع حفظ العقار وحذف مسودته ذريًا. هذه الموافقة لا تشمل تطبيق SQL أو تفعيل الميزة على قاعدة المشروع الفعلية.

## الوضع التنفيذي وحدود التسليم

- الإعدادان `rushd.drafts.enabled` في الباكند و`VITE_ADMIN_CLOUD_DRAFTS_ENABLED` في الواجهة معطلان افتراضيًا. ملف SQL منفصل ولم يُطبق على قاعدة المشروع. لا تفعيل قبل موافقة منفصلة وخطة استعادة قاعدة البيانات.
- يحفظ المحرر نصوص الحقول ومدخلات تبديل الأنواع عند إقرار الخادم فقط، لا الصور أو كلمات المرور، ولا يستخدم localStorage أو sessionStorage. الحد التنفيذي المفترض 25 مسودة لكل أدمن و64 KiB للمحتوى و16 KiB للحقل الواحد. فتح المسودة وحده لا ينشئ نسخة جديدة.
- تتوقف الكتابة عند اختلاف نسخة المسودة، وتبقى التغييرات غير المحفوظة في الصفحة المفتوحة فقط؛ يجب نسخها قبل مغادرتها. عند تغير العقار الأصلي يتوقف حفظه من المسودة. أضيفت **مراجعة للقراءة فقط** تعرض الفروق بين النموذج المفتوح والمسودة على الخادم والعقار الحالي؛ القراءة لا تدمج أو تستبدل شيئًا، وقد تصبح اللقطة قديمة بعد قراءتها. **حل التعارض/دمج النسخ وإعادة تأسيس المسودة غير منفذ بعد**؛ فلا تُعد هذه النسخة جاهزة للاستخدام الفعلي حتى يُستكمل ويُختبر دون إسقاط أي تعديل محفوظ.
- تُحفظ عملية العقار وحذف محتوى المسودة وإيصال بلا محتوى ضمن معاملة واحدة؛ يسمح الإيصال بمعرفة النتيجة بعد فقد الرد ويمنع التكرار. الإيصالات محفوظة بلا مدة انتهاء حاليًا، ومفاتيح العقار والمالك تمنع الحذف التلقائي الصامت؛ يجب اعتماد سياسة للاحتفاظ والحذف والنسخ الاحتياطية قبل النشر.
- واجهات التنفيذ الحالية تحت `/api/admin/property-drafts`: `GET /context/{propertyId}`، قائمة `GET`، قراءة `GET /{id}`، استعلام نتيجة `GET /{id}/result`، إنشاء `POST`، تحديث `PUT /{id}`، حذف `DELETE /{id}`، وحفظ ذري `POST /{id}/commit`. الإنشاء يستخدم `id` UUID من العميل؛ التحديث يستخدم `revision` و`payload`؛ الحذف `revision` و`operationId`؛ الحفظ الذري `revision` و`operationId` و`property` المحوّل والمتحقق منه على الخادم. لا تقبل العمليات `ownerId` من العميل. **الجدول أدناه مقترح تاريخي وليس وصف العقد التنفيذي الحالي**.
- يلزم قبل النشر اختبار أكثر شمولًا للمتصفح وحالات انقطاع الشبكة، ومراجعة الحد لكل نسخة ومعدل الطلبات، وسياسة الاحتفاظ والنسخ الاحتياطي وHTTPS والاستضافة. لا تضمن تجربة نافذتين على جهاز واحد تجربة أجهزة مستقلة.

- PostgreSQL مؤقت على Docker: نجحت اختبارات ملف الجداول وقيوده ومنع إعادة تطبيقه، و23 اختبارًا مركزًا للمسودات (منها تحديث عقار والحفظ الذري والتراجع عند فشل الإيصال والتعارض والملكية). بعض اختبارات المستودع ضمن هذه المجموعة تستخدم H2 خاصًا بها؛ ليست المجموعة الكاملة للمشروع على PostgreSQL.
- واجهة في نسخة مؤقتة: نجحت 324 حالة `npm test` و`npm run lint` و`npm run build`.
- متصفح معزول وحساب وبيانات تجريبية على H2: إنشاء مسودة واسترجاع الأرقام بعد إعادة التحميل، حفظ عقار واختفاء مسودته، ونافذتان لنفس المسودة ظهر بينهما التعارض ولم تُستبدل النسخة المحفوظة. جُرب أيضًا إلغاء التعديل وإعادة فتح المسودة والحذف اليدوي وإعادة تعديل العقار ثم حفظ تعديله. لم تُختبر أجهزة مستقلة أو الاستضافة الفعلية أو كل حالات الشبكة بصريًا.
- أضيف لاحقًا عرض الفروق النصية للقراءة فقط؛ اختُبر بنافذتين على H2 وظهر عنوان كل نسخة والعقار الأصلي، كما ظهرت رسالة الخطأ عند إيقاف خادم الاختبار. جُرب تسجيل خروج الحساب التجريبي في نافذة أخرى ثم طلب المراجعة؛ ظهرت رسالة الخطأ وبقي النموذج غير المحفوظ مفتوحًا. طلبات المراجعة لا تجدد الجلسة حتى لا يؤدي فشلها إلى إغلاق المحرر. لا يعني ذلك حماية التغييرات غير المؤكدة عند انتهاء الجلسة في العمليات الأخرى.

## 1. نتيجة فحص المشروع

- النموذج في `AdminPropertyForm` يحفظ الإدخال في حالة React داخل المكوّن، وفيه مسودات ذاكرة مؤقتة للتبديل بين أنواع المواصفات؛ مغادرته أو فقد الجلسة قد يضيّعها. حماية `Dashboard` الحالية تختص بمسودة الصور عند تغيير المحرر، ولا تحفظ مواصفات العقار عبر الأجهزة.
- واجهتا العقار الحاليتان هما `POST /api/properties` و`PUT /api/properties/{id}`؛ كلتاهما مقيّدتان بـADMIN، وتقبلان DTO للعقار الصحيح فقط. `PropertyService.updateProperty` يقفل صف العقار ثم يدمج المواصفات ويتحقق منها. `updatedAt` ليس رقم نسخة تفاؤليًا، ولا يكفي وحده لإثبات عدم التغير.
- Auth الحالي يعتمد cookies، وإثبات CSRF للكتابة، وAxios يجدد الجلسة في بعض حالات 401؛ لا ينبغي أن تكرر عملية إنشاء عقار بعد ضياع الرد. إعداد JPA للإنتاج المحلي `ddl-auto=none`. لا نخزن صورًا في جدول خصائص العقار؛ نظام الصور مستقل.
- قاعدة PostgreSQL المحلية **ليست سحابية بمجرد إضافة هذا التصميم**. الوصول من جهاز آخر يتطلب تشغيل backend وقاعدة ثابتة وآمنة وقابلتين للوصول من الجهاز الآخر؛ مزود الاستضافة والنسخ الاحتياطي وHTTPS وإعدادات الشبكة لم تُعتمد بعد. إذا توقف الخادم المحلي أو انقطعت الشبكة فلن تصبح المسودة متاحة سحابيًا.

## 2. معنى المسودة وحدودها المقترحة

- مسودات خاصة بمالكها ADMIN حصريًا، ولكل منها معرف مستقل ونوع: `CREATE` بلا عقار بعد، أو `EDIT` لعقار موجود. اعتمد المستخدم عدة مسودات إنشاء ومسودة تعديل واحدة لكل عقار، مع عدم الاستبدال الصامت بين الأجهزة.
- تحفظ **قيم حقول النموذج الخام كنصوص** بما فيها العربية والفارسية والمساحات والسعر والحقول الاختيارية والمواصفات المنطبقة ومسودات الأنواع إذا أردنا استعادتها. بذلك يمكن حفظ نص مؤقت غير مكتمل مثل `-` أو عدد يتجاوز الدقة بينما يظل نشر العقار مرفوضًا بالتحقق الحالي. لا تقطيع أو تقريب تلقائي، ولا `Number` لحقول المال أو المساحة.
- الهيكل محدد بالإصدار ومسموح الحقول مسبقًا فقط: لا JSON مفتوحًا بلا حدود، ولا حقول مستخدم/role أو مفاتيح مجهولة أو إعدادات أو أكواد/HTML قابلة للتنفيذ. تعرض النصوص كنص React عادي، ولا تُسجّل قيم المسودة الكاملة في logs أو روابط أو analytics. الحقول غير الصحيحة لا تصبح صالحة للنشر بمجرد حفظ المسودة.
- لا صور أو `File` أو base64 أو روابط ملفات أو مفاتيح أو JWT أو CSRF أو كلمات مرور ضمن المسودة. الصور المرفوعة بالفعل تبقى في نظام الصور بصلاحياته؛ الصور غير المرفوعة على جهاز أول **لن تنتقل** تلقائيًا للجهاز الثاني. حذف المسودة لا يحذف صورًا محفوظة. معالجة صور المسودات الجديدة مستقبلًا تحتاج عقدًا خاصًا.
- حدود مبدئية للمراجعة: 25 مسودة لكل أدمن، و64 KiB UTF-8 لكل جسم مسودة، و16 KiB لكل قيمة نصية، مع قائمة محدودة للحقول والأنواع. تحقق الحجم قبل التحليل والتخزين، وعند بلوغ الحد أعد خطأ واضحًا واحتفظ بالمحتوى المعروض؛ لا قص. يلزم التحقق أن الحدود تستوعب طول الوصف الحالي والأحرف العربية والأحجام المجمعة؛ لا يُعتمد أي رقم تلقائيًا.
- المقترح ألا تنتهي المسودات تلقائيًا وأن تبقى حتى الحذف اليدوي أو نجاح الحفظ، اتساقًا مع طلب المستخدم. سياسة النسخ الاحتياطية وحذف الحساب قد تحتفظ بآثار للنسخ لفترة منفصلة معلنة؛ لا يجوز الوعد بحذف فوري من جميع النسخ. تحديد الاحتفاظ وآلية حذف الحساب/العقار يتطلب قرارًا.

## 3. ملكية البيانات والحماية

- يحصل الخادم على `ownerUserId` من الجلسة الموثوقة لا من الطلب. جميع قراءات وكتابات وقوائم المسودات مؤهلة بشرط `owner_user_id = authenticated ADMIN id` بالإضافة إلى فحص دور ADMIN الحالي، وليس بالمعرف أو البريد المرسَل من العميل. الحساب الآخر، حتى لو كان ADMIN، لا يقرأ أو يعدل مسودتك ما لم تُعتمد مشاركة مستقبلًا. المفقود أو غير المملوك يعيد 404 موحدًا؛ معرف عشوائي وحده ليس حماية.
- GET يتطلب مصادقة وصلاحية ADMIN؛ كل POST/PUT/DELETE يتطلب CSRF الحالي. للضيف مع CSRF صحيح 401، وللمسجل غير الأدمن 403، وCSRF الخاطئ/الناقص 403 حسب ترتيب المرشحات. لا تغيير صلاحيات نشر العقارات أو فتح API للعموم.
- `Cache-Control: no-store` لكل الردود التي تحتوي بيانات خاصة، ولا تخزين مسودات أو tokens في localStorage/sessionStorage. الواجهة تمسح نسخ الذاكرة عند الخروج/تغير الحساب وتتجاهل ردود الحساب السابق؛ لا تعرض مسودة حتى يكتمل تحقق المستخدم. فقد الاتصال أو 401 لا يعني أن الحفظ البعيد تم: تعرض حالة متسخة وتسمح بإعادة الدخول دون إرسال تلقائي باسم حساب مختلف.
- تحظر الاستجابات إدراج بيانات أخرى غير لازمة؛ التحميل والعدد محدودان، والترتيب والصفحات على الخادم، مع rate limiting ملائم للخادم وحصص متفق عليها. تحديد طريقة فرض الحصة عند النشر المتعدد يحتاج تصميمًا موزعًا لا يعد به حد ذاكرة عملية واحدة.

## 4. التمثيل والنسخ والتعارض

المقترح جدول جديد مثل `admin_property_drafts` بمعرف UUID ينشئه الخادم، ومالك FK إلى users، ونوع `CREATE/EDIT`، ومعرف العقار إن كان تحريرًا، وحمولة محددة الإصدار وحجمها محدود، ورقم نسخة عددي متزايد، وبصمة نسخة أساس العقار عند بدء التحرير، وتاريخ الإنشاء والتعديل UTC. الفهرس حسب المالك والوقت؛ قيود uniqueness والحصة تُنفّذ مع قفل/قيد آمن وليس `count` منفصلًا وحده. تعريف حذف مستخدم أو عقار مرتبط يحتاج اعتماد سياسة صريحة: لا تحويل تحرير عقار محذوف إلى إنشاء تلقائيًا، ولا حذف مسودته بصمت دون اتفاق.

**تغير العقار الأصلي:** قبل فتح محرر EDIT جديد، تقترح الواجهة قراءة سياق تحرير خاص للأدمن عبر endpoint جديد يعيد القيم الحالية وبصمة محددة الإصدار من نفس لقطة البيانات لكل حقول العقار والمواصفات التي يمكن أن يستبدلها الحفظ، لا `updatedAt` وحده. تثبت بصمة الأساس مع المسودة عند بدئها؛ لا يحسب الخادم بصمة أساس جديدة صامتة عند أول حفظ مسودة قد يأتي بعد تعديل شخص آخر للعقار. عند الاستعادة، تُقرأ بيانات العقار الحالية ويعرض وجود اختلاف. عند طلب حفظ العقار من المسودة، يُقفل صف العقار ويُعاد احتساب بصمته من البيانات المقفلة، ثم تجرى المقارنة والحفظ في المعاملة نفسها. يشمل الحساب كل الحقول المؤثرة، لا بيانات الصور أو الناشر؛ تعرّف طريقة canonicalization والنسخة والثبات واختبارات حواف الأعداد. إذا اختلفت البصمة: **409 دون تعديل أو حذف**، مع إبقاء المسودة ومراجعة المستخدم للبيانات الجديدة؛ لا overwrite ولا merge آلي. كيف تُحل الاختلافات بدقة، ومن يملك صلاحية إعادة تطبيق القيم بعد المراجعة، قرار يحتاج اعتمادًا.

**تعارض الأجهزة:** كل تعديل لمسودة موجودة يقدم `expectedRevision` كنص decimal ويُحدّثها فقط إن تطابقت النسخة تحت قفل أو مقارنة ذرية. إصدار قديم يرجع 409 دون تغيير أي نسخة محفوظة؛ لا last-write-wins. تُعرض للمستخدم خيارات قراءة المسودة الجديدة ونسخ إدخاله الحالي أو مراجعتها، ولا يُستبدل أحدهما بصمت. يرسل المتصفح طلبًا واحدًا في كل مرة للمسودة، ويجمع الكتابة المتتابعة بعد تأخير قصير ويعرض «لم تحفظ/جارٍ الحفظ/حُفظت/تعارض» بناءً على رد الخادم. مع فقد الشبكة تبقى المدخلات في ذاكرة الصفحة أثناء بقائها مفتوحة فقط، ولا تُوصف بأنها محفوظة على الخادم قبل الإقرار. إغلاق جهاز قبل وصول طلبه قد يفقد آخر مدخلات؛ لا ضمان مزامنة لحظية.

## 5. عقد API مقترح — جديد وغير معتمد

المسارات أدناه أمثلة للمراجعة؛ أسماء الحقول ونطاق الاحتفاظ وإضافة schema تحتاج موافقة. لا تغيير لصيغ استجابات أو طلبات العقارات الحالية، ولا تشغيل تخزين الصور أو خدمة خارجية.

| العملية | المقترح |
|---|---|
| قائمة خاصة | `GET /api/admin/property-drafts?page=0&size=20`؛ بيانات موجزة لمسودات صاحب الجلسة فقط، وترتيب ثابت، لا محتوى ناشر/مستخدم آخر |
| سياق تحرير | `GET /api/admin/property-draft-context/{propertyId}`؛ حقائق العقار ونسخة أساس محسوبة من نفس القراءة، مع سياسة إتاحة الأدمن الحالية |
| إنشاء | `POST /api/admin/property-drafts` بجسم محدود `{kind, propertyId?, baseToken?, data, operationId}`؛ `CREATE` بلا propertyId/baseToken و`EDIT` بهما. `operationId` عشوائي ثابت لإعادة المحاولة؛ لا يقبل ownerId |
| قراءة | `GET /api/admin/property-drafts/{draftId}`؛ 200 لصاحبها ADMIN فقط وتتضمن `revision` كنص والبيانات وبصمة الأساس عند وجودها |
| تحديث | `PUT /api/admin/property-drafts/{draftId}` مع `{expectedRevision, data, operationId}`؛ 200 بالنسخة الجديدة، 409 عند اختلاف النسخة أو استخدام operationId بمحتوى مختلف |
| حذف يدوي | `DELETE /api/admin/property-drafts/{draftId}` مع revision/operationId وفق عقد يُراجع؛ حذف المالك فقط. لتفادي حذف نسخة جهاز آخر يجب عدم تجاهل تعارض revision؛ كيفية تمريرها دون تغيير CORS أو كسر دعم clients تراجع قبل التنفيذ |
| حفظ عقار من مسودة | `POST /api/admin/property-drafts/{draftId}/commit` مع `{expectedRevision, operationId}`؛ يتحقق الخادم من بيانات المسودة بDTO العقار الحالي، ثم ينشئ أو يعدل العقار ويلغي محتوى المسودة **في معاملة DB واحدة** ويعيد نتيجة العقار/إيصال العملية |

كل المعرفات والنسخ الجديدة نصوص دقيقة؛ الأسعار الخام نصوص. body محدود UTF-8 ويرفض العناصر المكررة/حقولًا مجهولة غير مسموحة، ويحافظ على العقد الحالي لتحقق الإنشاء/التعديل عند commit. لا ينشأ عقار جديد عند مجرد حفظ المسودة ولا ترسل بياناتها إلى خريطة أو نموذج أو خدمة أخرى.

## 6. الحفظ الذري والرد الضائع

لا يمكن تحقيق وعد «حفظ العقار ثم حذف المسودة دائمًا» بطلبين منفصلين من الواجهة: قد يفشل أحدهما أو ينقطع الاتصال بينهما. المقترح endpoint `commit` خاص يضم قفل مسودة مالكها وفحص النسخة، وفحص أساس العقار إن كان EDIT، وخرائط DTOs والتحقق الحالي، وكتابة العقار وحذف محتوى المسودة، وتسجيل إيصال عملية محكوم، ثم commit لقاعدة البيانات كوحدة واحدة. الفشل قبل commit يلغي الكل، بما فيه فشل التحقق أو رفض الصلاحية أو تعارض أو فشل قاعدة البيانات؛ تبقى المسودة كما كانت. الصور ليست ضمن المعاملة ولا يُدعى نجاح رفعها.

لقطع خطر الإنشاء المكرر عند ضياع رد نجاح أو عند إعادة Axios المحاولة بعد 401، يرسل العميل `operationId` UUID مرة واحدة للعملية ويحفظه في ذاكرة المحاولة. القاعدة تفرض فريدًا ضمن المالك ونوع العملية وتربط الإيصال بمعرف المسودة والنسخة وبصمة الطلب وحالة/معرف العقار الناتج. الإيصال لا يحتوي نص المسودة؛ إعادة الطلب المطابق ترجع النتيجة نفسها بعد التحقق من الملكية والدور، وطلب مختلف بنفس المعرف يرجع 409. تسجيل الإيصال والإنشاء وحذف المحتوى ذرية. حالة commit مجهولة تُعرض للتحقق/إعادة المحاولة بنفس المعرف، لا حفظ جديد. إذا حُذفت بيانات العقار بعد ذلك، لا يعاد إنشاؤه من إيصال قديم ولا تُكشف بيانات خاصة. آلية استعلام نتيجة العملية وفترة الاحتفاظ الدنيا بالإيصال ونتيجة انتهاء الفترة تحتاج اعتمادًا؛ بعد انتهاء الإيصال لا يُضمن تأكيد النتيجة القديمة، لكن طلب commit على مسودة محذوفة لا ينشئ عقارًا جديدًا. يلزم أيضًا تصميم مماثل لطلب إنشاء المسودة نفسه عند ضياع رده.

الـAPI القديم يبقى يعمل دون اشتراط نسخة أو مسودة؛ عميل قديم يستخدمه **لن يحذف تلقائيًا أي مسودة مرتبطة**. حذف مسودة عند حفظ قديم بلا معرفها/نسختها سيكون تخمينًا يمس بيانات، فلا يُضاف دون اعتماد وتغيير عقد صريح. التزامن مع حفظ العميل القديم يُكشف ببصمة الأساس عند commit للمسودة.

## 7. قاعدة البيانات والتفعيل والاختبارات المقترحة

- إصدار migration مستقل مراجع مع اختبارات guards والترقية من النسخة القديمة، جدول/جداول المسودة والإيصال والقيود والفهارس فقط بعد اعتماد العقد؛ الميزة مقترحة معطلة افتراضيًا، و503 واضح عند التعطيل دون استعلام جدول غير موجود. قبل تفعيلها على قاعدة المشروع يلزم اعتماد منفصل، نسخة احتياطية، خطة رجوع وتحقق الاستعادة؛ لا تشغيل SQL على القاعدة الفعلية ضمن الاعتماد على التصميم وحده.
- اختبارات H2 وPostgreSQL معزول: raw قيم غير مكتملة وعربية وفارسية وعشرية دقيقة، Unicode وحدود UTF-8 والحجم والحصة والحقول المجهولة، حالتا CREATE/EDIT ومتعدد المسودات، 401/403/CSRF وIDOR بين أدمنين ومستخدم عادي، no-store وغياب التسرب للسجلات/العامة، واستخدام مسودة بعد تغيير/حذف العقار والحساب.
- سباق جهازين على revision، وتغيير العقار عبر API القديم قبل/أثناء commit، والحذف/الحفظ المتزامن، وضياع رد الإنشاء أو commit وإعادة المحاولة بالمعرف نفسه ومختلف المحتوى، وفشل التحقق/قاعدة البيانات/commit والتأكد من عدم حذف غير المحفوظ أو إنشاء عقارين. إثبات المعاملة يكون على PostgreSQL الحقيقي المعزول لا H2 وحده.
- متصفح معزول بحسابي ADMIN صناعيين وجهازين/سياقين: حفظ تلقائي/صريح حسب القرار، إعادة دخول من الجهاز الآخر، حذف يدوي، نجاح الحفظ وإزالة المسودة، 401 وعدم الخلط بين الحسابات، انقطاع الشبكة ورد ضائع، التعارض وعرض الاختلاف، والجوال وإمكانية الوصول، مع عدم رفع صور أو بيانات شخصية حقيقية. لا ضمان لتجربة أجهزة أو متصفحات غير مجربة.

## 8. القرارات المطلوبة قبل التنفيذ

1. **معتمد:** حفظ تلقائي مع إظهار حالته، دون نشر تلقائي. تفاصيل مهلة الحفظ وحالات الانقطاع تقترح في العقد التنفيذي وتوضح للمستخدم.
2. **معتمد:** عدة إضافات ومسودة تعديل واحدة لكل عقار. حدود العدد والحجم المبدئية في §2 افتراضات تنفيذية يجب اختبارها وتوثيقها، وليست قيمًا لبيانات سوق أو صلاحيات إضافية.
3. **معتمد مبدئيًا:** منع الاستبدال الصامت عند اختلاف العقار الأصلي أو تعارض جهازين. تبقى طريقة مراجعة الفروق وإعادة المحاولة تفصيلًا للتنفيذ مع الحفاظ على نسخ المستخدم.
4. ما سياسة مسودة EDIT إذا حُذف العقار أو حُذف حساب صاحبها؟ وما مدة احتفاظ إيصال العملية والنسخ الاحتياطية؟ لا نفترض حذفًا مفاجئًا أو أبدية البيانات.
5. **معتمد:** تنفيذ معزول بعقد وجداول جديدة وحفظ العقار وحذف مسودته ضمن معاملة واحدة، دون تفعيل على قاعدة المشروع. يجب تصميم سلوك إقرار الحفظ بعد نجاح مجهول واحتفاظ الإيصالات؛ لا تغيير صامت لعقد العقارات القديم.
6. تفعيل قاعدة المشروع الفعلية والاستضافة، وتكاليفها/خصوصيتها والنسخ والاتصال بين الأجهزة، تتطلب خطة واعتمادًا منفصلين. حتى نشر قاعدة وbackend فعليين، يُختبر كل شيء في بيئة معزولة فقط.
